# 概念 18｜ACID 事务、MVCC 与 WAL 预写日志

> **一句话人话定义**：
> - **ACID 事务**：数据库立下的军令状——一组操作（如 A 扣 100 元、B 加 100 元）**要么全成功，要么全当没发生过（原子性 A）**，并发抢购时不互相踩踏（**隔离性 I**），提交了断电也绝不丢（**持久性 D**）；
> - **MVCC（多版本并发控制）**：改数据时不直接擦掉旧值，而是保留旧版本快照，让**“读数据的人看历史快照，写数据的人改最新版本”**，实现读写互不阻塞；
> - **WAL（预写日志）**：提交时不急着去硬盘 5 个角落随机改数据页，而是**先在磁盘末尾顺序追加写一行流水账日志**，既拿到了内存的速度，又保住了断电不丢！

## 1. 它们被什么痛点逼出来的？

有了 [概念 08：B+ 树](./08-B树与B+树.md)，数据库查得飞快了。但一到高并发写数据，三大灾难同时爆发：
1. **转一半断电**：A 账户刚扣了 100 元，服务器断电重启，B 没收到钱，100 元人间蒸发！
2. **读写互卡**：如果一个人正在改某行数据就把这行锁死，那同时来读这行数据的 1,000 个用户全得排队卡死！
3. **随机刷盘太慢**：一次事务改了分散在硬盘 5 个角落的数据页，如果每次提交都等硬盘随机写完这 5 页，每秒只能处理几百单！

## 2. 慢放图解：MVCC 快照读 + WAL 顺序追加写

### 2.1 MVCC：为什么普通 `SELECT` 不用加锁也不会读到改了一半的脏数据？
因为数据库给每一行数据配了一条**历史版本链（Undo Log 版本链）**：

```text
当前最新数据行（事务 #102 正在修改，尚未提交）：
  [ id: 1, balance: 0,   修改事务ID: #102 ]
         │
         ▼ (回滚指针纸条：指向修改前的已提交旧版本)
  [ id: 1, balance: 100, 修改事务ID: #100 (已提交) ]  ◄── 此时别的并发查询进来，直接读这份干净快照！
```
你看：写事务 `#102` 改它的新版本，读请求读 `#100` 的历史快照，**读不拦写、写不拦读**！

### 2.2 WAL（Write-Ahead Logging）：把“5 次随机写”换成“1 次末尾追加写”
硬盘最恨到处乱跳的随机写，最爱顺着末尾往下写的**顺序追加写**（速度差十倍以上）。
于是数据库定下铁律——**日志先行**：

```text
用户点击“确认支付”（提交事务）
   │
   ├─ 第 1 步（纳秒级）：直接修改内存缓冲池（Buffer Pool）里的数据页（此时叫“脏页”）
   │
   ├─ 第 2 步（极速顺序写）：把“账户A减100、账户B加100、状态COMMIT”顺着末尾追加写进硬盘 WAL 日志文件
   │
   ▼
立刻向用户返回“支付成功”！（至于内存里那几个分散的脏数据页，由后台线程趁闲时慢慢刷回硬盘 B+ 树！）
```
**万一刚返回“支付成功”就断电了呢？**
重启后，数据库打开硬盘上的 WAL 日志本从头看一遍：凡是盖了 `COMMIT` 章的记录，在内存里重新执行一遍（**REDO 重做**）；凡是只有开头、没盖 `COMMIT` 章的半截记录，顺着 Undo Log 全部撤销（**UNDO 回滚**）！

## 3. 20 行极简代码原型：用 15 行代码实现 WAL 崩溃重放恢复

```js
// 模拟数据库 WAL（预写日志）与断电重启后的 REDO / UNDO 恢复机制
const walLog = [
  { txId: 1, action: 'BEGIN' },
  { txId: 1, key: 'A', oldVal: 100, newVal: 0 },
  { txId: 1, key: 'B', oldVal: 0,   newVal: 100 },
  { txId: 1, action: 'COMMIT' },  // 事务 1 已盖章提交！
  { txId: 2, action: 'BEGIN' },
  { txId: 2, key: 'A', oldVal: 0,   newVal: -50 } // 事务 2 写了一半突然断电（无 COMMIT）！
]

function recoverFromCrash(logs) {
  const committed = new Set(logs.filter(l => l.action === 'COMMIT').map(l => l.txId))
  const db = { A: 100, B: 0 }
  for (const entry of logs) {
    if (!entry.key) continue
    // 已提交的事务执行 REDO（应用新值），未提交的半截事务跳过/回滚为旧值！
    if (committed.has(entry.txId)) db[entry.key] = entry.newVal
  }
  return db
}
console.log('断电重启恢复后的正确账本:', recoverFromCrash(walLog)) // { A: 0, B: 100 }
```
