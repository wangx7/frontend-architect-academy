# 概念 18｜ACID 事务、MVCC 与 WAL 预写日志

> **一句话人话定义**：
> - **ACID 事务**：数据库立下的生死军令状——一组关联操作（如张三扣 100 元、李四加 100 元）**要么全部成功，要么全部撤回当没发生过（原子性 A）**，并发抢购时互不串味（**隔离性 I**），一旦告诉你“支付成功”哪怕下一秒拔电源也绝不丢账（**持久性 D**）；
> - **MVCC（多版本并发控制）**：改数据时不在原处直接擦掉旧值，而是用[链表](./03-单向链表与双向链表.md)保留修改前的历史版本快照，让**“读数据的人看历史快照，写数据的人改最新版本”**，实现读写互不阻塞；
> - **WAL（预写日志）**：提交事务时不急着去硬盘 5 个角落随机改 B+ 树数据页，而是**先在磁盘日志文件末尾顺序追加写一行流水账**，用 1 次极速顺序写换取 100% 断电不丢！

## 1. 它们被什么痛点逼出来的？

在 [概念 08：B 树与 B+ 树](./08-B树与B+树.md) 里，我们解决了“怎么在两千万行数据里毫秒级查到记录”。但只要一进入真实的高并发交易场景（转账、秒杀下单），三个要命的灾难会同时扑过来：

1. **灾难一（改了一半断电，钱凭空消失）**：
   张三给李四转账 100 元，需要执行两步：① 张三余额 `100 -> 0`；② 李四余额 `0 -> 100`。万一刚执行完第 ① 步，机房跳闸断电了！重启后张三少了 100 元，李四一分钱没收到！（为了消灭“半截子工程”，逼出了 **Undo Log 回滚日志与原子性 Atomicity**）。
2. **灾难二（一个人改数据，一千个读数据的人全被锁在门外干等）**：
   如果事务 `#102` 正在修改商品详情，为了不让别人读到改了一半的脏数据，最笨的办法就是把这行锁死，等 `#102` 提交完才放人进来读——那双十一每秒 1 万个看商品的读请求全得排队卡死！（为了实现“读写完全不互卡”，逼出了 **MVCC 多版本并发控制**）。
3. **灾难三（每次提交都去硬盘随机改 B+ 树页，硬盘直接累趴下）**：
   一笔订单事务可能改了分散在硬盘 5 个不同角落的 16KB 数据页。机械磁头或 SSD 随机跳去 5 个地方写数据的速度极慢，如果每次用户点“支付”都要等这 5 张 B+ 树数据页全部刷入硬盘才返回成功，数据库每秒只能处理几百单！（为了兼顾“断电不丢”与“极致写速度”，逼出了 **WAL 预写日志 / Redo Log**）。

## 2. 逐帧慢放：Undo Log 版本链（MVCC）与 Redo Log 顺序写（WAL）

### 镜头一：MVCC 是怎么靠“历史版本链表 + 活跃事务名单（ReadView）”做到读写不互卡的？

在 MySQL InnoDB 里，每一行数据除了存你定义的字段（如 `id, balance`），还偷偷藏了两个隐藏字段：
- **`trx_id`（最后修改我的事务工号）**：记录是几号事务改出了当前这个版本；
- **`roll_pointer`（回滚门牌号纸条）**：指向这行数据被修改前的**上一个旧版本（存在 Undo Log 里）**！

假设账户 `id = 1` 最初余额是 **`100 元`**（由早已提交的老事务 `#90` 创建）。
现在，写事务 **`#102`** 进来把余额改成了 **`0 元`**，但 **`#102` 还没点提交（未 Commit）**！
就在这一秒，另一个读事务 **`#103`** 进来执行 `SELECT balance FROM account WHERE id = 1`。请看数据库是怎么靠版本链让 `#103` 瞬间读出正确结果且完全不用等锁的：

```text
【内存数据页里的最新版本（由尚未提交的事务 #102 刚改出来的）】
  ┌──────────────────────────────────────────────────────────┐
  │ id: 1  |  balance: 0 元  |  修改人 trx_id: #102 (未提交) │
  └────────────────────────────┬─────────────────────────────┘
                               │
                               │ 顺着 roll_pointer 门牌号纸条往回找旧版本！
                               ▼
【Undo Log 里的历史快照版本（由早已提交的事务 #90 留下的）】
  ┌──────────────────────────────────────────────────────────┐
  │ id: 1  |  balance: 100 元 | 修改人 trx_id: #90  (已提交) │ ◄── 读事务 #103 直接读这一版！
  └──────────────────────────────────────────────────────────┘
```

**读事务 `#103` 的判断法则（ReadView 可见性比对，3 秒看懂）**：
1. 读事务 `#103` 先看最顶上的最新版本 `[balance: 0, 修改人: #102]`；
2. 一查当前“还在干活没提交的事务黑名单”，发现 **`#102` 还在黑名单里（没提交）**！说明这 `0 元` 是未提交的脏数据，**不可见**！
3. 于是 `#103` 顺着 `roll_pointer` 纸条往下走一步，看到旧版本 `[balance: 100, 修改人: #90]`；
4. `#90` 早就提交了，**可见**！当场把 `100 元` 返回给用户！
你看：**写事务 `#102` 在顶楼改它的新版本，读事务 `#103` 顺着纸条去一楼看 `#90` 的老快照，两人连照面都不用打，零加锁、零阻塞！**

### 镜头二：WAL（预写日志 Redo Log）是怎么把“5 次随机写硬盘”变成“1 次末尾追加写”的？

再看写事务 `#102` 终于点击“确认提交（`COMMIT`）”的那一瞬间，数据库到底干了什么：
硬盘最讨厌“东一榔头西一棒子”的**随机写**（比如去硬盘第 100 页改张三、再去第 80000 页改李四），但硬盘极度擅长**在同一个文件末尾顺着往下追加写一行字（顺序写）**——顺序写的速度比随机写快 **10 倍到 100 倍**！

于是数据库立下了 **WAL（Write-Ahead Logging，日志先行）** 铁律：

```text
用户点击“提交事务 (COMMIT)”
   │
   ├─ 第 1 步（内存操作，耗时几百纳秒）：
   │    直接把【内存缓冲池 Buffer Pool】里的张三数据页改为 0、李四数据页改为 100。
   │    （注意：此时内存里的数据页是最新的，但硬盘 B+ 树上的数据页还是旧的，这种内存页叫“脏页”）
   │
   ├─ 第 2 步（硬盘顺序追加写 1 次，耗时仅零点几毫秒）：
   │    在硬盘上的【Redo Log（WAL 预写日志本）】末尾，顺着追加写一行紧凑记录：
   │    "事务 #102：页A偏移x改为0，页B偏移y改为100，状态：已提交 COMMIT！"
   │
   ▼
立刻向用户返回：“转账成功！”
（至于内存里那几张分散的 16KB 脏数据页，由后台线程趁夜深人静或空闲时慢慢写回硬盘 B+ 树！）
```

**灵魂拷问：万一刚向用户返回“转账成功”，后台线程还没来得及把内存脏页写回硬盘 B+ 树，机房突然拔电源断电了，钱会丢吗？**
**绝对不丢！** 因为在返回“转账成功”前，第 2 步已经把那行 `COMMIT` 流水账实打实写进硬盘末尾的 **WAL 日志本**里了！
等服务器通电重启后，数据库第一件事就是翻开硬盘上的日志本：
- **REDO（重做，保持久性 D）**：看到事务 `#102` 在日志本里已经盖了 `COMMIT` 钢印，但硬盘 B+ 树还没改，就照着日志本把张三改成 `0`、李四改成 `100`！
- **UNDO（回滚，保原子性 A）**：如果看到另一个事务 `#105` 在日志本里只写了开头、还没写 `COMMIT` 就断电了，就顺着 Undo Log 把 `#105` 改了一半的数据全部恢复原状！

## 3. 代码逐行带入走读：25 行亲手实现“MVCC 快照读 + WAL 断电重放恢复”

```js
// 1. 模拟 MVCC 版本链：即使事务 #102 正在修改未提交，并发读依然顺着 prev 纸条读到已提交的旧版本
const activeUncommitted = new Set([102]) // 当前正在进行、尚未提交的事务黑名单
const rowVersionChain = {
  balance: 0, trxId: 102,                // 最新版：被未提交的 #102 改成了 0
  prev: { balance: 100, trxId: 90, prev: null } // 历史版：已提交的 #90 留下的 100
}

function mvccSelect(headVersion) {
  let cur = headVersion
  while (cur) {
    // 如果修改该版本的事务不在“未提交黑名单”里，说明它已提交，直接返回这份快照！
    if (!activeUncommitted.has(cur.trxId)) return cur.balance
    cur = cur.prev // 否则顺着回滚纸条看上一个历史版本
  }
}
console.log('MVCC 无锁并发读取的余额:', mvccSelect(rowVersionChain)) // 输出: 100（完美避开脏数据 0！）

// 2. 模拟 WAL 预写日志与断电崩溃后的自动恢复（REDO 已提交事务，丢弃半截未提交事务）
const diskWalLogs = [
  { tx: 101, key: '张三', val: 0 },
  { tx: 101, key: '李四', val: 100 },
  { tx: 101, type: 'COMMIT' },       // 事务 101 已盖章提交！
  { tx: 102, key: '张三', val: -999 } // 事务 102 写了一半突然拔电源（没有 COMMIT 记录）！
]

function crashRecovery(logs) {
  const committedTxs = new Set(logs.filter(l => l.type === 'COMMIT').map(l => l.tx))
  const db = { 张三: 100, 李四: 0 }
  for (const log of logs) {
    if (log.key && committedTxs.has(log.tx)) db[log.key] = log.val // 只重做已 COMMIT 的事务
  }
  return db
}
console.log('断电重启恢复后的账本:', crashRecovery(diskWalLogs)) // { 张三: 0, 李四: 100 }
```

## 4. 前后端架构双视角落地

| 核心机制 | 前端架构中的同构映射 | 后端与系统架构中的核心体现 |
| :--- | :--- | :--- |
| **MVCC（读写分离多版本快照）** | 1. **React Fiber 双缓冲树（`current` vs `workInProgress`）**：屏幕上用户看到的永远是已提交的 `current` 树快照（读），后台正在计算的异步更新在 `workInProgress` 新树上进行（写），算完了再一把切换指针，绝不让用户看到渲染了一半的残缺画面；<br>2. **Immer / Immutable 状态库**：基于结构共享生成新状态版本，旧组件引用依然安全读取旧快照。 | **MySQL InnoDB MVCC**（`ReadView` + `Undo Log` 版本链）、PostgreSQL 多元组版本控制、Git 提交历史树（每次 Commit 生成新树快照而不破坏旧分支读取）。 |
| **WAL（顺序追加日志先行）** | 1. **富文本/在线文档本地防丢草稿**：用户每敲一个字，不立刻重存整篇几兆的排版 JSON，而是往 `IndexedDB` 顺序追加一条轻量操作指令（Delta Op），哪怕浏览器崩溃重启也能重放恢复到最后一秒；<br>2. **Redux / Pinia 时间旅行调试器**：记录 Action 流水日志，随时重放（Redo）或回退（Undo）到任意历史状态。 | **MySQL Redo Log**、**Redis AOF 日志**、**Kafka 消息队列**（之所以下能达到百万级 TPS，正是因为只做磁盘文件末尾顺序追加写！）。 |
