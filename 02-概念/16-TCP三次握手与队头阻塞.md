# 概念 16｜TCP 三次握手、字节流与队头阻塞

> **一句话人话定义**：
> - **TCP 三次握手**：两台电脑正式传数据前，互相打三声招呼（“听得到吗？” ──► “听得到，你听得到我吗？” ──► “我也听得到！”），确保**双方的发送与接收能力均正常，并当面同步双方的起始字节序列号（ISN）**；
> - **队头阻塞（Head-of-Line Blocking）**：在要求严格按序交付的管道中，**排在最前面的 1 个单元（HTTP 响应或 TCP 数据段）一旦延迟或丢失，后面早已准备就绪的其他单元都必须陪绑等待**。

## 1. 它们被什么痛点逼出来的？

互联网底层的 IP 网络是一个“尽力而为（Best-Effort）、不保证送达、也不保证顺序”的邮差：
当你从北京给上海发一段数据时，数据包经过十几个路由器转发，随时可能发生**半路丢包、后发的包走近道先到（乱序）、或者几分钟前迷路的旧连接包突然到达**。

如果浏览器下载 JS 代码时少了一截或者顺序颠倒，网页会直接因语法错误白屏。
于是传输层的 **TCP 协议** 承担起了可靠传输的重任：**给发出去的每一个字节都打上连续的序列号（Sequence Number），收到后回复确认号（ACK），超时未确认则重传，乱序到达则在操作系统内核接收缓冲区里排好队再按序交给上层应用！**

## 2. 第一层（直观模型）与第二层（真实机制）：三次握手与字节流真相

### 镜头一：为什么建立 TCP 连接需要 3 次握手，而不是 2 次？

要建立一条全双工可靠通道，客户端 A 和服务器 B 必须完成两项硬核任务：**① 确认双方的收发通道均正常**；**② 交换并确认双方的初始序列号（ISN，Initial Sequence Number）**：

```text
客户端 A (浏览器)                                             服务器 B (后端)
   │                                                               │
   ├─ 第 1 次握手：SYN (Seq = x)                                   │
   │  “我想建连，我的起始字节编号是 x，你收得到吗？” ─────────────►│
   │                                                               │  ✔ B 确认：【A 能发，B 能收】
   │  第 2 次握手：SYN + ACK (Ack = x + 1, Seq = y)                │
   │  “我收到了 x！下次请从 x+1 发；我的起始编号是 y！”            │
   │◄──────────────────────────────────────────────────────────────┤
   │  ✔ A 确认：【A 能发能收，B 能发能收，且 x 已被 B 确认】       │  ⚠️ 此时 B 尚未确认 y 是否被 A 收到！
   │                                                               │
   ├─ 第 3 次握手：ACK (Ack = y + 1)                               │
   │  “我收到了 y！咱们开始传数据吧！” ───────────────────────────►│  ✔ B 确认：【A 能收，B 能发，且 y 已确认】
```

**真实协议机制补充（为什么 2 次握手无法防御“历史迷路连接请求”？—— RFC 793 核心考量）**：
在复杂网络中，客户端 A 早前发送的一个旧 `SYN (Seq = x_old)` 可能在某个网络节点滞留了很久，A 早已超时重发并完成了通信。如果只有 2 次握手，当这个迟到的幽灵 `SYN` 终于漂到服务器 B 时，B 一回复 `SYN+ACK` 就会单方面认为新连接已建立，白白分配内核 Socket 缓冲区等待数据；而在 **3 次握手**下，客户端 A 收到针对旧序号 `x_old + 1` 的响应后，识别出这是过期的历史连接，会直接发送 `RST`（重置报文）令服务器 B 立即关闭该无效半连接！

### 镜头二：从 HTTP/1.1 到 HTTP/2 再到 HTTP/3，严格区分两类不同层级的“队头阻塞”

要成为架构师，必须精准区分 **“HTTP/1.1 应用层队头阻塞”** 与 **“HTTP/2 下的 TCP 传输层队头阻塞”**：

```text
【层级一：HTTP/1.1 应用层队头阻塞（FIFO 响应顺序约束）】
  理论机制（管线化 Pipelining）：客户端即使连续发送 Req_1(慢接口)、Req_2(快接口)，
  由于 HTTP/1.1 报文没有流编号（Stream ID），客户端只能靠“第几个收到的响应对应第几个请求”来匹配。
  因此服务端必须严格按序返回：
  [ 服务端已算完 Resp_2，但被迫扣留等待 ] ◄── [ 正在慢吞吞生成的 Resp_1 ]
  工程实践：现代浏览器默认禁用 Pipelining，在单条连接上串行请求，靠同域名开 6 条 TCP 连接并发。

══════════════════════════════════════════════════════════════════════════════════

【层级二：HTTP/2 多路复用解决了应用层排队，但受制于 TCP 传输层队头阻塞！】
  HTTP/2 在单条 TCP 连接上为每个请求分配了 Stream ID（如 Stream 1 传 app.js，Stream 2 传 style.css），
  服务端谁先算完谁先发帧。但在操作系统 TCP 内核眼里，不存在 Stream 的概念，只有一条按字节序号递增的流：

  内核 TCP 接收缓冲区：
  ┌─────────────────────────┐   ┌───────────────────────────┐   ┌──────────────────────────┐
  │ ❌ Seq 1000~2000 丢包！ │   │ ✅ Seq 2001~3000 已到达   │   │ ✅ Seq 3001~4000 已到达  │
  │    (内含 app.js 帧)     │   │    (内含 style.css 帧)    │   │    (内含 logo.png 帧)    │
  └────────────▲────────────┘   └─────────────▲─────────────┘   └────────────▲─────────────┘
               │                              └───────────────┬──────────────┘
               └── TCP 顺序交付铁律：Seq 1000~2000 重传到达前，后面两个包严禁上交应用层（全员连坐）！

══════════════════════════════════════════════════════════════════════════════════

【层级三：HTTP/3 (QUIC over UDP) —— 将可靠与有序交付粒度下沉到单个 Stream 内部！】
  Stream 1 (app.js)    ： [ ❌ 包丢失重传中... ]  ──► 仅阻塞 Stream 1 自身后续字节
  Stream 2 (style.css) ： [ ✅ 包已完整到达 ]     ──► 立即交付给浏览器解析 CSS（消除跨流队头阻塞！）
  Stream 3 (logo.png)  ： [ ✅ 包已完整到达 ]     ──► 立即交付给浏览器绘制图片
```

## 3. 第三层（边界与反例）：切勿把“字节流”当成“消息帧”，切勿神化 QUIC

1. **边界一：TCP 是无消息边界的字节流（为什么应用层必须自己做拆包/封包？）**
   TCP `socket.write()` 并不保证“写一次就触发对方一次 `data` 事件”。受 Nagle 算法（合并小包）与 MSS（最大报文段长度，通常约 1460 字节）切分影响，发送方连续写 3 条短消息可能被合并成 1 个 TCP 段到达（俗称**粘包**），而写 1 条 10KB 的大消息又会被拆成 7 个 TCP 段分批到达（**拆包**）。因此上层协议必须显式定义帧边界（如 HTTP/1.1 的 `Content-Length` / `Transfer-Encoding: chunked`，或 HTTP/2 的 `9 字节帧头 Length 字段`）。
2. **边界二：HTTP/3（QUIC）并非消除了所有网络阻塞**
   - **单流内阻塞依然存在**：如果一个 500KB 的 JS 文件在 `Stream 1` 上传输时丢了第 1 个包，该 JS 文件依然无法跳过缺失的字节直接执行；
   - **CPU 与网络设备边界**：QUIC 运行在用户态 UDP 之上，在大带宽满载场景下，用户态加解密与包处理的 CPU 开销通常高于经过硬件网卡卸载（TSO/GRO）优化的内核态 TCP；且部分企业内网防火墙会丢弃 UDP 流量，因此生产环境必须保留向 HTTP/2 回退的能力。

## 4. 可独立运行代码：用 Node `net` 模块复现 TCP 字节流粘包与定长帧拆包器

```js
// tcp-framing-demo.mjs —— 直接用 node 运行，对比原始 TCP 粘包现象与基于长度前缀（Length-Prefixed）的可靠拆包
import net from 'node:net'

// 编码器：在每条消息前加上 4 字节无符号整数表示正文长度（工业级 RPC / HTTP2 通用分帧思想）
function encodeFrame(str) {
  const body = Buffer.from(str, 'utf8')
  const header = Buffer.alloc(4)
  header.writeUInt32BE(body.length, 0)
  return Buffer.concat([header, body])
}

const server = net.createServer(socket => {
  let rawBuffer = Buffer.alloc(0)
  let chunkCount = 0

  socket.on('data', chunk => {
    chunkCount++
    console.log(`[内核网卡上报第 ${chunkCount} 次 data 事件] 收到原始字节数: ${chunk.length}`)
    rawBuffer = Buffer.concat([rawBuffer, chunk])

    // 循环按 4 字节长度头精准切出每一条独立应用层消息，彻底解决粘包与半包！
    while (rawBuffer.length >= 4) {
      const bodyLen = rawBuffer.readUInt32BE(0)
      if (rawBuffer.length < 4 + bodyLen) break // 半包：正文还没收齐，等下一次 data 事件
      const msg = rawBuffer.subarray(4, 4 + bodyLen).toString('utf8')
      console.log('  ──► 成功解出独立消息帧:', msg)
      rawBuffer = rawBuffer.subarray(4 + bodyLen)
    }
  })
})

server.listen(0, () => {
  const client = net.connect(server.address().port, () => {
    // 连续三次写入，TCP 底层通常会合并为 1 次 data 事件送达，但我们的拆包器能精准还原为 3 条消息！
    client.write(encodeFrame('指令1: 登录认证'))
    client.write(encodeFrame('指令2: 查询订单列表'))
    client.write(encodeFrame('指令3: 退出连接'))
    client.end()
  })
})
setTimeout(() => server.close(), 200)
```
