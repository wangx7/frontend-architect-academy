# 概念 16｜TCP 三次握手、字节流与队头阻塞

> **一句话人话定义**：
> - **TCP 三次握手**：两台电脑正式传数据前，互相打三声招呼（“听得到吗？” ──► “听得到，你听得到我吗？” ──► “我也听得到！”），确保**双方的喇叭（发）和耳机（收）都是完好的，并当面核对好各自的起始字节编号**；
> - **TCP 队头阻塞（Head-of-Line Blocking）**：因为 TCP 死守“必须按字节编号严格顺序交付”的家规，**只要排在第 1 号的数据包在半路丢了，哪怕第 2、3、4 号包早就平安抵达了终点，也必须全部扣在门卫室里干等第 1 号包重传回来！**

## 1. 它们被什么痛点逼出来的？

互联网底层的 IP 网络其实是一个“只管往外扔、不保证送到、也不保证先后顺序”的粗糙邮差：
当你从北京给上海发 `"Hello World"` 时，数据包经过十几个路由器转发，随时可能发生三件糟心事：
1. **半路丢包**：路由器太忙，直接把你的包扔进了垃圾桶；
2. **乱序到达**：后发出去的 `"World"` 走了近道先到了，先发出去的 `"Hello"` 堵在路上后到，拼成了 `"WorldHello"`；
3. **迷路迟到的幽灵包**：三分钟前已经作废的一个老连接请求，在网里绕了一大圈突然到了服务器门口。

如果浏览器下载 JS 代码时少了一截或者顺序乱了，网页直接语法报错白屏！
于是传输层的 **TCP 协议** 站出来当起了强迫症总管：**给发出去的每一个字节都打上连续的流水编号（Sequence Number），收到一笔就回一封确认信（ACK），超时没收到回信就重发，顺序乱了就在内存门卫室里排好队再交给浏览器！**

## 2. 逐帧慢放：为什么握手非要 3 次？为什么 HTTP/2 还是逃不出 TCP 队头阻塞？

### 镜头一：为什么打电话握手非要 3 次，2 次行不行？

要建立一条双向都能说话的可靠通道，客户端 A 和服务器 B 必须各自确认两件事：**① 我的喇叭是好的（对方能听见我）** + **② 我的耳机是好的（我能听见对方）**，并且双方要互报自己的**起始字节编号**。
请看三次握手每一声招呼到底确认了什么：

```text
客户端 A (浏览器)                                             服务器 B (后端)
   │                                                               │
   ├─ 第 1 次握手：SYN (我的起始字节编号是 x=100，你听得到吗？) ──►│
   │                                                               │  ✔ 此时 B 确认了：
   │                                                               │    【A 的喇叭好，我 B 的耳机好】
   │                                                               │
   │  第 2 次握手：SYN + ACK (收到 100！请从 101 继续发；          │
   │                         我的起始编号是 y=500，你听得到吗？)   │
   │◄──────────────────────────────────────────────────────────────┤
   │  ✔ 此时 A 确认了：                                            │  ⚠️ 但注意！在这一刻，B 还不
   │    【我的喇叭好、耳机好，B 的喇叭和耳机也全都是好的！】       │     知道自己的喇叭好不好、A
   │                                                               │     能不能收到刚才那声回话！
   ├─ 第 3 次握手：ACK (收到 500！请从 501 开始发，咱们传正事吧！)►│
   │                                                               │  ✔ 至此 B 终于确认了：
   │                                                               │    【我的喇叭好，A 的耳机好！】
```

**为什么绝对不能省成 2 次握手？**
假设只有 2 次握手（B 一发出第 2 声就以为连接建好了）：
万一客户端 A 早上发出的一个 `SYN` 握手包在某个烂路由器里卡了 10 分钟，A 早就放弃重试并关机下班了；结果 10 分钟后这个**幽灵老包**晃晃悠悠漂到了服务器 B 门口。如果只有 2 次握手，B 一回信就直接开辟内存建立连接，坐在那傻等已经关机的 A 发数据，白白浪费服务器资源！有了第 3 次握手，A 不会搭理这封过期回信，B 等不到第 3 次确认就会干脆利落地销毁半连接！

### 镜头二：从 HTTP/1.1 到 HTTP/2 再到 HTTP/3，看清两代“队头阻塞”的真相

假设网页同时要下载三个文件：`1. app.js`、`2. style.css`、`3. logo.png`。

```text
【第一代痛点：HTTP/1.1 应用层队头阻塞（单车道收费站）】
  同一条 TCP 连接上，请求必须排队一个接一个走：
  [ 正在下载巨慢的 app.js ... ] ◄── 后面的 style.css 和 logo.png 连请求都发不出去！
  （所以 HTTP/1.1 时代浏览器被迫对同一个域名偷偷开 6 条 TCP 连接并行跑）

══════════════════════════════════════════════════════════════════════════

【第二代改进与新死穴：HTTP/2 多路复用，却撞上了“TCP 传输层队头阻塞”！】
  HTTP/2 很聪明：只用 1 条 TCP 连接，把 app.js、style.css、logo.png 切成小碎片（Frame 帧）混在一起发！
  但在底下搬砖的操作系统 TCP 内核眼里，它根本不知道上面有 3 个互不相干的文件，
  它只认一条死规矩：“第 1 号字节没交上去之前，第 2、3 号字节死也不准交给浏览器！”

  网卡接收缓冲区现状：
  ┌─────────────────────┐   ┌───────────────────────┐   ┌──────────────────────┐
  │ ❌ 丢包重传中！     │   │ ✅ 早已平安到达！     │   │ ✅ 早已平安到达！    │
  │ TCP包 #1 (属 app.js)│   │ TCP包 #2 (属style.css)│   │ TCP包 #3 (属logo.png)│
  └──────────▲──────────┘   └───────────▲───────────┘   └──────────▲───────────┘
             │                          └─────────────┬────────────┘
             └── 1 号包没补齐前，TCP 内核门卫把早就到齐的 style.css 和 logo.png 全部扣留连坐！

══════════════════════════════════════════════════════════════════════════

【第三代终极根治：HTTP/3 (QUIC 协议) —— 放弃 TCP，改在 UDP 上给每个文件发独立通行证！】
  Stream 1 (app.js)    ： [ ❌ 包#1 丢了重传中... ]  （只卡 app.js 自己！）
  Stream 2 (style.css) ： [ ✅ 包#1 已到 ] ──► 立即交给浏览器解析渲染样式！（彻底消灭连坐阻塞！）
  Stream 3 (logo.png)  ： [ ✅ 包#1 已到 ] ──► 立即交给浏览器画出图标！
```

## 3. 代码逐行带入走读：20 行用 Node `net` 模块亲眼观察 TCP“字节流粘包”

很多转后端的前端第一次写 Socket 程序时，以为客户端调两次 `client.write()`，服务端就会触发两次 `data` 事件。
运行下面这段代码你会亲眼看到：**TCP 眼里根本没有“第一条消息、第二条消息”的边界，它只是一根连续流淌的水管（字节流 Byte Stream）**！

```js
import net from 'node:net'

const server = net.createServer(socket => {
  socket.on('data', chunk => {
    // 服务端一次读取水管里的字节，往往把客户端连续 write 的几句话粘在同一块 Buffer 里收到！
    console.log('服务端收到的原始字节流块:', JSON.stringify(chunk.toString()))
  })
})

server.listen(0, () => {
  const { port } = server.address()
  const client = net.connect(port, () => {
    // 客户端连续调用三次 write 发送三条指令
    client.write('指令1:登录')
    client.write('指令2:查余额')
    client.write('指令3:退出')
    client.end()
  })
})
setTimeout(() => server.close(), 200)
// 终端实测输出：服务端收到的原始字节流块: "指令1:登录指令2:查余额指令3:退出"（三句话粘在了一起！）
```
*(💡 这就是为什么在 TCP 之上设计 HTTP 或 RPC 协议时，必须在头部写明 `Content-Length: 字节长度` 或特殊分隔符 `\r\n`——否则接收方根本不知道一句话到哪里算完！)*
