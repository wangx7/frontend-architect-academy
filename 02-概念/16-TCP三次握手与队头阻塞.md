# 概念 16｜TCP 三次握手、字节流与队头阻塞

> **一句话人话定义**：
> - **TCP 三次握手**：两台机器正式传数据前，互相打三声招呼（“听得到吗？”→“听得到，你听得到我吗？”→“我也听得到！”），确保**双方的喇叭（发）和耳机（收）都是好的，并对齐双方的字节起始编号**；
> - **TCP 队头阻塞（Head-of-Line Blocking）**：因为 TCP 规定必须按字节编号严格顺序交付，**只要第 1 号包在路上丢了，哪怕第 2、3、4 号包早就平安到了，也必须全部扣在门卫室里干等第 1 号包重传回来！**

## 1. 它们被什么痛点逼出来的？

底层 IP 网络是个“只管寄、不包赔”的糙汉子：数据包在光纤和路由器里随时可能**丢包、乱序（后发的先到）、重复**。
但浏览器下载网页或 JS 文件时，绝对不能容忍中间少了一段代码或者前后顺序颠倒。于是传输层的 **TCP 协议** 站了出来：给每一个字节编上连续的序号（Sequence Number），收到就回信确认（ACK），丢了就重发，乱序了就排好队再交给浏览器！

## 2. 慢放图解：为什么握手非要 3 次？为什么 HTTP/2 还是会被 TCP 卡脖子？

### 2.1 为什么三次握手不能省成两次？
每次通信都要确认两件事：**我能发（对方能收）** + **对方能发（我能收）**：

```text
客户端 A                                                服务器 B
   │                                                       │
   ├─ 第 1 次：SYN (我的起始字节编号是 x，你听得到吗？) ──►│  此时 B 确认了：【A能发，B能收】
   │                                                       │
   │  第 2 次：SYN + ACK (收到 x+1！我的起始编号是 y)      │
   │◄──────────────────────────────────────────────────────┤  此时 A 确认了：【A能发能收，B能发能收】
   │                                                       │  ⚠️ 但注意：此时 B 还不知道 A 能不能收到自己的话！
   ├─ 第 3 次：ACK (收到 y+1！咱们开始传正事吧！) ────────►│  至此 B 也确认了：【A能收，B能发】！
```
如果只有两次握手，万一 A 以前发出的一个过期老连接请求在网路上迷路很久突然到了 B，B 一回信就以为连接建好了，白白占着服务器资源傻等！

### 2.2 HTTP/2 明明有了多路复用，为什么还会撞上“TCP 队头阻塞”？
- **HTTP/1.1 的队头阻塞**：同一条连接上，前一个 HTTP 请求没拿到响应，后一个请求连发都发不出去。
- **HTTP/2 的改进與新死穴**：HTTP/2 把 `app.js`、`style.css`、`logo.png` 三个请求拆成小碎片（帧），混在**同一条 TCP 连接**里并发传输。
  但在操作系统内核的 TCP 眼里，它根本不知道上面有三个文件，它只认**一条按序号排列的字节流**！

```text
网卡已收到的 TCP 包：[ 缺失: 包#1(app.js) ]  [ 已到: 包#2(style.css) ]  [ 已到: 包#3(logo.png) ]
                                ▲
                     TCP 内核铁律：包 #1 没重传到达前，#2 和 #3 一律扣留，不准交给浏览器！
```
你看：明明丢的只是 `app.js` 的一个包，结果连早就下载好的 `style.css` 和 `logo.png` 都被连坐卡死！
为了彻底根治这个毛病，**HTTP/3** 干脆抛弃了 TCP，改在 UDP 上造出了 **QUIC 协议**——让每个文件流（Stream）各自独立编号重传，`app.js` 丢包只卡 `app.js` 自己，`style.css` 照常交付渲染！

## 3. 15 行极简代码原型：用 Node `net` 模块观察 TCP 字节流

```js
import net from 'node:net'

// TCP 只认连续字节流，不保留你每次 write 的边界（粘包/拆包现象）
const server = net.createServer(socket => {
  socket.on('data', chunk => {
    console.log('服务端一次收到的字节流:', JSON.stringify(chunk.toString()))
  })
}).listen(0, () => {
  const client = net.connect(server.address().port, () => {
    client.write('第一句话|')
    client.write('第二句话|') // 连续两次 write，在接收端往往被合并成一次 data 事件收到！
    client.end()
  })
})
setTimeout(() => server.close(), 200)
```
