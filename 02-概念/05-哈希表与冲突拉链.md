# 概念 05｜哈希表与冲突拉链（Hash Table / Map）

> **一句话人话定义**：哈希表就是把 **[数组（按数字柜号 1 步直达）](./02-数组与连号房间.md)** 和 **[链表（同柜撞衫时用纸条串起来）](./03-单向链表与双向链表.md)** 合体——先用一道算术公式把字符串名字（如 `"apple"`）当场算成数组的数字柜号，万一两个名字算出了同一个柜号，就在那个柜子里挂一条短链表，从而实现**按任意名字 1 步秒查（`O(1)`）**！

## 1. 它被什么痛点逼出来的？

前面我们学了[数组](./02-数组与连号房间.md)和[链表](./03-单向链表与双向链表.md)，但它们都有一个共同的软肋：**只认位置，不认名字**。
假设你的内存里有 10 万个商品档案，现在用户搜索商品名 `"apple"` 想看它的价格：
- 如果存在**数组**里 `[{ name: 'apple', price: 5 }, ...]`：你手里只有字符串 `"apple"`，根本不知道它住在第几号下标！你只能调用 `arr.find(item => item.name === 'apple')`，让 CPU 从第 `0` 号房间傻乎乎地翻到第 `99999` 号房间（`O(n)`）！
- 如果存在**链表**里：同样得从排头顺着纸条挨个房间核对名字（`O(n)`）！

在前端状态树、Vue 响应式依赖表或后端 Redis 缓存里，每秒钟要按名字查找上百万次。如果每次都从头翻一遍，电脑早就卡死了。

怎么才能**给你一个英文名字 `"apple"`，不用从头翻找，也能像数组下标一样 1 步算出它住在几号房间**？
计算机科学家的脑洞非常简单粗暴：**既然数组只认识数字下标 `0, 1, 2...`，那我们就发明一道算术公式，把英文单词 `"apple"` 当场算成一个数字下标！**

---

## 2. 内存格子逐帧慢放：亲手从 0 造一个 8 格储物柜

别被“哈希函数（Hash Function）”、“拉链法（Separate Chaining）”、“负载因子（Load Factor）”这些黑话吓住。我们现在就在内存里摆一个只有 **8 个格子**的数组 `buckets`（编号 `0` 号柜到 `7` 号柜），一步步把它们推出来！

### 第 1 步：怎么把单词 `"apple"` 算成 `0 ~ 7` 之间的柜号？（哈希函数 = 字符编号相加 + 取余数）

我们要存第一件商品：`"apple" -> 5元`。怎么把字符串 `"apple"` 变成 `0 ~ 7` 里的一个数字？分两小步：

1. **把字母变成数字加起来（算出哈希值 Hash Code）**：
   电脑底层本来就给每个字符编了固定号码（ASCII 编码）：`'a'` 是 `97`，`'b'` 是 `98`，`'p'` 是 `112`，`'l'` 是 `108`，`'e'` 是 `101`。
   我们把 `"apple"` 五个字母的号码加起来：
   ```text
   "apple" 的总点数 = 97('a') + 112('p') + 112('p') + 108('l') + 101('e') = 530
   ```
2. **除以柜子总数 8 看余数（`530 % 8`，取模定位）**：
   算出了 `530`，可我们只有 `0 ~ 7` 共 8 个储物柜，没有第 530 号柜子怎么办？
   小学数学告诉我们：**用任何整数除以 8，算出来的余数（`% 8`）永远只可能是 `0, 1, 2, 3, 4, 5, 6, 7` 里的一个，绝对不会越界！**
   ```text
   柜号 = 530 ÷ 8 = 商 66 …… 余数为 2 ！
   ```

于是，我们直接打开数组的 **`[2]` 号柜**，把 `{ key: "apple", val: 5 }` 放进去！

```text
8 格数组储物柜 (buckets)
  [0] 号柜 ： null
  [1] 号柜 ： null
  [2] 号柜 ： ──► 堆房间 #501 { key: "apple", val: 5, next: null }
  [3] 号柜 ： null
  ...
  [7] 号柜 ： null
```

下次你想查 `"apple"` 多少钱时，根本不用翻遍所有柜子：再算一次 `"apple" -> 530 % 8 = 2`，直接去开 **`[2]` 号柜**，1 步拿到 `5` 元！

---

### 第 2 步：两个人算出了同一个柜号怎么办？（哈希冲突与“拉链法”）

你肯定马上发现了漏洞：**“柜子只有 8 个，全世界的英文单词有几百万个，万一两个不同的单词除以 8 余数刚好一样，撞衫了怎么办？”**
这种“不同名字算出了同一个柜号”的现象，就叫 **哈希冲突（Hash Collision）**。

我们来亲手制造一次撞衫：现在要存第二个商品 `"b" -> 99元`。
- 查表得知字母 `'b'` 的编码是 `98`；
- 除以 8 算余数：`98 ÷ 8 = 商 12 …… 余数也是 2`！

糟糕！`"b"` 算出来也要住 **`[2]` 号柜**，可 `[2]` 号柜里已经住着 `"apple"` 了！如果直接覆盖，`"apple"` 就丢了。怎么办？
还记得我们在 [概念 03：单向链表](./03-单向链表与双向链表.md) 学的绝活吗？
**在 `[2]` 号柜里挂一条单向链表！让 `"b"` 和 `"apple"` 用 `next` 门牌号纸条手拉手串在 `[2]` 号柜后面！**（因为在数组格子后面挂链表像拉链一样，所以行业里管它叫 **“拉链法”**）：

```text
【第 2 个商品 "b"(99元) 撞进 [2] 号柜后的真实内存图】

  [0] 号柜 ： null
  [1] 号柜 ： null
  [2] 号柜 ： ──► #809 { key: "b", val: 99, next: #501 } ──► #501 { key: "apple", val: 5, next: null }
  [3] 号柜 ： null
  ...
  [7] 号柜 ： null
```

注意看！现在 `[2]` 号柜里住了两个人，那电脑执行 `map.get("apple")` 时是怎么找人的？分两步：
1. **第一步（算术定位柜号）**：算 `"apple"` 的余数 `530 % 8 = 2`，1 步跳到 **`[2]` 号柜**；
2. **第二步（顺着柜内短链表核对名字）**：
   - 先看排第一的 `#809`：它的 `key` 是 `"b"`，不是我要找的 `"apple"`，顺着它的 `next` 纸条去看 `#501`；
   - 再看 `#501`：它的 `key` 是 `"apple"`，名字核对上了！当场返回 `val: 5`！
   *(这就是为什么哈希桶链表节点里，除了存值 `val`，**必须把原始名字 `key` 也一起存进去**——因为不存原始名字，撞衫时你就分不清谁是谁了！)*

---

### 第 3 步：柜子塞太多人导致链表变长怎么办？（负载因子 `0.75` 与翻倍扩容 Rehash）

如果我们的储物柜永远只有 8 格，而你往里面塞了 8,000 个商品，平均每个柜子后面都会拖着一条长 1,000 人的链表——那哈希表就退化成慢吞吞的普通链表了！

为了保证每个柜子后面的链表永远只有 1～2 个人，哈希表立下了一条自动扩建家规：
**只要存入的元素个数达到柜子总数的 75%（比如 8 个柜子存满了 6 个元素，这个 `0.75` 就叫“负载因子”），立刻把柜子总数翻倍（从 8 格扩建到 16 格），并把所有人按 `% 16` 重新算一次新柜号搬过去（这叫 Rehash）！**

看一个奇妙的细节：刚才在 8 格柜子里，`"apple"`（530）和字母 `"j"`（ASCII 码 `106`，`106 % 8 = 2`）都挤在 `[2]` 号柜；一旦扩建到 **16 格**，重新按 `% 16` 算余数：
- `"apple"`：`530 ÷ 16 = 33 …… 余 2` ──► 留在新数组的 **`[2]` 号柜**；
- `"j"`：`106 ÷ 16 = 6 …… 余 10` ──► 自动分流搬去了新数组的 **`[10]` 号柜**！

```text
【扩容前：8 格柜子（% 8），"apple"(530) 与 "j"(106) 撞在同一个 [2] 号柜】
  [2] 号柜 ──► [ "j" (106 % 8 = 2) ] ──► [ "apple" (530 % 8 = 2) ]

【扩容后：翻倍成 16 格柜子（% 16），两人自动分家，链表瞬间变短！】
  [2]  号柜 ──► [ "apple" (530 % 16 = 2) ]
  ...
  [10] 号柜 ──► [ "j"     (106 % 16 = 10) ]
```

## 3. 代码逐行带入走读：30 行手写带冲突拉链与原地更新的 `MiniHashMap`

```js
class MiniHashMap {
  constructor(size = 8) {
    // 开辟 8 个连号储物柜，初始全为空 null
    this.buckets = new Array(size).fill(null)
  }

  // 哈希函数：把任意字符串算成 0 ~ 7 之间的柜号
  _hash(key) {
    let sum = 0
    for (const ch of String(key)) sum += ch.charCodeAt(0)
    return sum % this.buckets.length
  }

  set(key, val) {
    const idx = this._hash(key) // 1. 算出柜号
    // 2. 先顺着这个柜子的链表找一圈：如果 key 已经存在，直接改它的 val！
    for (let cur = this.buckets[idx]; cur !== null; cur = cur.next) {
      if (cur.key === key) {
        cur.val = val
        return
      }
    }
    // 3. 如果是新 key（哪怕跟别人撞柜了），用头插法挂在当前柜子的链表最前面（O(1)）
    const newNode = { key, val, next: this.buckets[idx] }
    this.buckets[idx] = newNode
  }

  get(key) {
    const idx = this._hash(key) // 1. 算术 1 步跳到对应柜号
    // 2. 顺着该柜子的短链表逐个核对 key 名字
    for (let cur = this.buckets[idx]; cur !== null; cur = cur.next) {
      if (cur.key === key) return cur.val
    }
    return undefined
  }
}

// 带着具体数值走读验证：
const map = new MiniHashMap(8)
map.set('apple', 5) // 530 % 8 = 2 -> 住进 [2] 号柜
map.set('b', 99)    //  98 % 8 = 2 -> 撞进 [2] 号柜！挂在 "apple" 前面
map.set('apple', 8) // 再次设置 "apple" -> 顺着 [2] 号柜链表找到 "apple"，把 5 改成 8

console.log('2号柜内部拉链:', JSON.stringify(map.buckets[2]))
// 输出: {"key":"b","val":99,"next":{"key":"apple","val":8,"next":null}}
console.log('查 apple:', map.get('apple'), '| 查 b:', map.get('b')) // 8 | 99
```

## 4. 前后端架构双视角落地与哈希表的“唯一死穴”

| 场景维度 | 前端架构中的核心体现 | 后端与系统架构中的核心体现 |
| :--- | :--- | :--- |
| **把 `O(n)` 查找重构为 `O(1)`** | **前端高频性能重构第一招**：当你需要拿订单里的 `userId` 去用户数组 `users` 里匹配用户名时，若在渲染循环里写 `users.find(u => u.id === order.userId)`，1 万条订单 × 1 万个用户 = 1 亿次比对，页面直接卡死；先用 `new Map(users.map(u => [u.id, u]))` 建一张哈希表，再调 `userMap.get(order.userId)`，1 亿次瞬间降为 1 万次（从 500ms 降到 1ms）！ | 1. **Redis 的心脏（`dict` 字典）**：Redis 之所以能每秒处理 10 万次读写，底层就是一张全局哈希表（并且采用“渐进式 Rehash”，把扩容搬家分摊到每次请求里，绝不卡顿主线程）；<br>2. **Java 8+ `HashMap`**：当单个柜子里的冲突链表长度超过 8 时，自动把链表升级为我们在[概念 07](./07-2-3树与红黑树.md) 要学的**红黑树**，防止恶意构造哈希冲突攻击。 |

### 💡 承上启下的灵魂追问：哈希表既然这么快，为什么 MySQL 数据库不用哈希表做默认索引，非要发明树？

仔细看上面 8 格储物柜的图：
因为取余数公式 `% 8` 像一台搅拌机，把原本的大小顺序彻底搅碎了——价格 `5` 元的住 `[2]` 号柜，价格 `99` 元的也住 `[2]` 号柜，价格 `10` 元的可能住 `[7]` 号柜。
- 如果你问哈希表：**“请帮我查 `id = 25` 的商品”**（精确单点查找），哈希表 1 步秒答！
- 但如果你问哈希表：**“请帮我找出所有价格在 `10 元到 50 元之间` 的商品，并按价格从低到高排好序”**（范围查询与排序），哈希表当场傻眼——它只能把所有柜子从 0 号到最后一号全部翻个底朝天（退化成全表扫描 `O(n)`）！

**怎么才能造出一种既支持快速插删查找，又能让所有数据严格按从小到大排好队、支持极速“范围查询”的数据结构？**
