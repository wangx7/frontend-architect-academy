# 概念 02｜数组与连号房间（Array）

> **一句话人话定义**：数组就是在内存里**一口气包下一整排严格连号的房间（`#200`, `#201`, `#202`...）**——因为房间连号，按数字下标找人只需算一道加法（1 步直达 `O(1)`）；但也因为死守“连号不准断”的家规，往队伍中间插一个人或删一个人时，后面所有人都得集体起身搬家（`O(n)`）。

## 1. 它被什么痛点逼出来的？

在 [概念 01：内存门牌号与指针引用](./01-内存门牌号与指针引用.md) 里，我们知道了每个变量都要占一个内存格子。
现在假设你要存全班 100 个学生的成绩，或者一张图片里 100 万个像素点的颜色。你总不能在代码里手写 `score0, score1, score2 ... score99` 一百个变量名吧？
最自然的办法就是向内存管理员申请：**“请给我批一排紧紧挨在一起、门牌号完全连续的 100 个房间！我只需要记住排头第 0 号房间的门牌号，后面的房间靠数数就能找到！”**

这就是所有编程语言里最基础的数据结构——**数组（Array）**。

---

## 2. 内存格子逐帧慢放：看懂数组的“超能力”与“搬家病”

### 镜头一：为什么无论数组有多长，读 `arr[3]` 永远只需 1 步（`O(1)`）？

很多初学者以为：读取 `arr[3]` 时，电脑是从第 `0` 号房间出发，数着 `0 -> 1 -> 2 -> 3` 走过去的。
**完全错误！** 数组之所以快得像闪电，是因为它的房间门牌号是**严格连续且每个房间大小完全相同**的。

假设我们在内存里存了 `arr = [10, 20, 30, 40]`，排头第 `[0]` 号房间住在门牌号 `#200`（为了好算，假设每个数字占 1 个门牌号宽度）：

```text
数组下标 (Index)   ：   [0]       [1]       [2]       [3]
内存门牌号 (Addr)  ：  #200      #201      #202      #203
房间里住的数字     ： [ 10 ]    [ 20 ]    [ 30 ]    [ 40 ]
```

当你写下 `arr[3]` 时，CPU 连看都不看前面的房间，直接用算术电路算出一道小学加法：

```text
目标房间门牌号 = 排头起点门牌号 (#200) + 下标 (3) × 单个房间宽度 (1)
               = #200 + 3
               = #203
```

算出 `#203` 后，CPU 直接去 `#203` 房间把 `40` 拿出来！
想一想这意味着什么：**哪怕这个数组里有 1,000 万个元素，你读取 `arr[0]` 和读取 `arr[9999999]` 花费的时间是一模一样的（都是算一次加法，1 步直达，时间复杂度记作 `O(1)`）！**

### 镜头二：为什么往数组中间或头部插一个数，会引发“全员搬家灾难”（`O(n)`）？

成也连号，败也连号。
既然数组靠“排头门牌号 + 下标”就能算出每个人的位置，那就意味着**数组中间绝对不允许出现空洞，也绝对不允许把新元素挂在外面**。

现在，假设你想在下标 `[1]`（也就是 `#201` 房间）的位置插进一个新数字 `15`，让数组变成 `[10, 15, 20, 30, 40]`。
可是 `#201` 房间里已经住着 `20` 了！怎么办？只能让 `#201` 及后面的所有住户，从后往前挨个往右挪一个房间，把 `#201` 腾出来：

```text
【初始状态】
  下标：   [0]     [1]     [2]     [3]     [4]
  门牌：  #200    #201    #202    #203    #204
  数据： [ 10 ]  [ 20 ]  [ 30 ]  [ 40 ]  [ 空 ]

【第 1 步：把 #203 里的 40 搬去 #204】
  数据： [ 10 ]  [ 20 ]  [ 30 ]  [ 空 ]  [ 40 ]

【第 2 步：把 #202 里的 30 搬去 #203】
  数据： [ 10 ]  [ 20 ]  [ 空 ]  [ 30 ]  [ 40 ]

【第 3 步：把 #201 里的 20 搬去 #202】
  数据： [ 10 ]  [ 空 ]  [ 20 ]  [ 30 ]  [ 40 ]

【第 4 步：终于腾出 #201 了！把新来的 15 住进 #201】
  数据： [ 10 ]  [ 15 ]  [ 20 ]  [ 30 ]  [ 40 ]
```

反过来，如果你调用 `arr.shift()` 删掉排头 `#200` 里的 `10`，为了不让 `#200` 空着，后面的 `15, 20, 30, 40` 又得集体往左搬一格！
如果数组里有 10 万条数据，你在排头 `unshift` 插 1 条数据，后面 10 万条数据全得跟着搬一次家（耗时与数据量 `n` 成正比，记作 **`O(n)`**）。

### 镜头三：连号房间住满了，隔壁又被别人占了怎么办？（动态扩容）

你可能会问：*“如果最初只包下了 `#200 ~ #203` 四个连号房间，现在要 `push` 第 5 个数，偏偏隔壁 `#204` 已经住着别的对象了，不能连号往下扩了怎么办？”*

这时候，数组底层会做一次**“整栋楼搬迁（动态扩容）”**：
1. 去堆内存另一块宽敞的地方，包下一排**原来 2 倍长（8 个连号房间：`#600 ~ #607`）**的新房；
2. 把 `#200 ~ #203` 里的老住户按顺序全部抄到 `#600 ~ #603`；
3. 把第 5 个新数字住进 `#604`（剩下的 `#605 ~ #607` 空着备用，后续再 `push` 就不用搬家了）；
4. 把原来的 `#200 ~ #203` 退租回收！

```text
旧连号房（已满，且 #204 被邻居霸占）：
  #200[10]  #201[20]  #202[30]  #203[40]  │ #204[别人的对象，挡路！]
     │         │         │         │
     └─────────┴────┬────┴─────────┘ (集体搬迁到新批的 8 连号大排房)
                    ▼
新连号房（容量翻倍为 8 格，后 3 格预留给未来的 push）：
  #600[10]  #601[20]  #602[30]  #603[40]  #604[50(新)]  #605[空]  #606[空]  #607[空]
```

### 镜头四：V8 引擎里的隐藏陷阱——别把“快数组”玩成“慢字典”！

在 JavaScript（V8 引擎）里，如果你规规矩矩地按顺序存数据（如 `const arr = [10, 20, 30]`），V8 底层真的会给你分配上面这种极速的连续内存块（叫 **Fast Elements 快数组**）。
但如果你写出了下面这种“跨度极大的空洞代码”：

```js
const arr = []
arr[0] = 10
arr[1000000] = 20 // 中间 999,999 个房间全是空的！
```

V8 一算账：为了存这两个数，居然要浪费一百万个连续房间？太败家了！
于是 V8 会当场把这个数组**降级成一张慢速哈希字典（Dictionary Mode 慢数组）**——从此 `arr[i]` 失去了算术加法 1 步直达的超能力，每次读写都要走复杂的哈希查找，性能暴跌数倍！

## 3. 代码逐行带入走读：实测 `push`（末尾追加）与 `unshift`（头部插队）的百倍差距

你可以把下面这段代码直接粘进 Node 终端或浏览器控制台跑一下：

```js
const N = 100_000 // 测试 10 万条数据

// 1. 末尾追加 push：永远只往最后一个空位放，前面的人完全不用动（O(1)）
console.time('push 末尾追加 10 万次')
const fastArr = []
for (let i = 0; i < N; i++) {
  fastArr.push(i)
}
console.timeEnd('push 末尾追加 10 万次')

// 2. 头部插队 unshift：每插 1 次，后面已有的所有元素都要往右搬 1 格！（累计搬家约 50 亿次，O(n²)）
console.time('unshift 头部插队 10 万次')
const slowArr = []
for (let i = 0; i < N; i++) {
  slowArr.unshift(i)
}
console.timeEnd('unshift 头部插队 10 万次')
```

**运行结果与逐行算账**：
- `fastArr.push(i)`：10 万次循环总共只需约 **`2ms ~ 4ms`**。因为每次 `push` 只是往队尾空房塞数据，哪怕中间触发十几次翻倍扩容，平摊下来每次依然是 `O(1)`。
- `slowArr.unshift(i)`：10 万次循环耗时高达 **`800ms ~ 1,500ms`**，比 `push` 慢了整整 **300 多倍**！因为第 1 次插队搬 0 个人，第 2 次搬 1 个人……第 10 万次插队要搬 99,999 个人，总搬家次数是 `(1 + 100000) × 100000 / 2 ≈ 50 亿次` 内存拷贝！

## 4. 前后端架构双视角落地

| 场景维度 | 前端架构中的核心体现 | 后端与系统架构中的核心体现 |
| :--- | :--- | :--- |
| **连续内存极致性能** | 1. **Canvas 像素处理与 WebGL**：使用 `Uint8ClampedArray`、`Float32Array` 等定长二进制数组（TypedArray），直接在连续内存块上批量读写，传给 GPU 零序列化开销；<br>2. **长列表虚拟滚动（Virtual List）**：10 万条数据存在数组里，根据滚动条高度算出可视区起止下标 `startIdx ~ endIdx`，用 `arr.slice(startIdx, endIdx)` 瞬间切出屏幕可见的 20 条渲染。 | 1. **操作系统内存页（4KB）与 MySQL 数据页（16KB）**：磁盘和内存交换数据的基本单位就是一块固定长度的连续字节数组；<br>2. **高性能网络环形缓冲区（Ring Buffer）**：网卡收发字节流时复用同一块连续数组，彻底消除内存碎片。 |
| **架构避坑铁律** | 1. 严禁在大数组循环中调用 `unshift()`、`shift()` 或中间 `splice()`；如果必须反转顺序，先用 `push()` 收集完再一次性调用 `reverse()`；<br>2. 保持数组紧凑连续，切勿创建下标跨度极大的稀疏空洞数组。 | 数据库如果只用连续有序数组存几千万行记录，每次插入新行都要移动半个磁盘文件——正是为了解决数组“按序存则插入搬家、不搬家则没法快速插删”的死局，才逼出了下一篇的 **[概念 03：单向链表与双向链表](./03-单向链表与双向链表.md)**！ |
