# 概念 02｜数组与连号房间（Array）

> **一句话人话定义**：数组就是在内存里**一口气包下一整排严格连号的房间（`#200`, `#201`, `#202`...）**——因为房间连号，按数字下标找人只需做一次加法（1 步直达 $O(1)$）；但也因为必须死守连号规矩，往中间插一个人时，后面所有人必须集体起身搬家（$O(n)$）。

## 1. 它被什么痛点逼出来的？

如果你要存全班 50 个人的分数，总不能定义 `s1, s2, s3 ... s50` 五十个零散变量。最自然的想法就是向内存管家说：“给我批一排连在一起的 50 个格子，我按 `第 0 号、第 1 号……第 49 号` 顺序放进去！”

## 2. 内存门牌号从 0 到 1 慢放图

### 2.1 为什么 `arr[3]` 能 1 步直达？（加法寻址 $O(1)$）
假设数组 `arr = [10, 20, 30, 40]` 从门牌号 `#200` 开始住（假设每个数字占 1 个格子）：

```text
数组下标：   [0]      [1]      [2]      [3]
内存门牌号： #200     #201     #202     #203
房间里的数： [ 10 ]   [ 20 ]   [ 30 ]   [ 40 ]
```

当你想读取 `arr[3]` 时，电脑**绝不会**傻乎乎地从 `#200` 数到 `#203`。它直接算一道加法：
$$	ext{目标门牌号} = 	ext{起点 } \#200 + 	ext{下标 } 3 = \#203$$
哪怕数组长 1,000 万，读 `arr[999999]` 也是一次加法直达！这就是 **$O(1)$ 随机访问**的物理真相。

### 2.2 为什么往中间插一个数（`splice` / `unshift`）会引发搬家灾难？
现在你想在下标 `[1]`（`#201`）的位置插进一个 `15`，变成 `[10, 15, 20, 30, 40]`。
可是 `#201` 已经住着 `20` 了！为了不破坏“严格连号”的规矩，后面的人只能倒霉地挨个往后挪窝：

```text
第 1 步：把 #203 的 40 搬到 #204  ──►  [ 10 ] [ 20 ] [ 30 ] [ 空 ] [ 40 ]
第 2 步：把 #202 的 30 搬到 #203  ──►  [ 10 ] [ 20 ] [ 空 ] [ 30 ] [ 40 ]
第 3 步：把 #201 的 20 搬到 #202  ──►  [ 10 ] [ 空 ] [ 20 ] [ 30 ] [ 40 ]
第 4 步：把新来的 15 放进 #201！  ──►  [ 10 ] [ 15 ] [ 20 ] [ 30 ] [ 40 ]
```

同理，如果你删掉排头的 `10`（`arr.shift()`），后面的 `15, 20, 30, 40` 全得往前挪一格补齐空位。数据有 $n$ 条，中间插删就要搬动约 $n$ 次（**$O(n)$**）——**这个痛点直接逼出了下一篇的主角：[单向与双向链表](./03-单向链表与双向链表.md)**！

## 3. 15 行极简代码原型：亲手体验末尾追加 `push` 与头部插入 `unshift` 的百倍差距

```js
// 对比数组末尾追加 O(1) 与头部插队 O(n) 的耗时差距
const N = 100_000

console.time('✅ push 末尾追加 10 万次（无需搬家）')
const a1 = []
for (let i = 0; i < N; i++) a1.push(i)
console.timeEnd('✅ push 末尾追加 10 万次（无需搬家）')

console.time('❌ unshift 头部插队 10 万次（每次全员搬家）')
const a2 = []
for (let i = 0; i < N; i++) a2.unshift(i)
console.timeEnd('❌ unshift 头部插队 10 万次（每次全员搬家）')
// 实测：push 仅需约 2ms，而 unshift 高达 800ms~1500ms，慢了好几百倍！
```
