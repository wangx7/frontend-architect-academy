# 概念 06｜二叉搜索树与跷跷板旋转（BST & AVL Rotate）

> **一句话人话定义**：二叉搜索树（BST）就是把“二分查找”刻进每个房间的左右两张门牌号纸条里（**比我小的全挂左手 `left`，比我大的全挂右手 `right`**），兼顾了按大小顺序查找与插入不搬家；一旦因为按顺序插入歪成了单向链表，就用 **“跷跷板旋转（捏住中间节点提上去当新老大）”** 把歪树重新扭平！

## 1. 它被什么痛点逼出来的？

在 [概念 05：哈希表](./05-哈希表与冲突拉链.md) 的结尾，我们撞上了一个死胡同：
- **哈希表的死穴**：取余数公式 `% 8` 把大小顺序彻底搅乱了，没法做**范围查询**（如“找出价格在 `20 元 ~ 60 元` 之间的所有商品”）。
- **有序数组的死穴**：如果把数据从小到大排在[数组](./02-数组与连号房间.md) `[10, 20, 30, 40, 50, 60, 70]` 里，虽然能先看正中间的 `40` 做二分查找（每次排除一半，只需 3 步），也能做范围查询，但每次插入一个新商品 `25`，后面 `30 ~ 70` 全得集体搬家（`O(n)`）！

怎么才能**既保留有序数组“每次从正中间劈一半（二分查找）”的极速，又拥有[链表](./03-单向链表与双向链表.md)“插入新元素只改纸条、全员不搬家”的灵活**？

答案简直像变魔术一样自然：**把排好序的数组 `[10, 20, 30, 40, 50, 60, 70]` 正中间的 `40` 捏起来往上提！**
让每个房间手里拿两张门牌号纸条——左手 `left` 永远指向比自己小的分支，右手 `right` 永远指向比自己大的分支：

```text
【有序数组：插入要全员搬家】
  [ 10 ]   [ 20 ]   [ 30 ]   [ 40 ]   [ 50 ]   [ 60 ]   [ 70 ]

  ══════════ 捏住正中间的 40 往上提，左右再取正中间的 20 和 60 ══════════►

【二叉搜索树（BST）：左小右大，用 left / right 两张纸条连接】
                        ┌─── #100 [ 40 ] ───┐
                        │ (比40小)   (比40大)│
                        ▼                   ▼
                ┌── #205 [ 20 ] ──┐   ┌── #308 [ 60 ] ──┐
                ▼                 ▼   ▼                 ▼
              [ 10 ]            [ 30 ] [ 50 ]         [ 70 ]
```

## 2. 内存格子逐帧慢放：从查找、退化危机到“左旋与右旋手术”

### 镜头一：在二叉搜索树里找人和插人有多爽？（每次劈掉一半 `O(log n)`）

盯着上面那棵树看两个动作：
1. **查 `30` 在不在**：
   - 第 1 步看树根 `[40]`：`30 < 40`，右边 `[60, 50, 70]` 整片区域直接排除！顺着左手纸条去 `[20]`；
   - 第 2 步看 `[20]`：`30 > 20`，左边 `[10]` 直接排除！顺着右手纸条去 `[30]`；
   - 第 3 步：命中 `[30]`！（哪怕树里有 100 万个节点，每次砍掉一半，最多也只需走 **20 步**！这个速度记作 **`O(log n)`**）。
2. **插入新数字 `25`（全员零搬家）**：
   - 顺着 `40(走左) ──► 20(走右) ──► 30(走左)`，发现 `[30]` 的左手 `left` 是空的（`null`）；
   - 直接在堆里开个新房间 `[25]`，把 `[30].left` 的纸条指向 `[25]`！原有的 7 个节点连手指头都没动一下！

---

### 镜头二：致命死穴——按递增顺序插入 `10 -> 20 -> 30`，树直接瘫痪成单向链表！

理想很丰满，现实很骨感。
在真实业务里，订单号、自增主键 ID、时间戳往往是**按从小到大的顺序**进来的。
如果我们往一棵空树里依次插入 `10`、`20`、`30`，严格遵守“比我大的挂右手”的规矩，看看会发生什么惨剧：

```text
第 1 步：插 10          第 2 步：插 20 (比10大挂右)       第 3 步：插 30 (比20大再挂右)
   [ 10 ]                  [ 10 ]                            [ 10 ]  ◄── 第 1 层
                             └──► [ 20 ]                       └──► [ 20 ]  ◄── 第 2 层
                                                                      └──► [ 30 ]  ◄── 第 3 层
```

完了！因为每个新来的数都比前一个大，全挂在了右手 `right` 纸条上，**二叉搜索树彻底向右瘫倒，退化成了一条长长的单向链表**！
如果你按顺序插入 100 万条自增订单，树就有 100 万层高，查找速度从 20 步（`O(log n)`）暴跌回 100 万步（`O(n)`）！

---

### 镜头三：救命手术——怎么用“左旋”与“右旋”把歪脖子扭正，且大小顺序丝毫不乱？

看着上面向右歪成 3 层的 `10 -> 20 -> 30`，你的直觉肯定会喊出来：
**“10、20、30 这三个数里，`20` 才是正中间的数！应该用两只手捏住中间的 `20` 往上提当新老大，让原来的老大 `10` 往左下沉变成 `20` 的左孩子！”**

恭喜你，你刚刚自己发明了平衡树最核心的动作——**左旋（Left Rotate，因为老父亲 `10` 往左边沉下去了）**！

但别急，这里有一个**最考验基本功的细节（孩子过继原则）**：
万一在旋转之前，中间的 `20` 左手本来已经牵着一个孩子 `15`（注意：`15` 比 `10` 大、又比 `20` 小，所以夹在 `10` 和 `20` 中间）呢？
当 `20` 升任新老大后，`20` 的左手（`20.left`）要腾出来去拉老父亲 `10` 了，那原来的左孩子 `15` 岂不是没妈了？
请看下面三帧慢放图，看 `15` 是怎么完美过继给 `10` 的：

```text
【第 1 帧：左旋前（右边太重，且 20 左手还牵着一个拖油瓶 15）】
        [ 10 ]  (老父亲 x)
          └──(右)──► [ 20 ]  (大儿子 y，即将升任新老大)
                    ╱      ╲
           (左) [ 15 ]     [ 30 ] (右)
     (注意：15 比 10 大，但比 20 小！)

【第 2 帧：孩子过继！（把 20 原来的左孩子 15，过继给老父亲 10 当右孩子）】
  为什么 10 的右手刚好能接管 15？
  1. 因为 10 的右手本来牵的是 20，现在要跟 20 解绑，所以 10 的右手刚好空出来了！
  2. 因为 15 本来就在 10 的右边分支里（15 > 10），挂在 10 的右手完全符合“右大”规矩！

【第 3 帧：20 正式上位，左手拉住老父亲 10！（左旋完成，树高从 3 层降为 2 层）】
                  [ 20 ]  (新老大 y)
                 ╱      ╲
        (左) [ 10 ]     [ 30 ] (右)
               └──(右)──► [ 15 ] (过继给 10 当右孩子，10 < 15 < 20 秩序井然！)
```

反过来，如果是依次插入 `30 -> 20 -> 10` 导致树往**左边**歪成了斜棍，我们就捏住中间的 `20` 往上提，让老父亲 `30` 往右下沉（如果 `20` 原来有右孩子 `25`，就过继给 `30` 当左孩子）——这就叫 **右旋（Right Rotate）**！

---

### 镜头四：最容易懵的进阶情况——遇到“拐弯腿（`10 -> 30 -> 20`）”为什么转一次没用？

再想一个尖锐问题：如果依次插入的是 **`10 -> 30 -> 20`**（先往右走，再往左拐，长成了一条**拐弯的狗腿**），你还能直接对 `10` 做左旋吗？

我们试一下：如果你直接对 `10` 做左旋，把 `30` 提上去当老大，那根据刚才的“孩子过继原则”，`30` 的左孩子 `20` 会被过继给 `10` 当右孩子——结果变成了 `30 -> 10 -> 20`，**还是 3 层高的歪树，根本没变矮！**
为什么？因为**排在正中间的数字是底部的 `20`，而不是中间层的 `30`！**

怎么治“拐弯腿”？口诀只有六个字：**先掰直，再旋转！**

```text
【第 1 步：拐弯腿初始状态（10 右挂 30，30 左挂 20）】
    [ 10 ]
      └──(右)──► [ 30 ]
                ╱
             [ 20 ]  (正中间的数字 20 窝在最底下！)

【第 2 步：先对拐点 [30] 做一次局部右旋，把 20 提到中间，把拐弯腿掰成顺直腿！】
    [ 10 ]
      └──(右)──► [ 20 ]
                   └──(右)──► [ 30 ]

【第 3 步：现在变成熟悉的 10 -> 20 -> 30 顺直腿了！对 [10] 做一次左旋，大功告成！】
            [ 20 ]
           ╱      ╲
        [ 10 ]   [ 30 ]
```

把所有失衡形状总结起来，全天下只有这 **4 种旋转套路**（这也是 1962 年诞生的第一代自平衡树 **AVL 树** 的全部家当）：
1. **左左顺直腿（`30 -> 20 -> 10`）**：直接 **右旋** 1 次；
2. **右右顺直腿（`10 -> 20 -> 30`）**：直接 **左旋** 1 次；
3. **左右拐弯腿（`30 -> 10 -> 20`）**：先对 `10` **左旋**掰直，再对 `30` **右旋**；
4. **右左拐弯腿（`10 -> 30 -> 20`）**：先对 `30` **右旋**掰直，再对 `10` **左旋**。

## 3. 代码逐行带入走读：25 行手写二叉树“左旋”与“右旋”指针交接

```js
// 1. 左旋手术：把 x 的右孩子 y 提上去当新根，x 降为 y 的左孩子
function rotateLeft(x) {
  const y = x.right   // ① 先抓稳右孩子 y（比如 20）
  x.right = y.left    // ② 【孩子过继】把 y 原来的左孩子（比如 15）过继给 x 当右孩子
  y.left = x          // ③ y 的左手拉住老父亲 x（10），y 正式上位！
  return y            // ④ 返回新的子树根节点 y
}

// 2. 右旋手术（与左旋完全镜像对称）：把 x 的左孩子 y 提上去当新根，x 降为 y 的右孩子
function rotateRight(x) {
  const y = x.left    // ① 先抓稳左孩子 y
  x.left = y.right    // ② 【孩子过继】把 y 原来的右孩子过继给 x 当左孩子
  y.right = x         // ③ y 的右手拉住老父亲 x，y 正式上位！
  return y
}

// 走读验证：构造镜头四里的“右左拐弯腿” 10 -> 30 -> 20
let root = {
  val: 10, left: null,
  right: { val: 30, left: { val: 20, left: null, right: null }, right: null }
}
root.right = rotateRight(root.right) // 第一步：先对 30 右旋掰直，变成 10 -> 20 -> 30
root = rotateLeft(root)              // 第二步：再对 10 左旋扭平，变成 20 牵着 10 和 30
console.log('扭平后新根:', root.val, '左孩子:', root.left.val, '右孩子:', root.right.val)
// 输出：扭平后新根: 20 左孩子: 10 右孩子: 30
```

## 4. 前后端架构双视角落地与 AVL 树的遗留痛点

| 场景维度 | 前端架构中的核心体现 | 后端与系统架构中的核心体现 |
| :--- | :--- | :--- |
| **有序区间检索** | 1. **视频剪辑/时间轴编辑器**：按时间戳范围 `[startTime, endTime]` 快速查找当前帧命中的所有字幕与贴纸片段；<br>2. **2D/3D 游戏与大画布碰撞检测（四叉树 / BVH 树）**：用空间二分树快速排除 99% 不可能相交的图形。 | 内存有序集合、定时器最小堆/平衡树（快速找出距离现在最近到期的定时任务并执行）。 |

### 💡 承上启下的灵魂追问：既然 AVL 树靠左旋右旋已经能保持平衡了，为什么 Linux 内核、Java 和 C++ 都不用 AVL 树，反而全去用“红黑树”？

因为 **AVL 树的平衡洁癖太严重了**！
AVL 树死板地规定：**“任何节点的左右两条腿，高度差绝对不准超过 1 层！”**
这导致在一棵有 100 万节点的 AVL 树里，当你插入或删除一个节点时，哪怕底下只多出了 1 层，也会触发连锁反应，逼着你从树底一路往上连续做好几次左旋右旋！
在只读不写的场景里 AVL 树很快；但在像操作系统内核调度、网络并发连接管理这样**每秒钟既要高频查、又要高频插删**的场景里，天天忙着旋转调整太耽误工夫了！
