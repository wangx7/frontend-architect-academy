# 概念 19｜一致性哈希圆环与令牌桶限流

> **一句话人话定义**：
> - **一致性哈希（Consistent Hashing）**：把缓存服务器和数据都排在一个首尾相接的钟表圆环上，每个数据顺时针找离自己最近的那台服务器——这样新加或挂掉一台机器时，**只有它附近一小段数据需要搬家，不会引发全站缓存集体失效**；
> - **令牌桶限流（Token Bucket）**：网关门口放一个最多装 100 枚令牌的桶，水龙头每秒往桶里滴 20 枚令牌；每个请求进门必须拿走 1 枚令牌，桶空了就拒之门外（返回 `429`）——**既允许短时间的突发流量，又锁死了长期的平均速率！**

## 1. 它们被什么痛点逼出来的？

当你的网站从 1 台服务器扩到多台服务器时：
1. **普通取模分片的灾难**：如果你有 3 台 Redis 缓存机器，用我们在[概念 05](./05-哈希表与冲突拉链.md) 学的取余数公式 `hash(key) % 3` 分派数据。一旦双十一加了第 4 台机器，公式变成 `hash(key) % 4`——**整整 75% 的数据算出来的余数全都变了！** 75% 的缓存瞬间找不到，全部打穿到数据库（缓存雪崩）！怎么让加减机器时绝大多数数据不挪窝？（逼出了 **一致性哈希**）。
2. **突发流量冲垮后端**：秒杀开始第 1 秒涌进 5 万个请求，而后端每秒只能扛 1,000 个。怎么在网关门口既允许合理的瞬间小高峰，又把超额流量稳稳拦在门外？（逼出了 **令牌桶限流**）。

## 3. 25 行极简代码原型：15 行手写生产级令牌桶限流器

```js
class TokenBucket {
  constructor(capacity = 5, refillPerSec = 2) {
    this.capacity = capacity         // 桶最大容量：允许瞬间突发 5 个请求
    this.refillRate = refillPerSec   // 水龙头速率：每秒补充 2 个令牌
    this.tokens = capacity           // 初始满桶
    this.lastTime = Date.now()
  }
  allowRequest() {
    const now = Date.now()
    // 1. 先算距离上次请求过去了多少秒，补上水龙头这段时间滴入的令牌（最多不超过桶容量）
    const added = ((now - this.lastTime) / 1000) * this.refillRate
    this.tokens = Math.min(this.capacity, this.tokens + added)
    this.lastTime = now
    // 2. 桶里还有至少 1 枚令牌就扣减放行，否则拒绝（429）
    if (this.tokens >= 1) { this.tokens -= 1; return true }
    return false
  }
}

const limiter = new TokenBucket(3, 1) // 桶容量 3，每秒补 1 个
console.log('连续突发 5 次请求的结果:', [1, 2, 3, 4, 5].map(() => limiter.allowRequest()))
// 输出: [ true, true, true, false, false ] —— 前 3 个突发放行，第 4、5 个被精准限流！
```
