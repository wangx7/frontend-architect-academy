# 概念 19｜一致性哈希圆环与令牌桶限流

> **一句话人话定义**：
> - **一致性哈希（Consistent Hashing）**：把缓存服务器和数据都排在一个首尾相接的钟表圆环上，每个数据顺时针找离自己最近的那台服务器——这样新加或挂掉一台机器时，**只有它附近那一小段数据需要搬家，绝不会引发全站缓存集体失效**；
> - **令牌桶限流（Token Bucket）**：网关门口放一个最多装 100 枚令牌的桶，水龙头每秒匀速往桶里滴 20 枚令牌；每个请求进门必须领走 1 枚令牌，桶空了就拒之门外（返回 `429`）——**既允许合理的短时间突发流量，又死死锁住了长期的平均速率！**

## 1. 它们被什么痛点逼出来的？

当你的网站流量暴涨，从 1 台机器扩建到多台机器集群时，两个致命的高并发难题会迎面撞上来：

1. **难题一（加一台缓存机器，为什么反而把数据库干崩了？——逼出一致性哈希）**：
   假设你有 **3 台** Redis 缓存服务器（编号 `0, 1, 2`），存了 1,000 万个商品缓存。
   按我们在 [概念 05：哈希表](./05-哈希表与冲突拉链.md) 学的规矩，最简单的分派办法就是取余数：**`机器编号 = hash(商品ID) % 3`**。
   平时跑得好好的。结果双十一凌晨流量太大，运维紧急扩容加了第 4 台 Redis 机器，公式瞬间变成了 **`hash(商品ID) % 4`**！
   算一算小学数学：原本除以 `3` 和现在除以 `4`，余数还保持不变的数字只占 **`1/4（25%）`**，剩下整整 **`75%` 的商品算出来的机器编号全都变了**！
   这意味着扩容那一秒钟，750 万个热门商品去新编号的机器上查缓存全部扑空（Cache Miss），每秒几十万个读请求瞬间同时穿透打向底层的 MySQL 数据库，数据库当场雪崩暴毙！
   **怎么才能做到：加减一台机器时，90% 以上的数据留在原机器完全不用动？**

2. **难题二（瞬间涌进 10 万个秒杀请求，怎么护住脆弱的后端？——逼出令牌桶限流）**：
   你的后端订单服务每秒钟最多只能处理 **1,000 个请求**。如果整点秒杀那一秒突然冲进来 **50,000 个请求**，不加拦截全放进去，所有机器内存爆满，连正常浏览首页的用户都会一起陪葬。
   可如果你死板地规定“每 1 毫秒只准进 1 个请求（固定匀速漏桶）”，那平时哪怕只有 5 个用户同时点击，后 4 个人也得排队干等！
   **怎么才能“平时攒点余粮应对瞬间小高峰，一旦持续超负荷又立刻把超额流量挡在门外”？**

## 2. 逐帧慢放：钟表圆环顺时针寻址 + 令牌桶水龙头

### 镜头一：一致性哈希圆环是怎么把“75% 大搬家”降到“只搬一小段”的？

一致性哈希的核心脑洞只有一句话：**别用 `% 机器台数`（因为机器台数 `N` 一变，分母就变了）！把分母永远锁死成一个固定不变的圆环（比如 `0 ~ 359 度` 的钟表盘，工业界用 `0 ~ 2³²-1`）！**

1. **机器上环**：先算一下 3 台服务器名字的哈希值对 `360` 取余数，让它们驻扎在圆环的三个固定刻度上：
   - `Node_A` 驻扎在 **`0°`（12 点钟方向）**；
   - `Node_B` 驻扎在 **`120°`（4 点钟方向）**；
   - `Node_C` 驻扎在 **`240°`（8 点钟方向）**。
2. **数据顺时针找主人**：当存一个商品 `k1` 时，同样算出 `hash(k1) % 360` 落在圆环几度，然后**从该刻度出发，顺时针往下走，遇到的第一台机器就是它的主人**！

```text
【正常状态：3 台机器把 360° 圆环均分成三段辖区】
  - 落在 241° ~ 360°(0°) 的数据 ──(顺时针)──► 归 0° 的 Node_A 管
  - 落在 1°   ~ 120°     的数据 ──(顺时针)──► 归 120° 的 Node_B 管
  - 落在 121° ~ 240°     的数据 ──(顺时针)──► 归 240° 的 Node_C 管

══════════════════════════════════════════════════════════════════════════

【扩容瞬间：在 60°（2 点钟方向）新插入一台机器 Node_X！】
                      0° [ Node_A ]
                  . - ~ ~ ~ ~ ~ - .
              , '                   ' ,   ◄── 1° ~ 60° 之间的数据（如 40° 的 k1）：
            ,                           ,     顺时针走最先遇到新来的 60° [ Node_X ]！
           ,                             ,    （只有这一小段数据改嫁给 Node_X！）
          ,                               ,
          ,                               ,  60° [ ✨ 新机器 Node_X ]
           ,                             ,
            ,                           ,   ◄── 61° ~ 120° 之间的数据（如 90° 的 k2）：
              ,                       , '       顺时针走依然归 120° [ Node_B ] 管！纹丝不动！
                ' - , _ _ _ _ _ , - '
         240° [ Node_C ]        120° [ Node_B ]
```

看清楚这个奇迹了吗？
新加入一台 `Node_X (60°)` 后：
- 原来归 `Node_A` 管的（`241°~0°`）：**100% 原地不动！**
- 原来归 `Node_C` 管的（`121°~240°`）：**100% 原地不动！**
- 原来归 `Node_B` 管的后半段（`61°~120°`）：**100% 原地不动！**
- **只有落在 `1° ~ 60°` 这一小段弧线上的数据，从 `Node_B` 搬到了新机器 `Node_X`！**
*(💡 工业细节：为了防止机器太少时在圆环上扎堆站得不均匀，工程上会给每台物理机器化身为 100 个“虚拟节点分身”均匀撒在圆环上，让每台机器分到的流量绝对均衡！)*

### 镜头二：令牌桶限流（Token Bucket）是怎么用一道算术题免掉后台定时器的？

先看令牌桶的物理模型：

```text
          水龙头按恒定速率 r (比如每秒滴入 2 枚令牌)
                          │
                          ▼
               ┌─────────────────────┐
               │   🪙    🪙    🪙    │  ◄── 木桶最大容量 capacity = 3 枚
               └──────────┬──────────┘      (空闲时最多攒满 3 枚，多滴的直接溢出扔掉)
                          │
   用户请求进门 ──► 桶里当前令牌数 >= 1 吗？
                          ├── 是 ──► 拿走 1 枚令牌 (tokens -= 1)，返回 200 放行！
                          └── 否 ──► 桶空了！当场拦在网关门外，返回 429 Too Many Requests！
```

**架构师写代码时的精妙机关（惰性计算令牌，无需 `setInterval` 定时器！）**：
初学者写令牌桶，第一反应是开一个 `setInterval` 每秒往桶里加令牌——但如果网关上有 100 万个不同用户的限流桶，开 100 万个定时器会把内存撑爆！
真正的工业级写法**根本不开定时器**，而是只记录**“上次请求来的时间戳 `lastTime`”**。当新请求到来时，当场算一道减法：
**`这段空闲时间新滴入的令牌数 = (当前时间 now - 上次时间 lastTime) × 每秒速率 r`**，加进桶里（封顶不超过桶容量 `capacity`）即可！

## 3. 代码逐行带入走读：30 行手写“一致性哈希路由器 + 无定时器令牌桶限流器”

```js
// 1. 一致性哈希圆环路由器（基于二分查找顺时针定位最近节点）
class ConsistentHashRing {
  constructor(nodes = []) {
    this.ring = [] // 存放按角度从小到大排好序的 [{ angle, node }]
    nodes.forEach(n => this.addNode(n))
  }
  _hashToAngle(str) {
    let sum = 0
    for (let i = 0; i < str.length; i++) sum = (sum * 31 + str.charCodeAt(i)) % 360
    return sum // 映射到 0 ~ 359 度圆环
  }
  addNode(node) {
    this.ring.push({ angle: this._hashToAngle(node), node })
    this.ring.sort((a, b) => a.angle - b.angle)
  }
  getNode(key) {
    const keyAngle = this._hashToAngle(key)
    // 顺时针找第一个角度 >= keyAngle 的节点；如果走过了头（超过最大角度），就绕回圆环第 0 个节点！
    const hit = this.ring.find(item => item.angle >= keyAngle) || this.ring[0]
    return hit.node
  }
}

// 2. 工业级无定时器令牌桶限流器
class TokenBucketLimiter {
  constructor(capacity = 3, refillPerSec = 1) {
    this.capacity = capacity
    this.rate = refillPerSec
    this.tokens = capacity // 初始满桶 3 枚
    this.lastTime = Date.now()
  }
  allow() {
    const now = Date.now()
    // 惰性结算：算距离上次请求过去了多少秒，补上这段时间滴入的令牌（最多不超过桶上限）
    const added = ((now - this.lastTime) / 1000) * this.rate
    this.tokens = Math.min(this.capacity, this.tokens + added)
    this.lastTime = now
    if (this.tokens >= 1) {
      this.tokens -= 1
      return true  // 200 放行
    }
    return false   // 429 限流拦截
  }
}

const limiter = new TokenBucketLimiter(3, 1) // 桶容量 3，每秒补 1 枚
console.log('瞬间连发 5 次请求:', [1, 2, 3, 4, 5].map(() => limiter.allow()))
// 输出: [ true, true, true, false, false ] —— 前 3 次耗尽桶内积蓄放行，第 4、5 次被精准拦截！
```
