# 概念 11｜闭包背包 Context 与垃圾回收 GC

> **一句话人话定义**：
> - **闭包（Closure）**：就是让原本该随着函数执行结束而被销毁的局部变量，**收拾行李搬进堆内存的专属小背包（`#700 Closure Context`）里续命**，并由返回出来的内层小函数随身揣着 `#700` 的门牌号纸条；
> - **垃圾回收（GC）**：根本不是满内存找垃圾，而是**从全局根（GC Root）出发顺着门牌号纸条点名——凡是顺着纸条摸得着的房间就留着，摸不着的孤岛房间一律清空收回！**

## 1. 它们被什么痛点逼出来的？

按我们在 [概念 04：栈与队列](./04-栈与队列.md) 里学的规矩，每调用一次函数，就会往调用栈顶叠上一个栈帧盘子；**函数一执行完 `return`，它的栈帧盘子就会当场弹出销毁，住在里面的局部变量也跟着灰飞烟灭**。

但这带来了一个致命冲突：
在 JavaScript 里，函数是可以作为返回值带到外面去的！比如你写了一个计数器工厂 `createCounter()`，把里面的小函数 `increment` 返回给了外面的全局变量 `add`。
当 `createCounter()` 执行完退栈后，外面的 `add()` 过了十分钟才被用户点击调用，它里面写了 `return ++count`。如果当初 `createCounter()` 的局部变量 `count` 跟着栈帧一起死了，`add()` 去哪找 `count`？！

为了解决“外层函数已经退栈死了，内层小函数却还要继续读写外层变量”的矛盾，V8 引擎发明了 **“变量逃逸 + 堆内存闭包小背包（Closure Context）”**！

---

## 2. 内存格子逐帧慢放：从“逃逸进背包”到“顺着纸条抓孤岛”

### 镜头一：编译器是怎么决定谁死在栈里、谁搬进堆背包的？

看下面这段代码，V8 引擎在运行前扫描代码时，会给 `createCounter` 里的两个局部变量判处截然不同的命运：

```js
function createCounter() {
  let count = 0               // ⚠️ 被内层函数 increment 用到了！判处“逃逸”，搬进堆背包 #700！
  let temp = '用完即扔的废话'   // 💤 没有任何内层函数用它！留在栈帧里，函数结束当场销毁！
  return function increment() {
    return ++count
  }
}
let add = createCounter()
```

请看 `createCounter()` 执行前后，内存格子的 3 帧慢放：

```text
【第 1 帧：刚进入 createCounter() 时】
  - V8 发现在内层函数里引用了 count，于是在堆区专门开辟一个房间 #700（叫 Closure Context 闭包背包），把 count: 0 放进去；
  - 而没人引用的 temp 留在调用栈帧里。

【第 2 帧：createCounter() 执行 return，弹出栈帧！】
  - 栈帧销毁，里面的 temp 彻底消失；
  - 返回出来的函数对象 increment (#800) 背上多了一张隐藏属性纸条 [[Scopes]]: #700，死死拉住 #700 闭包背包！

  ┌──── 栈区 (Stack) ────┐          ┌──────── 堆区 (Heap) ────────────────────────┐
  │ 全局变量 add (#100)  │          │ 房间 #800 (函数对象 increment)              │
  │   [ 纸条 #800 ]      ├─────────►│   代码逻辑 : return ++count                 │
  └──────────────────────┘          │   [[Scopes]] 背包纸条 : [ 纸条 #700 ]       │
                                    └──────────────────────────┬──────────────────┘
                                                               │ (顺着 #700 纸条摸过去)
                                                               ▼
                                    ┌─────────────────────────────────────────────┐
                                    │ 房间 #700 (Closure Context 闭包专属小背包)  │
                                    │   count : 0  ──(调1次add)──► 1 ──► 2        │
                                    └─────────────────────────────────────────────┘

【第 3 帧：每次再调 createCounter()，都会发一个全新的独立背包！】
  如果你再写一行 let add2 = createCounter()：
  V8 会在堆区新开一个 #701 背包（里面的 count 也是从 0 开始），跟 #700 背包彻底隔离、互不打扰！
```

### 镜头二：React Hooks / 定时器最常踩的“旧闭包背包陷阱（Stale Closure）”是怎么来的？

很多前端写 React 或定时器时遇到过这种灵异事件：明明页面上的 `count` 已经变成 `5` 了，为什么定时器里打印出来的还是 `0`？
用门牌号纸条一看就破案了：
如果每次状态更新都重新执行一次函数、生成一个新的背包（`#701`, `#702`...），而你的老定时器回调 `#800` 手里攥着的 `[[Scopes]]` 纸条依然指着**第一轮创建的老背包 `#700`（里面装的是旧值 `0`）**，它读出来的当然永远是 `0`！

---

### 镜头三：垃圾回收（GC 标记-清除算法）是怎么决定 `#700` 背包生死的？

既然闭包把变量锁在了堆内存 `#700` 里，那岂不是永远占着内存不放了？什么时候才会收回 `#700`？
V8 的垃圾回收器（Garbage Collector）定期做一次**“从根出发顺藤摸瓜点名（Mark-and-Sweep 标记清除）”**：

1. **谁是“根（GC Roots）”？**
   当前正在执行的**调用栈帧里的局部变量**，以及**全局变量（如 `window` / `global`）**，它们是绝对不能删的“老祖宗”。
2. **第一阶段（顺着纸条点名画勾 Mark）**：
   GC 从所有“根”出发，顺着它们手里的门牌号纸条一路往下摸——凡是能摸到的堆房间，脑门上贴一张 **“活着（可达）”** 的绿标签。
3. **第二阶段（清扫孤岛 Sweep）**：
   点名结束后，遍历堆区所有房间——凡是脑门上没有绿标签的房间（哪怕有两个死房间互相指着对方，只要从根出发摸不到它们），一律当成失联孤岛，当场清空退租！

```text
【情况 A：全局变量 add 还指着 #800】
  全局根 add (#100) ──► 摸到 #800 (贴绿标✔) ──► 顺着 [[Scopes]] 摸到 #700 背包 (贴绿标✔)
  结果：#800 和 #700 都活着，GC 绝不敢动！

【情况 B：执行 add = null（撕毁指向 #800 的唯一纸条！）】
  全局根 add (#100) ──► [ null ]   ✕ (断开了！)
                                         #800 (函数) ──► #700 (闭包背包)
                                         (没人从根摸得到它俩，双双沦为孤岛，下次 GC 直接清空回收！)
```

## 3. 代码逐行带入走读：亲眼验证闭包独立背包与内存泄漏黑手

```js
// 1. 验证每次调用外部函数都会分配一个完全独立的闭包背包
function createWallet(owner, initMoney) {
  let balance = initMoney // 逃逸进堆内存闭包背包
  return {
    deposit(amount) {
      balance += amount
      console.log(`${owner} 存入 ${amount}，当前背包余额: ${balance}`)
    },
    getBalance() { return balance }
  }
}

let zhangWallet = createWallet('张三', 100) // 开辟 #700 背包 (balance = 100)
let liWallet = createWallet('李四', 500)    // 开辟 #701 背包 (balance = 500)
zhangWallet.deposit(50)                     // 改的是 #700 背包 -> 150
console.log('李四背包受影响了吗?', liWallet.getBalance()) // 依然是 500！

// 2. 经典前端内存泄漏现场与修复：
function mountComponent() {
  const hugeData = new Array(1_000_000).fill('组件大数组') // 住在 #900，占几兆内存
  const onResize = () => {
    // 因为回调里用到了 hugeData，hugeData 被装进了 onResize 的闭包背包 #705！
    console.log(hugeData.length)
  }
  window.addEventListener('resize', onResize)

  // ✅ 架构铁律：组件卸载时必须返回清理函数撕掉全局监听纸条！
  // 如果不 removeEventListener，全局根 window 会一直拽着 onResize -> 拽着 #705 背包 -> hugeData 永远无法被 GC 回收！
  return () => window.removeEventListener('resize', onResize)
}
```

## 4. 前后端架构双视角落地

| 场景维度 | 前端架构中的核心体现 | 后端与系统架构中的核心体现 |
| :--- | :--- | :--- |
| **状态封装与高阶函数** | 1. **防抖（`debounce`）与节流（`throttle`）**：为什么防抖函数能记住上一次的定时器 `timer` ID？正是因为 `timer` 住进了返回函数的闭包背包里；<br>2. **Vue 3 Composables (`useMouse`, `useFetch`) 与 React Hooks**：利用函数作用域与闭包封装独立逻辑状态。 | 1. **Go 语言的变量逃逸分析（Escape Analysis）**：Go 编译器在编译阶段自动分析变量是否被返回的函数或指针带出函数外部，没带出的分在极速栈上，带出的自动逃逸到堆上由 GC 管；<br>2. **Node.js / Koa 洋葱模型中间件**：通过闭包在 `await next()` 前后保存当前请求上下文耗时与状态。 |
| **线上 OOM（内存泄漏）排障** | 打开 Chrome DevTools `Memory` 面板拍两张堆快照（Heap Snapshot），对比切换路由前后多出来的 `Closure` 对象，90% 的前端内存泄漏都是：**未销毁的全局事件监听、未 `clearInterval` 的定时器、或全局 EventBus 拽住了组件闭包背包**！ | Node.js / Java 服务端若在模块顶层定义全局 `Map` 或数组缓存请求对象且不设 [LRU 上限](./09-LRU缓存淘汰算法.md)，GC 顺着全局变量永远摸得到这些对象，几小时后就会触发服务端 `Heap out of memory` 崩溃重启！ |
