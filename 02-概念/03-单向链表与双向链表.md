# 概念 03｜单向链表与双向链表（Linked List）

> **一句话人话定义**：链表就是**彻底废除数组的“连号坐”规矩**，允许大家散住在内存各处的任意空房间里，靠每个人手里攥着**“下一个人（`next`）和上一个人（`prev`）的门牌号纸条”**单线联系排成一队——从此插队和退队只需改写两张纸条（`O(1)`），所有人原地一动不动！

## 1. 它被什么痛点逼出来的？

在 [概念 02：数组与连号房间](./02-数组与连号房间.md) 里我们看到，数组为了死守“房间门牌号必须连续”的规矩，每次往队伍头部或中间插一个人，后面成千上万个人都得集体起身搬家（`O(n)`）。
如果某个业务场景（比如高频插删的任务列表、React Fiber 节点树、LRU 缓存队列）每秒钟要在队伍中间插删上万次，用数组会直接把 CPU 搬瘫痪。

怎么才能做到**“往队伍中间插人或踢人时，旧住户连屁股都不用抬一下”**？
答案只有一个：**放弃连号房！哪间房空着就住哪间，靠手里的门牌号纸条（[指针引用](./01-内存门牌号与指针引用.md)）把大家串起来！**

## 2. 内存格子逐帧慢放：从单向链表到双向链表的进化

### 镜头一：单向链表（Singly Linked List）——每个人右手只攥着“下一个人”的纸条

假设我们要按顺序存早起三件事：`["起床", "刷牙", "吃早饭"]`。
内存管理员发现 `#105`、`#620`、`#312` 这三个散装房间刚好空着，于是把它们租给我们。为了不弄丢先后顺序，我们在每个房间里多放一张 `next`（下一个）纸条：

```text
链表排头指针 head = #105

  ┌─── 堆房间 #105 ───┐        ┌─── 堆房间 #620 ───┐        ┌─── 堆房间 #312 ───┐
  │ val : "起床"      │        │ val : "刷牙"      │        │ val : "吃早饭"    │
  │ next: [纸条 #620] ├───────►│ next: [纸条 #312] ├───────►│ next: [ null ]    │
  └───────────────────┘        └───────────────────┘        └───────────────────┘
                                                             (null 代表队尾没人了)
```

### 镜头二：单向链表中间插队——为什么“改纸条的先后顺序”错了就会丢数据？

现在，你想在 `#105 ("起床")` 和 `#620 ("刷牙")` 中间插一件新事：`#888 ("穿衣服")`。
请睁大眼睛看：**这一步是所有初学者写链表代码最容易翻车的地方！**

- **❌ 致命错误做法（先改老前辈 `#105` 的纸条）**：
  如果你上来就写 `room105.next = room888`，把 `#105` 手里的纸条从 `#620` 擦掉改成了 `#888`——糟了！全程序再也没有任何人记得“刷牙”住在 `#620` 了！`#620` 和它后面的 `#312` 瞬间在内存里失联丢失（被当成垃圾回收掉）！

- **✅ 正确铁律（新来的人先拉住后辈的手，老前辈再松手拉新人）**：

```text
【第 1 步：让新人 #888 先抄下老前辈 #105 手里的纸条（先拉住后辈 #620）】
  代码：newNode.next = room105.next   (即 #888.next = #620)

  #105 ("起床", next: #620) ─────────────────────────┐
                                                     ▼
                               #888 ("穿衣服", next: #620) ──► #620 ("刷牙") ──► #312 ("吃早饭")

【第 2 步：后辈 #620 已经被 #888 牢牢抓住了，现在放心把 #105 的纸条改成 #888！】
  代码：room105.next = newNode        (即 #105.next = #888)

  #105 ("起床", next: #888) ──► #888 ("穿衣服", next: #620) ──► #620 ("刷牙") ──► #312 ("吃早饭")
```

全程只改了 **2 张纸条**，耗时 `O(1)`，原有的 `#105`、`#620`、`#312` 在各自的房间里纹丝不动！

### 镜头三：单向链表的死穴——为什么手里明明拿着节点 `#620`，却没法在 1 步内删掉它？

单向链表省内存，但它有一个让人抓狂的毛病：**“只认识后任，不认识前任（单向失忆）”**。
假设你手里已经拿到了 `#620 ("刷牙")` 这个节点的引用，现在你想**把 `#620` 从队伍里踢出去**。
想一想：把 `#620` 踢掉，需要改谁手里的纸条？
需要改 **`#620` 前面那个人（`#105 起床`）手里的 `next` 纸条**，让 `#105` 跨过 `#620` 直接指向 `#312`！

可问题是：你站在 `#620` 房间里，低头一看，手里只有指向后面 `#312` 的 `next` 纸条，**根本不知道排在自己前面的老大哥住在 `#105`！**
为了找到前任，你只能极其憋屈地从排头 `head` 出发，挨个房间问：“请问你的 `next` 是 `#620` 吗？”——本来 1 步能干完的删除，硬生生退化成了从头跑腿的 `O(n)`！

### 镜头四：进化成双向链表（Doubly Linked List）——左手记前任 `prev`，右手记后任 `next`！

怎么治好单向链表的“不识前任病”？
非常简单：**每个房间多发一张纸条！左手拿 `prev`（前任门牌号），右手拿 `next`（后任门牌号）！**

```text
  ┌───────── #105 ─────────┐      ┌───────── #620 ─────────┐      ┌───────── #312 ─────────┐
  │ prev: null             │      │ prev: [纸条 #105]      │      │ prev: [纸条 #620]      │
  │ val : "起床"           │◄────►│ val : "刷牙"           │◄────►│ val : "吃早饭"         │
  │ next: [纸条 #620]      │      │ next: [纸条 #312]      │      │ next: null             │
  └────────────────────────┘      └────────────────────────┘      └────────────────────────┘
```

现在，当你手里拿着任意一个节点 `node`（比如 `#620`），想把它从队伍里原地摘除时，根本不需要从头找人，直接原地喊一声：
1. **“喂，我的前任（`node.prev`，即 `#105`），把你的右手（`next`）直接拉住我的后任（`node.next`，即 `#312`）！”**
2. **“喂，我的后任（`node.next`，即 `#312`），把你的左手（`prev`）直接拉住我的前任（`node.prev`，即 `#105`）！”**

```text
【双向链表原地摘除 #620 的两行神仙代码（真正 O(1)！）】
  第 1 步：node.prev.next = node.next   // 让 #105.next 直接指向 #312
  第 2 步：node.next.prev = node.prev   // 让 #312.prev 直接指向 #105

  结果：#105 ("起床") ◄══════════════► #312 ("吃早饭")
                     （#620 被干净利落地摘除！）
```

### 镜头五：架构师写双向链表的偷懒秘籍——“首尾哨兵假节点（Dummy Head / Tail）”

如果你直接写双向链表，每次插入或删除时都要写一堆恶心判断：`if (node.prev === null)`（万一它是排头怎么办？）、`if (node.next === null)`（万一它是队尾怎么办？）。
工业级源码（比如 Vue `<KeepAlive>`、Linux 内核链表、LeetCode 满分写法）都有一个统一秘籍：**预先造两个永远不存真实数据的“假门卫”——假头 `dummyHead` 和假尾 `dummyTail`，让所有真实节点永远夹在两个假门卫中间！**

```text
  [假头 dummyHead] ◄══► [真实节点 1] ◄══► [真实节点 2] ◄══► [假尾 dummyTail]
```
这样一来，任何一个真实节点左边一定有 `prev`、右边一定有 `next`，**全篇代码一个 `if (null)` 判断都不用写**！

## 3. 代码逐行带入走读：带首尾哨兵的工业级双向链表

把下面这段代码复制到终端运行，跟着注释一行行看指针是怎么交接的：

```js
class DoublyLinkedList {
  constructor() {
    // 造两个永远不删的假门卫，初始时假头和假尾手拉手
    this.head = { val: 'HEAD', prev: null, next: null }
    this.tail = { val: 'TAIL', prev: null, next: null }
    this.head.next = this.tail
    this.tail.prev = this.head
  }

  // 在任意已知节点 target 后面插入新节点 newNode（永远 4 行改纸条，无需任何 null 判断！）
  insertAfter(target, newNode) {
    const oldNext = target.next // 先记下 target 原来的后任（比如假尾 TAIL）
    newNode.prev = target       // ① 新人左手拉住 target
    newNode.next = oldNext      // ② 新人右手拉住原来的后任
    oldNext.prev = newNode      // ③ 原来的后任左手改拉新人
    target.next = newNode       // ④ target 右手改拉新人
  }

  // 把任意已知节点 node 从链表里原地摘除（永远 2 行改纸条，真正 O(1)！）
  remove(node) {
    node.prev.next = node.next  // ① 让前任的右手跨过我，直接拉我的后任
    node.next.prev = node.prev  // ② 让后任的左手跨过我，直接拉我的前任
  }
}

const list = new DoublyLinkedList()
const n1 = { val: '起床' }, n2 = { val: '刷牙' }
list.insertAfter(list.head, n1) // HEAD <-> 起床 <-> TAIL
list.insertAfter(n1, n2)        // HEAD <-> 起床 <-> 刷牙 <-> TAIL
list.remove(n1)                 // 1 步摘除“起床”：HEAD <-> 刷牙 <-> TAIL
console.log('摘除后排第一的是:', list.head.next.val) // 输出: 刷牙
```

## 4. 数组 vs 链表终极对比与架构落地

先把两者的脾气对照表刻在脑子里：

| PK 维度 | 数组（连号房间） | 链表（散装房间 + 门牌号纸条） |
| :--- | :--- | :--- |
| **按位置编号找人（读第 `i` 个）** | ⚡️ **`O(1)` 1 步算术直达**（`起点 + i`） | 🐢 **`O(n)` 必须从排头顺着纸条跑 `i` 趟腿** |
| **往中间或头部插入 / 删除** | 🐢 **`O(n)` 后面所有人集体搬家** | ⚡️ **`O(1)` 已知节点时只需改 2~4 张纸条** |

| 场景维度 | 前端架构中的核心体现 | 后端与系统架构中的核心体现 |
| :--- | :--- | :--- |
| **框架与内核底座** | 1. **React Fiber 架构**：为什么 React 16 要把原来的递归虚拟 DOM 树彻底重构成 **Fiber 链表**？因为递归卡死主线程没法停；而每个 Fiber 节点存了三张纸条：`child`（大儿子）、`sibling`（右边的亲弟弟）、`return`（老父亲），变成单向链表后，时间片一到只需拿一个全局变量记下当前节点的门牌号就能随时暂停，下一帧顺着纸条继续跑！<br>2. **Vue 3.4+ 响应式重构**：将属性订阅集合从 `Set` 重构为双向链表节点，大幅降低了内存占用与 GC 压力。 | 1. **MySQL InnoDB [B+ 树](./08-B树与B+树.md) 叶子页双向链表**：所有底层 16KB 数据页之间全靠 `FIL_PAGE_PREV` 和 `FIL_PAGE_NEXT` 两张双向链表纸条串联，范围查询时顺着链表横扫；<br>2. **Linux 内核任务调度与 `epoll` 就绪队列（`list_head`）**：操作系统管理成千上万个活跃进程与就绪网卡事件，全靠带哨兵的双向循环链表实现 `O(1)` 挂载与摘除。 |

> 💡 **承上启下的灵魂追问**：
> 数组**查得快（`O(1)`）但插删要搬家（`O(n)`）**；链表**插删不搬家（`O(1)`）但找人要从头跑腿（`O(n)`）**。
