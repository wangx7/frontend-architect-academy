# 概念 08｜B 树与 B+ 树（B-Tree & B+ Tree）

> **一句话人话定义**：为了适配块存储设备（SSD/磁盘）**按固定页（InnoDB 默认 `16KB`）批量读写**的特性，**B 树**将 [2-3 树](./07-2-3树与红黑树.md) 的小节点扩展成了能容纳成百上千个路标的 **M 叉节点**；而数据库广泛采用的 **B+ 树** 进一步规定：**① 内部节点（非叶目录页）仅存放索引键（Key）与子页指针（Page Pointer），不存放完整行数据，从而最大化单页分支因子（Fan-out）；② 所有完整行记录（或二级索引的主键引用）均存放在最底层叶子页，且叶子页之间通过[双向链表](./03-单向链表与双向链表.md)按序相连，兼顾了极低树高与高效顺序范围扫描！**

## 1. 它被什么痛点逼出来的？

在 [概念 07：2-3 树与红黑树](./07-2-3树与红黑树.md) 中我们知道，红黑树是**纯内存数据结构**的佼佼者。但当数据量达到千万级、且必须持久化保存在磁盘（SSD 或机械硬盘）上时，直接把二叉树搬上磁盘会遭遇两个物理瓶颈：

1. **二叉树的树高（Height）在百万/千万级规模下偏高**：
   - 完美平衡二叉树的高度约为 `log2(N)`（100 万节点约 `20` 层，1,000 万节点约 `24` 层）；
   - 而**红黑树**由于容许红黑交替路径，其理论高度上界为 **`h <= 2 × log2(N + 1)`**（即 100 万节点最坏可达约 `40` 层，实际平均约 `20~25` 层）。
2. **磁盘与操作系统页缓存以“页（Page）”为最小读写单元，且未命中内存时延迟高昂**：
   - CPU 访问内存仅需约 `100 ns`，而一旦发生缓存未命中（Cache Miss）需要去 SSD 读取，耗时约为 `50,000 ~ 150,000 ns`（机械盘更是高达数毫秒），相差 **3 到 5 个数量级**；
   - MySQL InnoDB 存储引擎默认以 **`16KB`（`innodb_page_size = 16384` 字节）** 为一个逻辑与物理读写页。如果用二叉树存储，每个节点只有几十字节，每次沿着指针向下走一层，若目标节点不在同一页内，就可能触发一次昂贵的 `16KB` 页加载，读上来 `16KB` 却只用了其中几十字节！

**破局思路**：既然每次页加载固定是 `16KB`，那就**让树的每一个节点恰好对应一张 `16KB` 的数据页**，在一个节点里并排塞进几百上千个路标（多路平衡查找树），把 20 多层的瘦高树压扁成 **3～4 层的矮胖树**！

## 2. 第一层（直观模型）与第二层（真实机制）：B 树 vs B+ 树结构剖析

### 镜头一：B 树（B-Tree）与 B+ 树（B+ Tree）的真实存储结构差异

请看两者在**内部节点（非叶子页）**与**叶子节点（底层页）**上的核心结构对比：

```text
【结构 A：B 树（B-Tree）—— 内部节点与叶子节点均存储“键 + 数据记录（或记录指针）”】
  ┌───────────────────────── 1 张 16KB 的 B 树内部节点 ─────────────────────────┐
  │ 子页P1 │ Key:10 + 行数据Payload │ 子页P2 │ Key:20 + 行数据Payload │ 子页P3 │
  └─────────────────────────────────────────────────────────────────────────────┘
  - 特点：如果在顶层碰巧命中 Key=10，无需走到叶子层即可直接返回；
  - 局限：
    1. 若内部节点直接内联存储较大的行数据 Payload，单页能容纳的 Key 数量（分支因子）会显著下降，导致树变高；
    2. 做范围查询（如 WHERE id BETWEEN 10 AND 50）时，需要在内部节点和不同层的子节点之间来回做中序遍历跳转。

══════════════════════════════════════════════════════════════════════════════════

【结构 B：B+ 树（B+ Tree，InnoDB 索引模型）—— 内部目录页纯存“路标键 + 子页号”，数据全在底层双向链表！】
  ┌───────────────────── 1 张 16KB 的 B+ 树上层目录页（非叶节点） ─────────────────────┐
  │ [ 最小键:10 | 子页号:P1 ]  │  [ 最小键:20 | 子页号:P2 ]  │  [ 最小键:30 | 子页号:P3 ] │
  └─────────────┬──────────────────────────────┬──────────────────────────────┬────────┘
                ▼                              ▼                              ▼
  ┌─── 底部叶子页 P1 (16KB) ───┐ ┌─── 底部叶子页 P2 (16KB) ───┐ ┌─── 底部叶子页 P3 (16KB) ───┐
  │ 10: 张三完整行  15: 王五   │◄─►│ 20: 李四完整行  28: 赵六   │◄─►│ 30: 孙七完整行  40: 周八   │
  └────────────────────────────┘ └────────────────────────────┘ └────────────────────────────┘
         (页内记录按单向链表 + 页目录槽二分查找；跨页之间通过 FIL_PAGE_PREV / NEXT 双向链表串联！)
```

### 镜头二：有前提假设的数量级估算——3 层 B+ 树到底能存多少行数据？

很多面试资料直接背诵结论：“3 层 B+ 树固定能存 2,190 万行数据”。
作为架构师，我们必须记住一条铁律：**数字越精确，越必须清楚它背后的假设前提！**

下面我们列出 InnoDB `16KB` 页在理想假设下的估算过程，以及真实生产环境中的折损边界：

#### 1. 理想简化估算模型（用于理解数量级）
- **前提假设 A（页可用空间）**：InnoDB 每页 `16,384B`，扣除 `File Header (38B)`、`Page Header (56B)`、`Infimum + Supremum 虚拟记录 (26B)`、`File Trailer (8B)` 及页目录槽位（Page Directory Slots）开销后，假设按约 `15KB ~ 16KB` 满载估算；
- **前提假设 B（非叶目录项大小）**：假设主键为 `BIGINT (8B)`，InnoDB 页号指针为 `6B`，加上记录头信息（`Record Header 5B`），每个目录项约占 **`14B ~ 19B`**。
  - 若按简化教材忽略记录头（`8B + 6B = 14B`）粗算：单张目录页可容纳 `16,384 ÷ 14 ≈ 1,170` 个分支；
  - 若计入 `5B` 记录头与页头开销（按每项 `19B`、可用 `15,000B` 算）：单张目录页可容纳 `15,000 ÷ 19 ≈ 789` 个分支；
- **前提假设 C（叶子页单行大小）**：假设每行完整业务记录平均为 **`1KB`**，则单张 `16KB` 叶子页约可装 **`15 ~ 16` 行**（若单行仅 `200B`，则一页可装约 `75` 行）。

| 估算口径 | 第 1 层（根页分支数） | 第 2 层（二级目录总分支数） | 第 3 层（单叶页行数 × 叶子页数） | 3 层树总容量数量级 |
| :--- | :--- | :--- | :--- | :--- |
| **教材理想上限口径**（14B/项，16行/页，100% 填满） | `1,170` | `1,170 × 1,170 ≈ 137 万页` | `137 万 × 16 行` | **约 `2,190 万行`** |
| **计入页头与填充因子口径**（19B/项，1KB/行，顺序填充率 `15/16`） | `~740` | `740 × 740 ≈ 54.7 万页` | `54.7 万 × 15 行` | **约 `820 万行`** |
| **窄表口径**（19B/项，单行仅 `250B`，每叶页约 60 行） | `~740` | `~54.7 万页` | `54.7 万 × 60 行` | **约 `3,280 万行`** |

> **核心结论**：无需死记 `2,190 万` 这个单一数字，架构师真正需要把握的工程事实是——**由于 B+ 树非叶目录页不存行数据，其分支因子高达数百至上千，因此千万级行数的表，其 B+ 树高度通常只有 `3 ~ 4` 层！**

### 镜头三：B+ 树从 0 到 1 的插入与“叶子页分裂（Page Split）”慢放

为了直观展示指针变化，我们将单页容量缩小为教学模型：**假设每张页最多存 2 条记录，塞入第 3 条时触发页分裂**，依次插入 `10:张三 -> 20:李四 -> 30:王五 -> 40:赵六 -> 50:孙七`：

```text
【第 1 帧：插入 10:张三、20:李四（单页未满，页内按主键有序排列）】
  ┌────────── 数据页 P1 ──────────┐
  │  10:张三   │   20:李四        │
  └───────────────────────────────┘

【第 2 帧：插入 30:王五 ──► P1 满 3 条触发分裂！排头兵键 20 复印上推至目录页】
  注意 B+ 树与 2-3 树的关键区别：20:李四 的完整档案必须留在底层叶子页 P2 中，
  只是把 P2 的最小主键值【20】复印一份（不含李四档案）写入上层目录页 D1 作为路标！

                 ┌──── 目录页 D1 (仅存键值与子页号) ────┐
                 │        [10 -> P1]  │  [20 -> P2]     │
                 └───────────┬────────┴────────┬────────┘
                             ▼                 ▼
             ┌─── 数据页 P1 ───┐             ┌────── 数据页 P2 ──────┐
             │ 10:张三         │ ◄═════════► │ 20:李四  │  30:王五   │
             └─────────────────┘  双向链表   └───────────────────────┘

【第 3 帧：插入 40:赵六、50:孙七 ──► P2 再次分裂出 P3，并将 P3 最小键 30 登记到目录页 D1】
                 ┌─────────── 目录页 D1 (非叶节点) ───────────┐
                 │  [10 -> P1]  │  [20 -> P2]  │  [30 -> P3]  │
                 └──────┬───────┴──────┬───────┴──────┬───────┘
                        ▼              ▼              ▼
        ┌─── 数据页 P1 ───┐  ┌─── 数据页 P2 ───┐  ┌───────── 数据页 P3 ─────────┐
        │ 10:张三         │◄►│ 20:李四         │◄►│ 30:王五 │ 40:赵六 │ 50:孙七 │
        └─────────────────┘  └─────────────────┘  └─────────────────────────────┘
```

## 3. 第三层（边界与反例）：逻辑读 vs 物理读、聚簇索引回表与主键选型边界

1. **重要边界一：3 层 B+ 树查一次 = 读 3 次物理硬盘吗？（逻辑 I/O vs 物理 I/O）**
   **绝不等于！** 在真实的 MySQL InnoDB 中，访问一个页首先查的是内存中的 **[Buffer Pool（缓冲池，底层用改进版 LRU 管理）](./09-LRU缓存淘汰算法.md)**（这叫 **逻辑读 Logical Read**）。
   - 根节点（第 1 层）和第 2 层目录页因为被所有查询高频共享，几乎 **100% 常驻内存 Buffer Pool**；
   - 热门的底层叶子页也常驻内存（成熟线上库的 Buffer Pool 命中率通常 `> 99%`）；
   - **只有当最底层的冷数据叶子页不在 Buffer Pool 中时，才会触发 1 次真正的物理磁盘读取（Physical I/O）！**
2. **重要边界二：聚簇索引（Clustered Index）、二级索引回表与覆盖索引**
   - **聚簇索引（主键树）**：叶子页直接存完整行数据（`id, name, age, bio...`）；
   - **二级索引（辅助索引，如 `INDEX idx_name(name)`）**：叶子页只存 **`(name 键值 + 主键 id)`**。当执行 `SELECT * FROM users WHERE name = '李四'` 时，必须先在 `idx_name` 树查到 `id = 20`，再拿 `id = 20` 回到主键树查完整行（**回表**）；
   - **何时二级索引反而比全表扫描更慢？（反例）**：如果某个筛选条件区分度极低（例如 `WHERE status = 1` 命中了全表 80% 的行），走二级索引需要做几十万次随机回表读页，代价远高于直接顺着主键叶子链表做顺序全表扫描——此时 MySQL 优化器会主动放弃二级索引，改走全表扫描！
3. **重要边界三：自增 ID vs UUID / 雪花算法的分场景权衡**
   - **单机或主从 InnoDB 表**：强烈优先使用趋势递增主键（`AUTO_INCREMENT`），因为新记录总是追加在最右侧叶子页末尾，页填充率高达 `15/16`；而完全随机的 `UUID v4` 会随机插入中间历史页，导致高频**页分裂（Page Split）**与约 `50%` 的空间碎片浪费；
   - **分布式分库分表或多写场景（反例）**：单机自增步长在分片场景下协调繁琐且容易暴露业务单量，此时工程上常采用 **Snowflake（雪花算法：高位时间戳 + 机器号 + 序列号）** 或 **UUID v7（高位毫秒时间戳有序 + 低位随机）**——既保证了全局唯一，又保住了 B+ 树所需的**时间趋势递增顺序写特性**！

## 4. 可独立运行代码：模拟 B+ 树“目录页二分寻路 + 底部叶子链表范围游标扫描”

```js
// bplus-tree-scan.mjs —— 直接用 node 运行，验证 B+ 树非叶目录路由与底部双向链表范围扫描
const leaf1 = { pageNo: 'P1', prev: null, next: null, rows: [{ id: 10, name: '张三' }, { id: 15, name: '钱二' }] }
const leaf2 = { pageNo: 'P2', prev: leaf1, next: null, rows: [{ id: 20, name: '李四' }, { id: 25, name: '周八' }] }
const leaf3 = { pageNo: 'P3', prev: leaf2, next: null, rows: [{ id: 30, name: '王五' }, { id: 40, name: '赵六' }, { id: 50, name: '孙七' }] }
leaf1.next = leaf2
leaf2.next = leaf3

// 上层目录页：仅存储每张子数据页的最小主键值（minKey）与页引用
const rootDirectory = [
  { minKey: 10, childPage: leaf1 },
  { minKey: 20, childPage: leaf2 },
  { minKey: 30, childPage: leaf3 }
]

export function rangeScanBPlusTree(minId, maxId) {
  // 1. 在目录页中逆序找到最后一个 minKey <= minId 的子页入口
  let targetEntry = rootDirectory[0]
  for (const entry of rootDirectory) {
    if (entry.minKey <= minId) targetEntry = entry
    else break
  }

  // 2. 下潜到目标叶子页后，无需再回溯上层目录，直接沿着叶子页 next 链表水平扫描
  let curPage = targetEntry.childPage
  const visitedPages = []
  const matchedRows = []

  while (curPage !== null) {
    visitedPages.push(curPage.pageNo)
    for (const row of curPage.rows) {
      if (row.id > maxId) return { visitedPages, matchedRows }
      if (row.id >= minId) matchedRows.push(row)
    }
    curPage = curPage.next
  }
  return { visitedPages, matchedRows }
}

const res = rangeScanBPlusTree(20, 42)
console.log('扫描经过的叶子页:', res.visitedPages) // ['P2', 'P3']
console.log('命中的记录:', res.matchedRows.map(r => `${r.id}:${r.name}`)) // ['20:李四', '25:周八', '30:王五', '40:赵六']
```
