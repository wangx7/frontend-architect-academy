# 概念 08｜B 树与 B+ 树（B-Tree & B+ Tree）

> **一句话人话定义**：因为硬盘每次读写必须整页批发（MySQL 默认 **16KB 一页**），**B+ 树**把 [2-3 树](./07-2-3树与红黑树.md) 的小盒子扩建成了 **“16KB 超大盒子”**，并立下两条铁律：**① 上层目录页只印数字路标（一页塞 1,000 个，3 层管两千万行）；② 所有真实数据全沉在最底层的数据页，并用[双向链表](./03-单向链表与双向链表.md)手拉手串起来！**

## 1. 它被什么痛点逼出来的？

在 [概念 07：红黑树](./07-2-3树与红黑树.md) 里，红黑树在内存里天下无敌。但数据库的数据必须存在断电不丢的**硬盘（SSD/机械盘）**上。
硬盘有两个物理怪癖：
1. **慢**：去硬盘拿一次数据比内存慢 **1,000 到 100,000 倍**；
2. **只做整页批发，不做零售**：哪怕你只想读硬盘上的 1 个数字，硬盘一次也必须把整整 **16KB（一页 Page）** 搬进内存。

如果把 100 万条数据存成 20 层高的红黑树放在硬盘上，查 1 条数据就要让硬盘搬 **20 次 16KB 大页**，每次只看里面 1 个数字，99.9% 的带宽全运了空气！
怎么让硬盘每次搬上来的 16KB 大页都值回票价？**让一个树节点刚好等于一张 16KB 的磁盘页，里面一口气塞上千个路标！**

## 2. 从 0 到 1 生长慢放：亲眼看 B+ 树是怎么裂开并串起底部链表的

为了让你一眼看清，我们规定：**每张页纸最多只准装 2 条记录，装满 3 条就裂成两页**。现在依次插入 `10:张三 -> 20:李四 -> 30:王五 -> 40:赵六 -> 50:孙七`：

### 第 1 步：插入 `10:张三` 和 `20:李四`
第 1 张数据页还没满，直接并排写进去：
```text
数据页 P1：[ 10:张三 | 20:李四 ]
```

### 第 2 步：插入 `30:王五`（满 3 条撑爆！裂成两页 + 复印排头兵 `20` 送上头顶目录页）
注意 B+ 树分裂时和 2-3 树最大的不同：**因为 B+ 树规定“所有真实用户档案都必须留在最底层”，所以中间的 `20:李四` 绝对不能离开底部！**
1. 前一半 `[ 10:张三 ]` 留在 P1，后一半 `[ 20:李四 | 30:王五 ]` 搬进新数据页 P2，并在 P1 和 P2 之间挂上**双向链表箭头 `<==>`**；
2. 把 P2 的排头兵编号 **`20` 复印一份（只复印数字 `20`，不复印“李四”的厚重档案！）**，送到头顶新建的“目录页”当路标：

```text
           目录页（只印数字路标，不印档案）： [ 20 ]
                                             /                                       (< 20 走左)          (≥ 20 走右)
                                           /          底部数据页（双向链表手拉手）：       [ 10:张三 ] <==> [ 20:李四 | 30:王五 ]
```

### 第 3 步：插入 `40:赵六` 和 `50:孙七`（右侧再裂出 P3，把 `30` 复印进头顶目录页）
```text
           目录页（16KB 可塞上千个路标）：  [  20   |   30  ]
                                           /        |                                       (< 20 走左)     (20~29 走中)    (≥ 30 走右)
                                         /          |          底部数据页（存完整档案）：          [ 10:张三 ] <==> [ 20:李四 ] <==> [ 30:王五 | 40:赵六 | 50:孙七 ]
```

看这张亲手推出来的图，所有数据库高频考题一眼看穿：
- **为什么是 B+ 树而不是 B 树？** B 树把厚重的用户档案也塞在上层节点里，导致一张 16KB 页只能塞十几个路标，树变高了，而且做范围查询时必须在树上爬上爬下；**B+ 树给上层目录页彻底“脱水”（只印数字 ID 和页码），一页能塞 1,170 个路标，3 层就能管住 $1170 	imes 1170 	imes 16 pprox 2,190$ 万行数据！** 而且范围查询 `WHERE id BETWEEN 15 AND 45` 时，只需顺着目录找到起点 `20`，然后**沿着底部 `<==>` 双向链表一路平推过去**即可！
- **什么叫“聚簇索引”与“二级索引回表”？**
  - **聚簇索引（主键树）**：就是上面画的这棵树，最底层叶子页里直接装着整行档案。
  - **二级索引（如给 `name` 建索引）**：为了省空间，`name` 树的底部叶子页里**只存 `("李四" -> 主键 id: 20)`**。查 `WHERE name = '李四'` 时，先在 `name` 树查到主键 `20`，再拿 `20` 回主键树取整行——这第二步就叫 **“回表”**！

## 3. 20 行极简代码原型：模拟 B+ 树“目录路标定位 + 底部链表范围扫描”

```js
// 模拟 B+ 树的两大绝活：1. 顺着目录路标定位叶子页  2. 顺着底部链表极速范围扫描
const leaf1 = { items: [{ id: 10, name: '张三' }], next: null }
const leaf2 = { items: [{ id: 20, name: '李四' }], next: null }
const leaf3 = { items: [{ id: 30, name: '王五' }, { id: 40, name: '赵六' }, { id: 50, name: '孙七' }], next: null }
leaf1.next = leaf2; leaf2.next = leaf3 // 底部叶子页链表手拉手

const directory = { keys: [20, 30], children: [leaf1, leaf2, leaf3] } // 上层脱水目录页

function rangeQuery(minId, maxId) {
  // 1. 先看头顶目录页，找到起点所在的叶子页
  let pageIdx = directory.keys.findIndex(k => minId < k)
  let page = directory.children[pageIdx === -1 ? directory.children.length - 1 : pageIdx]
  // 2. 根本不用再回目录页！直接顺着底部 next 链表一路往右滑！
  const result = []
  while (page) {
    for (const row of page.items) {
      if (row.id > maxId) return result
      if (row.id >= minId) result.push(row)
    }
    page = page.next
  }
  return result
}
console.log('范围查询 id 20~45:', rangeQuery(20, 45))
```

## 4. 前后端架构双视角落地

| 维度 | 前端架构中的体现 | 后端与系统架构中的体现 |
| :--- | :--- | :--- |
| **持久化存储引擎** | 浏览器内置数据库 **IndexedDB** 的底层对象仓库（Object Store）与索引，正是基于 B+ 树 / LSM 树实现客户端百万级数据检索与范围游标（`IDBKeyRange.bound`） | **MySQL InnoDB 存储引擎**、PostgreSQL 索引、操作系统文件系统（XFS / Ext4 / NTFS 目录树） |
| **建表与查询铁律** | 前端使用 IndexedDB 或设计大数据表格分页时，优先使用游标分页（`id > lastId`）避免深分页卡顿 | **为什么推荐自增 ID 作主键？** 因为自增 ID 永远往最右边叶子页顺序追加；用随机 UUID 作主键会逼迫中间已满的叶子页频繁裂开搬家（页分裂）！ |
