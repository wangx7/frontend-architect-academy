# 概念 08｜B 树与 B+ 树（B-Tree & B+ Tree）

> **一句话人话定义**：因为硬盘每次读写必须按 **16KB 整页批发**，**B 树**把 [2-3 树](./07-2-3树与红黑树.md) 的小房间直接扩建成了能塞几百个数的 **“16KB 豪华大房间（M 叉树）”**；而统治 MySQL 的 **B+ 树** 在 B 树基础上又做了两刀狠手术——**① 上层目录页彻底“脱水”，只印数字 ID 和页码（不装用户档案），让 1 张 16KB 目录页能塞满 1,170 个路标，仅需 3 层就能管住 2,190 万行数据；② 所有真实数据全沉在最底层的数据页，并用[双向链表](./03-单向链表与双向链表.md)手拉手串起来！**

## 1. 它被什么痛点逼出来的？

在 [概念 07：2-3 树与红黑树](./07-2-3树与红黑树.md) 的结尾，我们留了一个致命问题：
既然红黑树在内存里这么快，为什么 MySQL、PostgreSQL 以及电脑的文件系统，全都不用红黑树存数据，非要发明 **B 树** 和 **B+ 树**？

答案藏在**内存（RAM）与硬盘（SSD / 机械硬盘）的物理鸿沟**里：
1. **硬盘慢得像蜗牛**：CPU 去内存拿一个数只需约 `100 纳秒`，而去硬盘拿一次数据需要 `10 万纳秒 ~ 1,000 万纳秒`（慢了 **1,000 到 10 万倍**）！在硬盘世界里，**“读了几次硬盘（磁盘 I/O 次数）”直接决定了你的数据库是 1 毫秒响应还是卡死超时！**
2. **硬盘只做“16KB 整页批发”，不做零售**：哪怕你只想读硬盘上的 1 个字节，操作系统和 MySQL InnoDB 引擎一次也必须从硬盘搬回整整 **16KB（16,384 字节，称为一页 Page）** 的连续数据！

想一想：如果把 2,000 万行数据存成一棵**红黑树**放在硬盘上，每个节点只存 1 个数，这棵树有 **25 层高**。每次查一条数据，顺着树根往下走 25 层，就要让硬盘做 **25 次随机读取**——每次大费周章搬上来 16KB 的大箱子，却只掏出里面几十字节的 1 个节点，剩下 99.8% 的空间全运了空气！

怎么让硬盘每次搬上来的 16KB 大箱子都塞得满满当当、把 25 层高的瘦竹竿压成只有 **3 层高的矮胖子**？
答案脱口而出：**别让一个房间只住 2 个数（2-3 树）了！直接把一个树节点做成整整 16KB 大，里面一口气并排塞进 1,000 个数，分出 1,001 条岔路！**

## 2. 第一幕对比：B 树 vs B+ 树，为什么 MySQL 最终淘汰了 B 树？

把 2-3 树的房间扩建成 16KB 大房间后，先诞生的是 **B 树（B-Tree）**，后来才进化出 **B+ 树（B+ Tree）**。
很多教程讲不清它俩的区别，你只需看下面这张**“16KB 目录页里到底装了什么”**的物理解剖图，一秒钟就能看懂为什么数据库全都选了 B+ 树：

```text
【方案 A：B 树（B-Tree）—— 不管上层还是下层，每个路标旁边都背着沉重的完整用户档案！】
  ┌─────────────────── 1 张 16KB 的 B 树顶层节点 ───────────────────┐
  │ [ id:10 + 张三的1KB完整档案 ]  │  [ id:20 + 李四的1KB完整档案 ] │ ...
  └─────────────────────────────────────────────────────────────────┘
  ❌ 痛点 1（树不够矮）：因为每条用户档案重达 1KB，16KB 的房间塞 16 个人就满了！
                         要存 2,000 万行数据，树还是有 6~7 层高（要读 6~7 次硬盘）！
  ❌ 痛点 2（范围查询痛苦）：想查 id 在 10~50 之间的人，要在底层和顶层之间像猴子一样爬上爬下！

══════════════════════════════════════════════════════════════════════════════════

【方案 B：B+ 树（B+ Tree）—— 上层目录页彻底“脱水”只印数字路标，所有档案全沉到底部并连成双向链表！】
  ┌─────────────── 1 张 16KB 的 B+ 树上层目录页（纯路标，不含档案！） ───────────────┐
  │ [ 路标id:10 (8字节) + 子页号 (6字节) ] │ [ 路标id:20 + 子页号 ] │ ... (共塞 1,170 个！) │
  └──────────────────────────────────────────────────────────────────────────────────┘
           ╱ (id < 20 去 P1 页)                 ╲ (id >= 20 去 P2 页)
          ▼                                      ▼
  ┌── 底部数据页 P1 (16KB) ──┐          ┌── 底部数据页 P2 (16KB) ──┐
  │ 10 : 张三的 1KB 完整档案 │ ◄══════► │ 20 : 李四的 1KB 完整档案 │ ◄══════► ...
  │ 15 : 王五的 1KB 完整档案 │ 双向链表 │ 28 : 赵六的 1KB 完整档案 │
  └──────────────────────────┘          └──────────────────────────┘
```

一起来算一笔震撼的小学乘法账（为什么面试常说 **“InnoDB 一棵 3 层高的 B+ 树能存两千万行数据”**）：
1. **第 1 层（根目录页，16KB，常驻内存）**：因为不装用户档案，每条路标只需 `主键 bigint (8字节) + 子页号指针 (6字节) = 14 字节`。一张 16KB 的目录页能塞下 `16,384 ÷ 14 ≈ 1,170` 个路标，分出 **1,170 个分支**！
2. **第 2 层（二级目录页，共 1,170 页）**：每一页又能塞 1,170 个路标，总共分出 `1,170 × 1,170 = 1,368,900`（约 **137 万**）个分支！
3. **第 3 层（最底层叶子数据页，共 137 万页）**：每张 16KB 数据页装真实的 1KB 用户档案，每页能装 **16 行**。
4. **总容量**：`1,170 × 1,170 × 16 = 21,902,400`（**整整 2,190 万行数据！**）。
5. **查询耗时**：因为第 1 层根页和第 2 层热目录页早就缓存在内存里了，**从 2,190 万行数据里查任何一条记录，最多只需要去硬盘读 1 次最底层的叶子页！**

## 3. 第二幕逐帧慢放：B+ 树从 0 到 1 的插入与“页分裂（Page Split）”

为了让你看清每一个指针和路标的来龙去脉，我们把 16KB 数据页缩小成迷你版：**规定每张页最多只准装 2 条记录，装满 3 条就触发“页分裂”**。
现在我们依次往空表里插入 **`10:张三 -> 20:李四 -> 30:王五 -> 40:赵六 -> 50:孙七`**：

```text
【第 1 帧：插入 10:张三，再插入 20:李四】
  第 1 张数据页 P1 还没满（最多装 2 条），按主键从小到大并排坐好：
  ┌────────── 数据页 P1 ──────────┐
  │  10:张三   │   20:李四        │
  └───────────────────────────────┘

【第 2 帧：插入 30:王五 ──► P1 塞满 3 条撑爆！触发“叶子页分裂 + 排头兵复印上推”！】
  ⚠️ 请看 B+ 树分裂与 2-3 树最关键的区别：
  在 2-3 树里，中间的 20 搬去楼上后，底下就没有 20 了；
  但在 B+ 树里，【所有真实档案都必须留在最底层】！所以：
  1. 把 P1 劈成两半：P1 留 [10:张三]，新开一页 P2 装后半截 [20:李四 | 30:王五]，并用双向链表 ◄══► 连起来；
  2. 把新页 P2 的排头兵主键【20】复印一份（只复印数字 20，不带“李四”档案！），送到头顶新建的目录页当分界路标！

                 ┌──── 目录页 D1 (只印数字路标) ────┐
                 │           路标 : 20              │
                 └──────┬────────────────────┬──────┘
         (id < 20 走左) │                    │ (id >= 20 走右)
                        ▼                    ▼
        ┌─── 数据页 P1 ───┐                ┌────── 数据页 P2 ──────┐
        │ 10:张三         │ ◄════════════► │ 20:李四  │  30:王五   │
        └─────────────────┘    双向链表    └───────────────────────┘

【第 3 帧：插入 40:赵六，再插入 50:孙七 ──► 右侧 P2 又塞满 3 条撑爆，裂出 P3 并把排头兵 30 复印进目录页！】

                 ┌─────── 目录页 D1 (只印数字路标) ───────┐
                 │       路标 : 20       │    路标 : 30   │
                 └───┬───────────────────┼────────────────┴───┐
      (id < 20 走左) │    (20 <= id < 30)│                    │ (id >= 30 走右)
                     ▼                   ▼                    ▼
     ┌─── 数据页 P1 ───┐     ┌─── 数据页 P2 ───┐     ┌───────── 数据页 P3 ─────────┐
     │ 10:张三         │◄═══►│ 20:李四         │◄═══►│ 30:王五 │ 40:赵六 │ 50:孙七 │
     └─────────────────┘     └─────────────────┘     └─────────────────────────────┘
```

### 看着第 3 帧的图，体验一下 B+ 树做“范围查询”有多爽：
假设你写了一句 SQL：`SELECT * FROM users WHERE id BETWEEN 20 AND 45`。
1. **第一步（顺着目录页找起点 `20`）**：看顶层目录页 D1，`20 >= 20 且 20 < 30`，走中间箭头直达 **数据页 P2**，拿到 `20:李四`；
2. **第二步（根本不用再回目录页！顺着底部双向链表 `◄═══►` 往右滑）**：从 P2 的 `next` 指针直接滑到隔壁 **数据页 P3**，依次拿出 `30:王五`、`40:赵六`，看到 `50 > 45` 立刻停手收工！

## 4. 第三幕拆解：一图看懂“聚簇索引”、“二级索引回表”与“覆盖索引”

在 MySQL InnoDB 里，每张表其实不止一棵 B+ 树：
- **主键树（聚簇索引 Clustered Index）**：就是上面画的那棵树——按主键 `id` 排序，**最底层叶子页里装的是整行完整档案（`id, name, age, phone...`）**。
- **普通字段索引树（二级索引 Secondary Index）**：假设你给 `name` 字段也建了个索引（`CREATE INDEX idx_name ON users(name)`）。数据库会单独再建一棵按姓名拼音排序的 B+ 树。
  但想一想：如果 `name` 树的底部叶子页里也把整行档案完整抄一遍，建 5 个索引岂不是要把整张表复印 5 份？太费硬盘了！
  所以 **二级索引的底部叶子页里，绝对不存整行档案，只存 `(name字段值 + 对应的主键 id)`**！

请看当你执行 `SELECT * FROM users WHERE name = '李四'` 时，数据是怎么在两棵 B+ 树之间跳接的（这就叫 **“回表”**）：

```text
【第 1 步：先查 name 二级索引树】               【第 2 步：拿着 id=20 回主键树取整行档案（回表！）】
          [ 目录: "李四" ]                                  [ 目录: 20 | 30 ]
                 │                                                  │
                 ▼                                                  ▼
  叶子页：[ name:"李四" ──► 主键 id: 20 ]  ════(拿着 id:20)════► 叶子页 P2：[ id:20, name:"李四", age:28, phone:"138..." ]
```

- **什么叫“回表”？** 先在 `name` 二级索引树里查到主键 `id = 20`，再拿着 `20` 回到主键 B+ 树里查一次才能拿到 `age` 和 `phone`，跑了两棵树，就叫**回表**。
- **什么叫“覆盖索引（免回表优化）”？** 如果你的 SQL 写的是 `SELECT id, name FROM users WHERE name = '李四'`（只查 `id` 和 `name`），当走到左边那棵 `name` 树的叶子页 `[ name:"李四", id:20 ]` 时，你要的数据已经全齐了！根本不需要再跑去右边的主键树——这就叫**索引覆盖（Covering Index）**，速度直接翻倍！

## 5. 代码逐行带入走读：模拟 B+ 树“目录二分定位 + 底部链表范围横扫”

```js
// 构建第 3 帧里的 3 张底部叶子数据页，并用 next 指针连成链表
const page1 = { pageNo: 'P1', rows: [{ id: 10, name: '张三' }], next: null }
const page2 = { pageNo: 'P2', rows: [{ id: 20, name: '李四' }], next: null }
const page3 = { pageNo: 'P3', rows: [{ id: 30, name: '王五' }, { id: 40, name: '赵六' }, { id: 50, name: '孙七' }], next: null }
page1.next = page2
page2.next = page3

// 构建顶层脱水目录页（只存分界路标 keys 与对应的子数据页指针 children）
const dirPage = {
  keys: [20, 30],                 // 2 个路标分出 3 条路：<20 走 P1，20~29 走 P2，>=30 走 P3
  children: [page1, page2, page3]
}

function bPlusRangeQuery(minId, maxId) {
  // 第一步：在顶层目录页里比对路标，定位起点 minId 落在哪张数据页
  let branchIdx = dirPage.keys.findIndex(roadSign => minId < roadSign)
  if (branchIdx === -1) branchIdx = dirPage.children.length - 1
  let curPage = dirPage.children[branchIdx]

  // 第二步：落地到底部数据页后，彻底甩开目录页，顺着底部 next 链表一路往右滑！
  const result = []
  while (curPage !== null) {
    console.log(`正在扫描底部数据页 [${curPage.pageNo}]...`)
    for (const row of curPage.rows) {
      if (row.id > maxId) return result // 一旦超过终点 maxId，立刻刹车返回！
      if (row.id >= minId) result.push(row)
    }
    curPage = curPage.next // 顺着叶子链表滑向下一页
  }
  return result
}

console.log('查询结果:', bPlusRangeQuery(20, 45))
// 输出：依次扫描 [P2]、[P3]，精准拿出 李四(20)、王五(30)、赵六(40)，遇到孙七(50)立即停止！
```

## 6. 前后端架构双视角落地与建表铁律

| 场景维度 | 前端架构中的核心体现 | 后端与系统架构中的核心体现 |
| :--- | :--- | :--- |
| **存储与分页优化** | 1. **浏览器 IndexedDB 存储引擎**：前端在本地存储几万条聊天记录或离线商品库时，IndexedDB 的 Object Store 与 Index 底层正是利用 B+ 树 / LSM 树支持 `IDBKeyRange.bound(min, max)` 毫秒级范围游标查询；<br>2. **彻底消灭“深分页卡顿”**：当列表翻到第 10,000 页时，如果前端传 `page=10000&size=20`（`LIMIT 200000, 20`），数据库得顺着底部链表白白数过前 20 万行再扔掉；架构师会改为**游标分页**——前端传上一页最后一条的 `lastId=200000`（`WHERE id > 200000 LIMIT 20`），数据库直接用 B+ 树目录 1 步跳到 `200000` 往后拿 20 条，耗时从 800ms 降到 1ms！ | 1. **为什么大厂军规严禁用随机字符串（如 `UUID`）做 InnoDB 主键，强制要求用自增整数（`AUTO_INCREMENT` 或雪花算法趋势递增 ID）？**<br>看上面第 3 帧图就懂了：如果主键是递增的（`10, 20, 30, 40, 50`），每次新数据永远规规矩矩往最右边的最新页 `P3` 末尾追加，写满了就开新页 `P4`，前面的老页永远不用动；<br>但如果你用毫无规律的 `UUID` 做主键，每次新来的 ID 一会儿插在 `P1` 中间、一会儿插在 `P2` 中间，把原本已经装满的老数据页硬生生撑爆裂开（**高频页分裂 Page Split + 随机磁盘 I/O**），写入性能直接暴跌数倍！ |
