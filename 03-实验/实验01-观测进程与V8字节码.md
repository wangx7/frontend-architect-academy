# 实验 01｜观测操作系统进程与 V8 字节码

> 📖 **关联教程**：[第 01 讲：程序是怎么跑起来的](../01-教程/第01讲-程序是怎么跑起来的.md)  
> 🔍 **关联概念**：[概念 01：内存门牌号与指针引用](../02-概念/01-内存门牌号与指针引用.md)

## 1. 实验目标

打破“代码跑起来是个抽象比喻”的错觉，亲眼在终端里看到两件物理事实：
1. 程序运行 = 操作系统进程表里多了一个有真实 PID（进程号）和内存占用的实体；
2. V8 引擎确实把你的 JS 文本翻译成了中间字节码（Bytecode）与机器指令。

## 2. 复制即跑代码

### 步骤 A：亲眼看到 V8 把 `a + b` 翻译成字节码
直接在终端运行下面这行 Node.js 自带命令（无需新建文件）：

```bash
node --print-bytecode --print-bytecode-filter=addNumbers -e "function addNumbers(a, b) { return a + b; } addNumbers(10, 20);"
```

### 步骤 B：观测运行中的进程 PID 与内存占用
运行下面这行命令：

```bash
node -e "console.log('当前进程 PID:', process.pid, '内存占用(MB):', (process.memoryUsage().rss/1024/1024).toFixed(1))"
```

## 3. 实测输出与机制拆解

在步骤 A 中，你会看到终端吐出类似下面的 V8 字节码指令：
```text
[generated bytecode for function: addNumbers]
Bytecode Age: 0
   0 E> 0x... @    0 : 0b 03             Ldar a1          <-- 把第 2 个参数 b 装进累加寄存器
   2 S> 0x... @    2 : 39 02 00          Add a0, [0]      <-- 与第 1 个参数 a 相加
   5 S> 0x... @    5 : a9                Return           <-- 返回累加寄存器里的结果
```
这就是铁证：CPU 根本没看你的 `return a + b` 字符串，它执行的是 `Ldar -> Add -> Return` 这几条搬运格子的指令！

## 4. 破坏性实验：触发 JIT 机器码编译（`--trace-opt`）

如果把 `addNumbers(10, 20)` 放在循环里连跑 20,000 次，会发生什么？运行下面这行命令：

```bash
node --trace-opt -e "function hotAdd(a, b) { return a + b; } for (let i = 0; i < 20000; i++) hotAdd(i, 1);"
```
你会看到输出 `[marking ... hotAdd for optimization]` 和 `[completed optimizing ...]`——因为 V8 发现这段代码太热了，当场把它从“解释字节码”升级编译成了 CPU 原生机器码（JIT）！

## 5. 思考题

1. **如果在上面的 `hotAdd` 循环跑了 20,000 次整数加法后，突然传进一次字符串 `hotAdd('hello', 'world')`，V8 刚才编译好的整数加法机器码还能直接用吗？会发生什么？**

<details>
<summary>💡 点击展开本实验思考题参考答案</summary>

不能直接用！因为整数加法的机器指令和字符串拼接的内存分配指令完全不同。当 V8 发现传入的参数类型突然从一直稳定的 `Number` 变成了 `String` 时，会被迫废除刚才编译好的高速机器码，退回到慢速的字节码解释执行——这就叫 **逆优化（Deoptimization / Deopt）**。这也是为什么 TypeScript 和保持函数参数类型稳定有助于引擎保持最佳性能的原因。

</details>
