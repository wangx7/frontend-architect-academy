# 实验 03｜制造并治愈浏览器布局抖动 (Layout Thrashing)

> 📖 **关联教程**：[第 04 讲：字节是怎么变成屏幕像素的](../01-教程/第04讲-字节是怎么变成屏幕像素的.md)  
> 🔍 **关联概念**：[概念 13：GPU 合成层与 BFC 布局边界](../02-概念/13-合成层与BFC布局边界.md)

## 1. 实验目标

在浏览器控制台里亲手验证：为什么同样是修改 500 个 DOM 元素的宽度，**“边读边写”比“先读完再写”慢上十倍甚至几十倍**。

## 2. 复制即跑代码（浏览器 DevTools Console）

打开任意网页，按 F12 打开 Console 面板，粘贴以下代码回车：

```js
// 在浏览器控制台直接运行：实测强制同步布局（Layout Thrashing）的代价
const box = document.createElement('div')
for (let i = 0; i < 600; i++) {
  const row = document.createElement('div')
  row.style.cssText = 'height:3px; width:100px; margin:1px; background:#42b883;'
  box.appendChild(row)
}
document.body.appendChild(box)
const rows = [...box.children]

// ❌ 写法 A（读写交替）：逼迫浏览器在循环里同步重排 600 次！
const t0 = performance.now()
for (let i = 0; i < rows.length; i++) {
  const w = rows[i].offsetWidth        // 读几何属性：逼浏览器当场结算上一轮写入的样式！
  rows[i].style.width = (w + 1) + 'px' // 写几何属性：把布局再次标脏！
}
const thrashMs = (performance.now() - t0).toFixed(2)

// ✅ 写法 B（读写分离）：先集中读完，再集中写，浏览器合并为 1 次重排！
const t1 = performance.now()
const cachedWidths = rows.map(el => el.offsetWidth)
for (let i = 0; i < rows.length; i++) {
  rows[i].style.width = (cachedWidths[i] + 1) + 'px'
}
const batchMs = (performance.now() - t1).toFixed(2)

box.remove()
console.table({ '❌ 边读边写 (强制重排600次)': `${thrashMs} ms`, '✅ 先读后写 (批量重排1次)': `${batchMs} ms` })
```

## 3. 破坏性实验：在 Performance 面板抓出“紫块红三角”

打开 DevTools 的 **Performance** 面板 → 点击左上角录制圆点 → 在控制台跑一遍上面的代码 → 停止录制。
放大火焰图里的 Main 主线程，你会看到写法 A 对应着密密麻麻 **600 个紫色的 `Layout` 小方块**，每个方块右上角都有一个**红色小三角警告（Forced reflow is a likely performance bottleneck）**！

如果每次修改响应式变量都同步立即更新真实 DOM，业务代码在一个函数里修改 10 个状态、中间再穿插读取几次 DOM 尺寸，就会像本实验的写法 A 一样频繁触发组件重算与浏览器强制同步布局。Vue 将所有 DOM patch 集中在同步代码执行完后的微任务阶段一次性批量提交，相当于在框架层强制帮开发者做到了“先算完所有状态，最后批量写一次 DOM”。
