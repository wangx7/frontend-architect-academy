# 实验 13｜百万数据查找复杂度压测与并发超卖复现

> 📖 **关联教程**：[第 16 讲：数据落盘与分布式：B+ 树、事务、Redis 与 Raft](../01-教程/第16讲-数据落盘与分布式B+树索引事务Redis与Raft.md)  
> 🔍 **关联概念**：[概念 08：B 树与 B+ 树](../02-概念/08-B树与B+树.md) ｜ [概念 18：ACID 事务、MVCC 与 WAL 预写日志](../02-概念/18-ACID事务MVCC与WAL预写日志.md)

## 1. 实验目标与验证边界声明（重要！）

### 1.1 本实验真正验证的机理
1. **算法时间复杂度的数量级鸿沟**：在 100 万条记录规模下，实测对比 **线性全表扫描 `O(n)`**、**有序二分查找 `O(log n)`** 与 **哈希精确查找 `O(1)`** 的耗时差距；
2. **异步 I/O 交错下的“先读后写（Read-Modify-Write / TOCTOU）”竞态超卖**：复现两个并发请求在同一时间窗口内读到相同的旧库存 `stock = 1`，导致扣减互相覆盖（丢失更新 Lost Update），并验证如何通过**原子条件校验与扣减合一**根治超卖。

### 1.2 教学模型与真实数据库引擎（MySQL InnoDB）的差异边界
- **内存寻址 vs 磁盘 B+ 树页加载**：本脚本中的数组二分查找与 `Map` 运行在 V8 堆内存中，仅测试 CPU 比较次数与内存指针寻址开销，**并未直接测量真实数据库的 16KB 磁盘页 I/O、Buffer Pool 页置换或 B+ 树页分裂**；
- **单线程异步交错 vs 多线程行锁（X 锁）**：Node.js 单线程中之所以没有发生两个 CPU 核心同时修改同一内存字节的物理撕裂，是因为同步代码块天然不可中断；但一旦中间跨越了 `await`（如先发 `SELECT` 再发 `UPDATE`），事件循环就会交错执行其他请求。而在真实 MySQL 中，单条 `UPDATE goods SET stock = stock - 1 WHERE id = 1 AND stock > 0` 依靠存储引擎内部的 **排他行锁（X Lock）+ 当前读（Current Read）** 保证原子性。

## 2. 复制即跑代码

新建 `lab13-db-index-tx.mjs`，运行 `node lab13-db-index-tx.mjs`：

```js
// lab13-db-index-tx.mjs —— 100 万条数据查找复杂度压测 + 异步交错并发超卖复现与治愈
import { performance } from 'node:perf_hooks'
import assert from 'node:assert/strict'

// 【实验 1】构造 100 万条有序记录，对比线性扫描 O(n) vs 二分查找 O(log n) vs 哈希查找 O(1)
const N = 1_000_000
const table = Array.from({ length: N }, (_, i) => ({ id: i, user: `u_${i}`, amount: (i % 100) * 10 }))
const hashIndex = new Map(table.map(row => [row.id, row]))
const targetId = N - 1 // 查找最末尾一条

// 1. 线性全表扫描 O(n)：模拟无索引时逐行比对 100 万次
const t0 = performance.now()
const r0 = table.find(r => r.id === targetId)
const scanMs = (performance.now() - t0).toFixed(3)

// 2. 有序二分定位 O(log n)：模拟 B+ 树/平衡树约 20 次比较定位（支持等值与范围起点定位）
const t1 = performance.now()
let lo = 0, hi = N - 1, r1 = null, steps = 0
while (lo <= hi) {
  steps++
  const mid = (lo + hi) >> 1
  if (table[mid].id === targetId) { r1 = table[mid]; break }
  table[mid].id < targetId ? (lo = mid + 1) : (hi = mid - 1)
}
const binaryMs = (performance.now() - t1).toFixed(3)

// 3. 哈希表查找 O(1)：模拟内存哈希索引单点直达（不支持范围查询）
const t2 = performance.now()
const r2 = hashIndex.get(targetId)
const hashMs = (performance.now() - t2).toFixed(3)

assert.equal(r0.id, targetId)
assert.equal(r1.id, targetId)
assert.equal(r2.id, targetId)

console.table({
  '❌ 无索引线性扫描 O(n)': { '比较次数': N, '耗时(ms)': scanMs, '范围查询': '全表遍历慢' },
  '🌲 有序二分定位 O(log n)': { '比较次数': steps, '耗时(ms)': binaryMs, '范围查询': '✅ 支持极速范围扫描' },
  '⚡ 哈希索引查找 O(1)': { '比较次数': 1, '耗时(ms)': hashMs, '范围查询': '❌ 不支持范围查询' }
})

// 【实验 2】复现“先 SELECT 再 UPDATE”的异步交错超卖 vs “原子条件扣减”防超卖
let unsafeStock = 1
let safeStock = 1

// ❌ 错误模式：把“读取判断”与“写入扣减”拆在两次异步 I/O 之间（TOCTOU 竞态漏洞）
async function buyUnsafe(buyer) {
  const currentStock = unsafeStock                  // 第 1 步：SELECT stock (A 和 B 同时读到 1！)
  await new Promise(r => setTimeout(r, 15))         // 模拟网络/数据库往返间隙
  if (currentStock > 0) {
    unsafeStock = currentStock - 1                  // 第 2 步：UPDATE stock = 0 (两人先后写回，卖出了 2 单！)
    return `${buyer}:抢购成功`
  }
  return `${buyer}:已售罄`
}

// ✅ 正确模式：将“条件校验 (stock > 0)”与“扣减动作 (stock -= 1)”收敛在同一个不可分割的原子临界区内
async function buySafe(buyer) {
  await new Promise(r => setTimeout(r, 15))
  // 对应 SQL: UPDATE goods SET stock = stock - 1 WHERE id = 1 AND stock > 0 (受影响行数 > 0 才算成功)
  if (safeStock > 0) {
    safeStock -= 1
    return `${buyer}:抢购成功`
  }
  return `${buyer}:已售罄`
}

const unsafeResults = await Promise.all([buyUnsafe('买家A'), buyUnsafe('买家B')])
const safeResults = await Promise.all([buySafe('买家A'), buySafe('买家B')])

console.log('❌ 拆分读写的并发结果 (发生超卖!):', unsafeResults)
console.log('✅ 原子条件扣减结果 (严格防超卖):', safeResults)
assert.equal(unsafeResults.filter(x => x.includes('成功')).length, 2) // 复现超卖：1 件库存卖出 2 单
assert.equal(safeResults.filter(x => x.includes('成功')).length, 1)   // 治愈验证：仅 1 人成功
```

## 3. 破坏性实验与真实 SQLite 命令行实测

除了运行上面的 Node.js 复杂度脚本，你的 Mac 自带了真实的 **SQLite 数据库引擎（底层正是 B-Tree / B+ Tree 页存储）**！
在终端直接运行下面这行零依赖单行命令，亲眼看看真实数据库优化器生成的 `EXPLAIN QUERY PLAN`（区分 `SCAN` 全表扫描、`SEARCH USING INDEX` 索引定位与 `COVERING INDEX` 覆盖索引免回表）：

```bash
sqlite3 :memory: "
CREATE TABLE users (id INTEGER PRIMARY KEY, city TEXT, age INT, bio TEXT);
CREATE INDEX idx_city_age ON users(city, age);
EXPLAIN QUERY PLAN SELECT * FROM users WHERE age = 25;
EXPLAIN QUERY PLAN SELECT * FROM users WHERE city = 'Beijing' AND age = 25;
EXPLAIN QUERY PLAN SELECT city, age FROM users WHERE city = 'Beijing' AND age = 25;
"
```

**真实终端输出对照**：
1. 第一条（缺最左列 `city`）：输出 `SCAN users` ──► 无法使用 `idx_city_age` 二分定位，退化为全表扫描！
2. 第二条（命中联合索引但查 `*`）：输出 `SEARCH users USING INDEX idx_city_age (city=? AND age=?)` ──► 二分定位索引，但需**回表**读取 `bio` 列！
3. 第三条（只查索引自带的 `city, age`）：输出 `SEARCH users USING COVERING INDEX idx_city_age (city=? AND age=?)` ──► **命中覆盖索引（Covering Index），零回表**！

## 4. 思考题

1. **为什么在 SQL 里先执行 `SELECT stock FROM goods WHERE id=1`，在业务代码里判断 `if (stock > 0)` 后再发 `UPDATE goods SET stock = stock - 1 WHERE id=1` 会导致超卖，而直接发单条 `UPDATE goods SET stock = stock - 1 WHERE id = 1 AND stock > 0` 就不会超卖？**

<details>
<summary>💡 点击展开本实验思考题参考答案</summary>

因为前一种写法中，普通的 `SELECT` 默认走的是 **MVCC 快照读（不加锁）**，两个并发事务在同一毫秒读到的都是 `stock = 1`，随后两条无条件 `UPDATE` 依次执行，把库存减成了 `-1`（卖出 2 单）。而后一种单条 `UPDATE ... WHERE id = 1 AND stock > 0` 在 InnoDB 中属于**当前读（Current Read）**，存储引擎会先对 `id = 1` 的行记录加上**排他行锁（X 锁）**，并在持有锁的原子状态下检查最新的 `stock > 0` 是否成立；第一个事务扣减提交后，第二个事务获得行锁时发现 `stock` 已经是 `0`（不满足 `WHERE stock > 0`，返回 `Affected rows: 0`），从而在存储引擎层根除了超卖。

</details>
