# 实验 13｜百万数据查找压测与并发超卖复现

> 📖 **关联教程**：[第 16 讲：数据落盘与分布式：B+ 树、事务、Redis 与 Raft](../01-教程/第16讲-数据落盘与分布式B+树索引事务Redis与Raft.md)  
> 🔍 **关联概念**：[概念 08：B 树与 B+ 树](../02-概念/08-B树与B+树.md) ｜ [概念 18：ACID 事务、MVCC 与 WAL 预写日志](../02-概念/18-ACID事务MVCC与WAL预写日志.md)

## 1. 实验目标

1. 在 100 万条数据规模下，实测对比 **第 0 级全表扫描 $O(n)$**、**第 1 级二分查找 $O(\log n)$** 与 **哈希索引 $O(1)$** 的数量级差距；
2. 亲手复现高并发抢购下的 **“丢失更新（超卖）”**，并验证如何用原子条件判断锁死库存边界！

## 2. 复制即跑代码

新建 `lab13-db-index-tx.mjs`，运行 `node lab13-db-index-tx.mjs`：

```js
// lab13-db-index-tx.mjs —— 100 万条数据查找压测 + 并发抢购超卖与治愈对比
import { performance } from 'node:perf_hooks'

// 【实验 1】构造 100 万条订单数据，对比全表扫描 vs 二分索引 vs 哈希索引
const N = 1_000_000
const table = Array.from({ length: N }, (_, i) => ({ id: i, user: `u_${i}` }))
const hashIndex = new Map(table.map(row => [row.id, row]))
const targetId = N - 1 // 查最后一条

const t0 = performance.now()
table.find(r => r.id === targetId)
const scanMs = (performance.now() - t0).toFixed(3)

const t1 = performance.now()
let lo = 0, hi = N - 1
while (lo <= hi) {
  const mid = (lo + hi) >> 1
  if (table[mid].id === targetId) break
  table[mid].id < targetId ? (lo = mid + 1) : (hi = mid - 1)
}
const treeMs = (performance.now() - t1).toFixed(3)

const t2 = performance.now()
hashIndex.get(targetId)
const hashMs = (performance.now() - t2).toFixed(3)
console.table({ '❌ 全表扫描 O(n)': `${scanMs} ms`, '🌲 树/二分查找 O(log n)': `${treeMs} ms`, '⚡ 哈希索引 O(1)': `${hashMs} ms` })

// 【实验 2】对比“无保护读改写（超卖）” vs “原子条件扣减（防超卖）”
let unsafeStock = 1, safeStock = 1
async function buyUnsafe(user) {
  const cur = unsafeStock
  await new Promise(r => setTimeout(r, 10)) // 模拟 I/O 间隙
  if (cur > 0) { unsafeStock = cur - 1; return `${user}成功` }
  return `${user}失败`
}
async function buySafe(user) {
  await new Promise(r => setTimeout(r, 10))
  // 模拟数据库 UPDATE goods SET stock = stock - 1 WHERE id = 1 AND stock > 0 原子判断与扣减合二为一！
  if (safeStock > 0) { safeStock -= 1; return `${user}成功` }
  return `${user}失败`
}

console.log('❌ 无隔离保护抢最后 1 件:', await Promise.all([buyUnsafe('A'), buyUnsafe('B')]))
console.log('✅ 原子条件扣减抢最后 1 件:', await Promise.all([buySafe('A'), buySafe('B')]))
```

## 3. 破坏性实验：把内存差距换算到硬盘尺度

在实验 1 中，内存里的全表扫描需要几毫秒，而索引查找不到 `0.005` 毫秒（相差约 1,000 倍）。
如果把这 100 万条数据放到比内存慢 1,000～10,000 倍的磁盘上：索引查找依然只需读 3 个磁盘页（不到 **1 毫秒**），而全表扫描则会直接飙升到 **几秒甚至几十秒**，瞬间把数据库连接池全部堵死！

## 4. 思考题

1. **为什么在 SQL 里写 `SELECT stock FROM goods WHERE id=1` 然后在业务代码里算完再发 `UPDATE goods SET stock=0 WHERE id=1` 会超卖，而直接写一句 `UPDATE goods SET stock = stock - 1 WHERE id = 1 AND stock > 0` 就绝对不会超卖？**

<details>
<summary>💡 点击展开本实验思考题参考答案</summary>

因为前一种写法把“读取旧值”和“写入新值”拆成了两条没有加排他锁的独立语句，两个并发事务在第一步读到的都是 `stock = 1`。而后一种单条 `UPDATE ... WHERE stock > 0` 语句在 InnoDB 执行时，数据库会先对该行加上**排他行锁（X 锁）**，并在持有锁的原子状态下重新检查当前最新的 `stock > 0` 是否成立；第一个事务扣成 0 后，第二个事务拿到锁时发现 `stock > 0` 已不成立（受影响行数为 0），从而在存储引擎层彻底杜绝了超卖。

</details>
