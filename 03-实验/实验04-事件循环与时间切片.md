# 实验 04｜事件循环宏微任务与时间切片调度器

> 📖 **关联教程**：[第 05 讲：JS 单线程与事件循环调度](../01-教程/第05讲-JS单线程与事件循环调度.md) ｜ [第 08 讲：React Fiber 架构](../01-教程/第08讲-React-Fiber架构与双框架设计权衡.md)  
> 🔍 **关联概念**：[概念 04：栈与队列](../02-概念/04-栈与队列.md)

## 1. 实验目标

1. 亲手验证“1 个宏任务 → 清空全部微任务（含新追加微任务）→ 下一轮宏任务”的精确调度顺序；
2. 亲手实现一个 **时间切片调度器（Time Slicing）**，把一个会阻塞主线程 300ms 的大任务切成每片 10ms 的小任务，验证期间定时器/交互回调能顺利插队响应！

## 2. 复制即跑代码

新建 `lab04-time-slicing.mjs`，运行 `node lab04-time-slicing.mjs`：

```js
// lab04-time-slicing.mjs —— 对比“一口气死算 200ms”与“每 20ms 时间切片让出主线程”
import { performance } from 'node:perf_hooks'

function busyWork2ms() {
  const end = performance.now() + 2
  while (performance.now() < end) {} // 模拟单个节点耗时 2ms 的计算
}

async function runExperiment() {
  console.log('--- 实验开始：启动一个每 30ms 触发一次的模拟用户点击心跳 ---')
  let clicks = 0
  const timer = setInterval(() => {
    clicks++
    console.log(`  ⚡ [用户点击事件 #${clicks}] 得到了主线程即时响应！`)
  }, 30)

  // 使用时间切片处理 60 个任务（总计算量约 120ms，但每算 15ms 就主动让出一次主线程！）
  let i = 0
  while (i < 60) {
    const sliceDeadline = performance.now() + 15
    while (i < 60 && performance.now() < sliceDeadline) {
      busyWork2ms()
      i++
    }
    // 满 15ms 了，通过宏任务 setTimeout 让出主线程，让上面的用户点击回调有机会插队执行！
    await new Promise(r => setTimeout(r, 0))
  }

  clearInterval(timer)
  console.log(`--- 60 个重计算任务全部完成，期间用户点击成功响应了 ${clicks} 次！ ---`)
}

runExperiment()
```

## 3. 破坏性实验：如果把 `setTimeout` 换成 `Promise.resolve()` 会怎样？

把上面代码里的 `await new Promise(r => setTimeout(r, 0))` 改成：
```js
await Promise.resolve() // ❌ 错误地使用微任务让出！
```
重新运行！你会震惊地发现：**期间用户点击响应次数变成了 `0` 次！**
因为 `Promise.resolve()` 产生的是微任务，微任务在当前轮次原地清空，根本不给外面的宏任务（`setInterval` 或用户点击、页面渲染）任何插队的机会！

## 4. 思考题

1. **为什么 React 的 Concurrent Mode（并发时间切片）内部不用 `setTimeout(fn, 0)`，而是优先使用 `MessageChannel` 来调度下一个时间片？**

<details>
<summary>💡 点击展开本实验思考题参考答案</summary>

因为 HTML 标准规定：当浏览器中的 `setTimeout` 嵌套层级达到 5 层以上时，浏览器会强制加上至少 **4ms** 的最小延迟（Clamping）！对于每帧只有 16.7ms 预算的 UI 渲染来说，白白浪费 4ms 太奢侈了；而 `MessageChannel` 的 `port1.postMessage` 同样产生宏任务（能正常让出渲染与响应用户输入），却没有 4ms 的嵌套惩罚，可以做到 0ms 紧接着开启下一片任务。
