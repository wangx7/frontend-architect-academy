# 第 06 讲｜作用域、闭包与原型链的物理真相

> **本讲在主线的位置**：第二卷第 3 讲。把 JS 语言里最容易让人背口诀的三个难点（**词法作用域与闭包、原型链继承、`this` 绑定**），全部还原成内存格子里的**门牌号寻址游戏**。

## 1. 场景与核心问题

为什么在 JavaScript 里：
1. 函数 A 里定义了小函数 B，A 都执行完销毁了，B 为什么还能读写 A 里的变量（**闭包**）？
2. 我明明只写了一个空对象 `const obj = {}`，从来没写过 `toString` 方法，为什么调用 `obj.toString()` 却不会报错（**原型链**）？
3. 同一个函数 `fn()`，直接调和放在 `obj.fn()` 里调，里面的 `this` 为什么指向完全不同的人？

其实，**作用域链**和**原型链**在物理上是同一种东西——都是在内存格子里放一张👉 **[“上级房间的门牌号纸条”](../02-概念/01-内存门牌号与指针引用.md)**，自己房间找不到的东西，顺着纸条去上级房间找！（只不过一个是**找变量**，一个是**找对象属性**）。

## 2. 从零推导：两条“顺着纸条找上级”的链条

### 2.1 第一条链：词法作用域链与“闭包堆背包”
当你查找一个**变量**（比如 `count`）时，引擎顺着函数栈帧里的 `outer`（外部词法环境指针）往上找。
**铁律：函数的外层上级是谁，只看这个函数写（定义）在哪个位置，跟它在哪被调用毫无关系！**

而当内层函数被返回到外面时，为了不让它用到的外层变量随栈帧一起被销毁，V8 引擎会在堆内存里专门开辟一个 👉 **[概念 11：闭包背包 Context（如 `#700`）](../02-概念/11-闭包背包Context与垃圾回收GC.md)**，把被捕获的变量装进这个堆背包里，让内层函数随身揣着 `#700` 的门牌号纸条！

```js
function createLogger(prefix) {
  let seq = 0 // prefix 和 seq 被内层函数用到了 -> 打包放进堆内存 #700 闭包背包！
  return function log(msg) {
    seq++
    console.log(`[${prefix} #${seq}] ${msg}`)
  }
}
const orderLog = createLogger('订单模块') // 揣着 #700 背包纸条
orderLog('创建成功') // [订单模块 #1] 创建成功
orderLog('支付完成') // [订单模块 #2] 支付完成
```

### 2.2 第二条链：原型链（Prototype Chain）—— 对象之间的“共享工具间”
假设你要创建 10,000 个用户实例 `u1, u2 ... u10000`，每个用户都有自己的 `name`，也都需要一个 `sayHi()` 方法。
如果在每个用户的堆房间里都单独塞一份 `sayHi` 函数，10,000 个房间就要重复存 10,000 份一模一样的函数代码，太浪费内存了！

怎么办？**建一个公共工具间（原型对象 `User.prototype`，假设门牌号是 `#300`），把 `sayHi` 放在 `#300` 里；然后在那 10,000 个用户房间里，每人只放一张写着 `#300` 的隐藏纸条（`__proto__` / `[[Prototype]]`）！**

```text
【用户实例 u1 (#501)】                【用户实例 u2 (#502)】
  name: "张三"                          name: "李四"
  [[Prototype]] 纸条: #300 ─────┬─────── [[Prototype]] 纸条: #300
                                │
                                ▼ (自己房间找不到 sayHi，顺着纸条去 #300 找！)
                  【公共工具间 User.prototype (#300)】
                    sayHi: function() { ... }
                    [[Prototype]] 纸条: #100 (指向最顶层 Object.prototype，里面有 toString / hasOwnProperty)
                                │
                                ▼
                  【顶层工具间 Object.prototype (#100)】
                    toString: function() { ... }
                    [[Prototype]] 纸条: null (到头了！再找不到就返回 undefined)
```
你看：**ES6 的 `class User` 根本不是什么新机制，它底层就是帮你自动建好这个 `#300` 公共工具间，并在每个实例里塞一张 `#300` 纸条的语法糖！**

### 2.3 一张表彻底终结 `this` 指向问题
既然 `sayHi` 函数住在 `#300` 公共工具间里，被 `u1` 和 `u2` 共享，那 `sayHi` 执行时怎么知道当前是 `u1`（张三）在说话，还是 `u2`（李四）在说话？
所以 JS 设计了 **`this`（当前调用的上下文门牌号）**。与词法作用域恰恰相反，**普通函数的 `this` 跟它在哪定义无关，只看调用它那一秒“点号 `.` 前面站着谁”**（按优先级从高到低只有 4 条规则）：

| 优先级 | 调用形式 | `this` 格子里装的门牌号是谁？ |
| :--- | :--- | :--- |
| **1（最高）** | `new User()` 构造调用 | 新创建出来的那个实例房间（如 `#501`） |
| **2** | `fn.call(target)` / `apply` / `bind` | 你在第一个参数里显式塞进去的 `target` 门牌号 |
| **3** | `u1.sayHi()` 对象方法调用 | **点号 `.` 前面站着的那个人**（即 `u1` `#501`！） |
| **4（最低）** | `sayHi()` 光杆司令直接调用 | 严格模式下为 `undefined`（非严格模式兜底为全局 `window`） |
| **特殊例外** | `() => {}` 箭头函数 | **箭头函数自己根本没有 `this` 格子！** 它直接顺着作用域链借用外层函数的 `this`（且无法被 `call/bind` 改写） |

## 4. 思考题

1. **查找变量 `x` 和查找属性 `obj.x`，分别顺着哪条纸条链往上找？如果一直找到最顶头都没找到，两者的结果有什么不同？**
2. **为什么把对象方法解构出来单独调用（如 `const { sayHi } = u1; sayHi()`）时，里面的 `this.name` 会报错？怎么修？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **作用域链 vs 原型链的终点差异**：查变量 `x` 顺着栈帧与闭包背包的**词法作用域链（`outer` 纸条）**往上找，找到全局作用域还没找到会直接抛出 `ReferenceError: x is not defined` 报错；而查属性 `obj.x` 顺着对象堆房间的**原型链（`[[Prototype]]` 纸条）**往上找，找到 `Object.prototype -> null` 还没找到时不会报错，而是静默返回 `undefined`。
2. **解构丢失 `this` 的原因与修法**：`const { sayHi } = u1` 只是把 `#300` 工具间里的函数地址赋给了变量 `sayHi`；随后执行 `sayHi()` 变成了第 4 类“光杆司令直接调用”，点号前面没人了，严格模式下 `this` 变成了 `undefined`。修复方法：要么写 `u1.sayHi()`，要么 `sayHi.bind(u1)`，或者在类定义中使用箭头函数绑定实例。

</details>
