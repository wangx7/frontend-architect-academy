# 第 05 讲｜JS 单线程与事件循环调度

> **本讲在主线的位置**：第二卷第 2 讲。连接了第 03 讲（并发模型）、第 04 讲（渲染管线）与第 07 讲（Vue `Scheduler` 与 `nextTick`）。

## 1. 场景与核心问题

你在按钮点击事件里写了一段再正常不过的代码：
```js
btn.onclick = () => {
  statusEl.textContent = '正在拼命计算中...' // ① 先提示用户
  heavyWork500ms()                           // ② 算了 500 毫秒
  statusEl.textContent = '计算完成！'        // ③ 更新结果
}
```
怪事发生了：点击按钮后，页面直接卡死半秒钟，**用户自始至终根本没看到 `'正在拼命计算中...'` 这几个字**，半秒后直接蹦出 `'计算完成！'`！
还有：为什么 `Promise.resolve().then(...)` 永远比 `setTimeout(..., 0)` 先打印？
答案全在 **事件循环（Event Loop）** 的两级队列调度规矩里。

## 2. 从零推导：宏任务、微任务与渲染插帧的四步铁律

### 2.1 为什么只有一条任务队列不够，非要分“宏任务”和“微任务”？
我们在 👉 **[概念 04：栈与队列](../02-概念/04-栈与队列.md)** 里学过，单线程要想不阻塞地处理定时器、网络回调和点击事件，就得让这些回调在**队列**里排队。
但如果全天下只有一条普通队列（**宏任务队列 Task / Macrotask Queue**）：当你的代码刚改完状态，想在浏览器画下一帧屏幕**之前**把关联的 Promise 链或 Vue DOM 更新赶紧收尾做完，如果去排普通队列，前面可能已经堵了 20 个鼠标移动和定时器回调！

于是宿主定下了**两级队列 + 渲染插帧**的四步循环铁律：

```text
      ┌──────────────────────────────────────────────────────────────────┐
      ▼                                                                  │
【第 1 步：只取 1 个宏任务 (Macrotask)】                                 │
  从宏任务队列队头取出 1 个任务（如 onclick / setTimeout 回调）执行      │
  ⚠️ 铁律：每轮循环只取 1 个！绝不连取第 2 个！                          │
      │                                                                  │
      ▼ （当前宏任务同步代码跑完，调用栈清空）                           │
【第 2 步：彻底清空全部微任务 (Microtask Checkpoint)】                   │
  执行所有 Promise.then / queueMicrotask / MutationObserver 回调         │
  ⚠️ 铁律：一清到底！连清空途中新塞进来的微任务也必须本轮当场清完！      │
      │                                                                  │
      ▼ （微任务队列彻底见底 = 0！）                                     │
【第 3 步：检查是否到达渲染时机 (Render Opportunity，如满 16.7ms)】      │
      ├─ 未到渲染时机 ──────────────────────────────────────────────────►┤
      ▼ 已到渲染时机！                                                   │
【第 4 步：执行渲染帧（即第 04 讲的流水线）】                            │
  跑 rAF 回调 ──► Style ──► Layout ──► Paint ──► Composite 上屏！        │
      └──────────────────────────────────────────────────────────────────┘
```

盯着这张图，开头的两个谜团当场解开：
1. **为什么 `Promise.then` 比 `setTimeout(fn, 0)` 快？** 因为 `setTimeout` 注册的是**宏任务**，必须排到下一轮循环的【第 1 步】；而 `Promise.then` 注册的是**微任务**，在当前这一轮的【第 2 步】就当场插队清空了！
2. **为什么 `'正在拼命计算中...'` 被吞掉了？** 因为 `statusEl.textContent = ...` 发生在【第 1 步：宏任务】里，它只改了内存里的 DOM 节点，**真正的屏幕绘制在【第 4 步】**！主线程在【第 1 步】里被 500ms 计算卡住后，紧接着又把文字改成了 `'计算完成！'`；等终于走到【第 4 步】画屏幕时，早就是最终文字了！

### 2.2 示例代码：用“时间切片（Time Slicing）”把 500ms 大任务切成不卡页面的小碎块
在前端架构中，任何霸占主线程超过 **50ms** 的任务都叫**长任务（Long Task）**。遇到几十万条数据处理时，每算 **8ms** 就主动用 `setTimeout` 让出一次主线程，让浏览器先去走完【第 4 步】画画面、响应用户点击，下一轮宏任务再接着算：

```js
// 时间切片调度器：每算 8ms 主动让出主线程一次，保持页面 60FPS 丝滑响应
async function processInChunks(items, handler) {
  let i = 0
  while (i < items.length) {
    const deadline = performance.now() + 8 // 每片最多占用主线程 8ms
    while (i < items.length && performance.now() < deadline) {
      handler(items[i++])
    }
    // ⚠️ 必须用宏任务 setTimeout 让出控制权（不能用 Promise 微任务，否则卡死在第2步不进第4步渲染！）
    await new Promise(resolve => setTimeout(resolve, 0))
  }
}
```


### 2.2 黄金实战：一段经典调度题的完整四阶段状态追踪

看下面这段混合了同步代码、微任务、宏任务与 `requestAnimationFrame` 的代码：

```js
console.log("1. 同步开始")
setTimeout(() => console.log("2. setTimeout 宏任务"), 0)
Promise.resolve()
  .then(() => console.log("3. Promise 微任务 1"))
  .then(() => console.log("4. Promise 微任务 2"))
queueMicrotask(() => console.log("5. queueMicrotask 微任务"))
console.log("6. 同步结束")
```

| 调度阶段 | 调用栈（Call Stack） | 微任务队列（Microtask Queue） | 宏任务队列（Macrotask Queue） | 终端输出顺序 |
| :--- | :--- | :--- | :--- | :--- |
| **阶段 1：执行首个宏任务（整段脚本）** | 输出 `1`；注册定时器；将 `Promise.then(3)` 与 `queueMicrotask(5)` 压入微任务队列；输出 `6` | `[ 微任务3, 微任务5 ]` | `[ setTimeout(2) ]` | `1. 同步开始`<br>`6. 同步结束` |
| **阶段 2：排空全部微任务（死磕到底）** | 先弹出 `微任务3` 执行（其完成后将链式 `.then(4)` 追加进微任务队尾）；再执行 `微任务5`；最后执行新入队的 `微任务4` 直至队列彻底为空！ | `[ 微任务5, 微任务4 ]` ──► `[]` | `[ setTimeout(2) ]` | `3. Promise 微任务 1`<br>`5. queueMicrotask 微任务`<br>`4. Promise 微任务 2` |
| **阶段 3：浏览器渲染时机（若到达 16.6ms 帧边界）** | 若当前帧需要重绘，依次执行 `rAF` 回调 ──► Style ──► Layout ──► Paint ──► Composite 上屏 | `[]` | `[ setTimeout(2) ]` | （画面更新上屏） |
| **阶段 4：下一轮事件循环取 1 个宏任务** | 从宏任务队列取出 `setTimeout(2)` 执行 | `[]` | `[]` | `2. setTimeout 宏任务` |

> **第三层（边界与反例）**：切勿滥用 `queueMicrotask` 或无限递归 `Promise.then`！因为事件循环规定**必须把微任务队列彻底清空才会进入渲染阶段**，如果微任务不断衍生新微任务，会导致主线程饥饿，页面同样完全卡死（这正是为什么 React 时间切片选择宏任务 `MessageChannel` 而非微任务！）。

## 4. 思考题

1. **如果写一个函数 `function loop() { Promise.resolve().then(loop) }` 并在页面里调用，页面会发生什么？如果把 `Promise.resolve().then` 换成 `setTimeout(loop, 0)` 呢？**
2. **如果你想在修改 DOM 后，先让浏览器把 Loading 真正画到屏幕上，然后再开始跑一段同步耗时计算，代码应该怎么套？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **微任务死递归 vs 宏任务递归**：`Promise.resolve().then(loop)` 会在【第 2 步：清空微任务】阶段无限往微任务队列里塞新微任务，因为微任务的规矩是“不清空绝不往下走”，主线程会永久卡死在第 2 步，页面彻底冻死（无法点击、无法滚动、无法渲染）。而 `setTimeout(loop, 0)` 每轮只执行 1 个宏任务，新注册的 `setTimeout` 排在下一轮，中间会正常走过【第 4 步】渲染画面并响应用户事件，所以页面不会卡死。
2. **确保先上屏再计算的标准写法**：先改 DOM `loading.style.display = 'block'`，然后套一层 `requestAnimationFrame(() => { setTimeout(() => { heavyWork() }, 0) })`——`rAF` 确保来到了第 4 步渲染帧前夕，里面的 `setTimeout` 则把耗时计算推迟到本帧绘制上屏之后的下一轮宏任务去执行。

</details>
