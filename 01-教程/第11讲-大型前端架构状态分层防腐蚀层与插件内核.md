# 第 11 讲｜大型前端架构：状态分层、防腐蚀层、类型建模与 ADR 决策

> **本讲在主线的位置**：第三卷第 3 讲（大型前端系统设计核心）。回答前端架构师最常面对的四个工程治理命题：**① 状态究竟该归谁管（何时用查询缓存、何时用领域 Store）？② 后端接口频繁变动时，如何用防腐蚀层（ACL）与 TypeScript 可辨识联合类型锁死爆炸半径？③ 复杂业务模块如何用微内核插件化替代上千行的 `if-else`？④ 如何编写一份经得起团队评审的架构决策记录（ADR）？**

## 1. 场景与核心问题

假设你接手了一个迭代了三年的大型供应链中后台系统，打开代码库看到四个典型症状：
1. **全局 Store 与组件状态职责失焦**：有的团队把所有分页列表、详情接口返回的数据全塞进全局 Pinia/Redux，切页面忘记清理就出现脏数据闪烁；另一个极端则是听信“服务端数据一律不准进 Store”的教条，导致需要跨 5 个工作区协同编辑的复杂采购单数据散落在各组件里无法同步。
2. **后端改一个字段名，前端改 40 个组件文件**：后端把订单状态字段从 `ord_sts: 1` 改成 `status: 'PAID'`，前端有 40 个 `.vue` 文件里直接写着 `v-if="item.ord_sts === 1"`，牵一发而动全身。
3. **非法状态组合引发线上幽灵 Bug**：组件里同时定义了 `isLoading: boolean`、`isError: boolean`、`data: Order | null`，某次异常分支漏重置 `isLoading`，页面竟然同时转着加载圈又弹出报错提示！
4. **核心模块沦为 3,000 行的 `if-else` 泥潭**：导出报表或富文本画布每加一个新业务方定制逻辑，就在核心函数里加 `if (tenant === 'A')`，没人敢重构。

## 2. 第一层（直观模型）与第二层（真实机制）：四大架构治理武器

### 2.1 武器一：状态所有权分类与边界权衡（破除一刀切教条）

很多文章会给出死板口诀：“服务端状态绝不进 Pinia”、“全站不能超过 5 个 Store”。**在真实工程中，这种不看业务上下文的硬性数字是危险的。**
架构师划分状态的真正标准不是“数据从哪来”，而是**“数据在客户端生命周期内的所有权、读写模式与同步复杂度”**：

| 状态类别 | 核心特征与生命周期 | 推荐首选方案 | 何时打破常规？（第三层：反例与边界） |
| :--- | :--- | :--- | :--- |
| **1. 远端异步快照状态 (Remote Cache State)** | 所有权在后端数据库；前端主要是**“拉取展示 + 过期刷新 + 局部乐观更新”**（如商品列表、订单日志） | **TanStack Query (Vue Query)** / SWR 或带 [LRU 缓存](../02-概念/09-LRU缓存淘汰算法.md) 的请求管理层（自动处理缓存去重、焦点刷新、竞态丢弃） | **反例（何时应该放进 Pinia/Zustand 领域 Store？）**：<br>① **离线优先或重度客户端协同编辑应用**（如在线画布、多步复杂排程工作台）：数据拉下来后需在前端经历几十步跨组件本地派生、撤销重做（Undo/Redo）最后才批量提交，此时它已转化为**客户端领域模型（Domain State）**，放入按领域划分的 Store 更合适；<br>② **极低频变动的全局基础字典/权限配置**：在应用启动时拉取一次、全站同步读取的权限树或枚举表，存入 `useAuthStore` 比到处调异步 Query 更直接。 |
| **2. URL 视图定位状态 (URL / Router State)** | 决定“当前看哪一页、什么筛选条件”；要求**刷新不丢、前进后退可恢复、复制链接可复现** | 路由 `query / params` 与响应式同步封装（如 `useUrlSearchParams`） | **反例**：包含敏感隐私的参数（如身份证号筛选）或超大 JSON 筛选树不宜直接裸露在 URL 中，应改用服务端短链 Snapshot ID（`?filterId=f_982`）或 `sessionStorage`。 |
| **3. 跨模块客户端状态 (Shared Domain / UI State)** | 跨多个不相邻组件共享的客户端状态（如主题、多标签页工作区、购物车草稿） | **Pinia / Zustand**（按**业务限界上下文 Bounded Context** 拆分 Store，而非规定死板的数字上限） | **边界说明**：Store 的数量取决于业务子域边界（5 个子域就 5 个 Store，20 个独立业务域完全可以有 20 个按需加载的 Store）。真正的禁忌不是 Store 数量，而是**缺乏模块边界、所有组件随意直接篡改的“大泥球根 Store”**。 |
| **4. 组件局部状态 (Local UI State)** | 仅单个组件或紧密父子组件关心的临时交互态（下拉框展开、弹窗显隐、输入框未提交草稿） | 组件内 `ref / useState`（遵循**状态就近原则 Colocation**） | 当兄弟组件频繁需要同步该状态时，才适度向上提升（Lift State Up）到最近的共同父组件。 |

### 2.2 武器二：防腐蚀层（Anti-Corruption Layer, ACL）+ TypeScript 可辨识联合类型

#### 1. 防腐蚀层（ACL）：把后端接口变动锁死在单文件内
为了防止后端 DTO（数据传输对象）的怪异命名、空值缺陷直接渗透进 40 个 UI 组件，架构师会在 `API 基础设施层` 与 `UI 视图层` 之间建立一层显式的 **防腐蚀转换层（ACL Mapper）**：

```text
后端接口原始 DTO (随数据库表结构与历史包袱变动)
  { ord_id: 101, ord_sts: 2, pay_fen: 9950, usr_nm: null }
        │
        ▼ 【防腐蚀层 ACL (orderMapper.ts) —— 全项目唯一允许出现 ord_sts 的隔离带！】
前端领域模型 Domain Model (类型安全、语义清晰、默认值完备)
  { id: '101', status: 'PAID', statusText: '已支付', priceYuan: '¥99.50', buyerName: '匿名用户' }
        │
        ▼
UI 组件层（40 个页面组件只依赖干净的 Domain Model；后端改字段时，前端永远只改 orderMapper.ts 一处！）
```

#### 2. 用 TypeScript“可辨识联合类型（Discriminated Unions）”从编译期消灭非法状态
在前端状态建模中，尽量避免用多个松散的布尔值（`isLoading: boolean; isError: boolean; data?: T`）组合状态（因为 `2 × 2 × 2 = 8` 种组合里有一半是不合法的幽灵状态）。
改用 **TypeScript 可辨识联合类型（状态机建模）**，让编译器强制帮你检查分支：

```ts
// ❌ 脆弱的布尔组合建模：可能同时出现 isLoading=true 且 error!=null 的非法状态
interface BadRequestState<T> {
  isLoading: boolean
  data: T | null
  error: Error | null
}

// ✅ 架构师级类型建模：用 status 字面量作为可辨识标签，合法状态只有这 4 种！
type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }      // 只有 status === 'success' 时，类型系统才允许访问 .data！
  | { status: 'error'; error: string }  // 只有 status === 'error' 时，类型系统才允许访问 .error！
```

### 2.3 武器三：微内核 + 插件化架构（Microkernel）—— 用扩展点代替修改核心代码

当面对富文本编辑器、报表引擎、请求流水线或埋点 SDK 等“核心流程稳定、但业务定制规则层出不穷”的模块时，采用 **微内核（Core）+ 插件（Plugin）** 模式：
- **微内核（Core）**：只负责维护上下文状态与生命周期钩子流水线（不到 50 行代码，稳定不变）；
- **插件（Plugin）**：每个业务特性封装为独立插件，通过标准契约挂载到钩子上，实现**对扩展开放、对修改关闭（开闭原则 OCP）**。

```js
// microkernel-acl-demo.mjs —— 直接用 node 运行，验证“防腐蚀层转换 + 微内核插件流水线”
// 1. 防腐蚀层（ACL）：将后端原始脏 DTO 清洗为前端标准领域模型
export function toOrderDomainModel(rawDto) {
  const statusMap = { 0: 'PENDING', 1: 'PAID', 2: 'CANCELLED' }
  return {
    id: String(rawDto.ord_id ?? ''),
    status: statusMap[rawDto.ord_sts] ?? 'UNKNOWN',
    amountYuan: ((rawDto.amt_fen ?? 0) / 100).toFixed(2),
    customerName: rawDto.cust_nm || '默认客户'
  }
}

// 2. 微内核引擎：提供标准生命周期钩子与插件注册能力，核心逻辑零业务 if-else
export class DocumentKernel {
  constructor() {
    this.hooks = {
      beforeSave: [], // 同步/异步转换钩子队列
      afterSave: []   // 保存后通知钩子队列
    }
  }

  use(plugin) {
    plugin. setup(this.hooks)
    return this
  }

  async executeSave(rawDoc) {
    let current = { ...rawDoc }
    for (const transformFn of this.hooks.beforeSave) {
      current = await transformFn(current)
    }
    const savedRecord = { ...current, savedAt: '2026-10-14T10:00:00Z' }
    for (const notifyFn of this.hooks.afterSave) {
      await notifyFn(savedRecord)
    }
    return savedRecord
  }
}

// 独立插件 1：敏感词脱敏插件
const sanitizePlugin = {
  setup(hooks) {
    hooks.beforeSave.push(doc => ({ ...doc, content: doc.content.replace(/内部机密/g, '[已脱敏]') }))
  }
}

// 独立插件 2：审计日志插件
const auditLogs = []
const auditPlugin = {
  setup(hooks) {
    hooks.afterSave.push(doc => auditLogs.push(`已归档文档 #${doc.id}: ${doc.content}`))
  }
}

const kernel = new DocumentKernel().use(sanitizePlugin).use(auditPlugin)
const cleanOrder = toOrderDomainModel({ ord_id: 9527, ord_sts: 1, amt_fen: 18800, cust_nm: '' })
console.log('1. ACL 清洗后的领域模型:', cleanOrder)

kernel.executeSave({ id: cleanOrder.id, content: '这是一份内部机密采购单' }).then(res => {
  console.log('2. 微内核处理结果:', res)
  console.log('3. 插件审计日志:', auditLogs)
})
```

## 3. 第三层（边界与反例）：什么时候不该做防腐蚀层与插件化？如何写 ADR？

任何架构抽象都不是免费的，都会带来**间接层理解成本（Indirection Cost）**与代码文件数量的增加。

### 3.1 过度设计的反例与适用边界
1. **何时不需要重度 ACL 防腐蚀层？**
   - 如果你们团队采用了 **BFF（Backend For Frontend）** 或 **GraphQL / tRPC 全栈同构类型共享**，BFF 层已经专门为前端页面裁剪并对齐了字段语义，前端再在浏览器里手写一层冗长的 Class/Mapper 转换纯属画蛇添足；
   - 对于生命周期只有两周的营销活动页或简单 CRUD 内部工具，直接基于 OpenAPI 自动生成的 TypeScript 接口类型开发即可，不必强上复杂 DDD 分层。
2. **何时不该搞微内核插件化？（遵循 Rule of Three 事不过三法则）**
   - 当一个模块目前只有 1～2 种确定的业务分支，且未来半年没有多团队扩展诉求时，直接写清晰的策略函数或 `switch` 分支反而最直观好查；过早设计庞大的插件生命周期钩子，只会让新同事跳 5 个文件还找不到一行真正干活的代码。

### 3.2 架构师实战基本功：编写一份 ADR（Architecture Decision Record，架构决策记录）

在真实研发团队中，架构师推动重构靠的不是拍脑袋下命令，而是写出一份只有 1 页纸、但把**背景、备选方案对比、最终决策、负面代价与退出条件**写得清清楚楚的 **ADR 文档**（存放在仓库 `docs/adr/` 目录下）：

```markdown
# ADR-004：中后台订单模块服务端状态管理与接口适配层重构方案

- **状态**：已采纳（2026-10）
- **背景与问题（Context）**：
  当前订单模块将 18 个列表与详情接口响应全部存入单一 `useOrderStore`，导致切页残留脏数据 Bug 频发（近两月 6 起）；且后端供应链接口改造频繁，每次字段变更平均波及 15+ 个 Vue 组件。
- **备选方案对比（Options Considered）**：
  1. **方案 A（维持全量 Pinia Store，增加手动 reset 规范）**：零新依赖，但依赖人工遵守规范，仍无法自动处理并发竞态、缓存过期与分页去重；
  2. **方案 B（引入 TanStack Vue Query 管理纯查询列表 + 保留精简 Pinia 管理跨步创建订单草稿 + 单函数 ACL 映射）**：利用成熟缓存状态机消除样板代码，但需约 3 人日迁移成本；
  3. **方案 C（全面引入面向对象 DDD 实体类 + Inversify 依赖注入容器）**：隔离最彻底，但对现有前端团队心智负担过重，打包体积与样板代码激增。
- **最终决策（Decision）**：采纳 **方案 B**。
  - 纯查询类接口（订单列表、物流轨迹）迁移至 `useQuery`，并在 `queryFn` 出口统一通过纯函数 `toOrderDomainModel()` 完成字段防腐蚀转换；
  - 跨步骤复杂表单草稿保留在 `useOrderDraftStore` 中。
- **后果与退出条件（Consequences & Exit Criteria）**：
  - **正面收益**：删减约 1,200 行手动维护 `loading/error` 的 Store 样板代码，后端字段变更修改范围收敛至 `src/domains/order/mapper.ts` 单文件；
  - **负面代价**：团队需掌握 `queryKey` 依赖失效机制；
  - **未来复审条件**：若未来后端上线统一 BFF 层并提供 OpenAPI 强契约生成，可移除手写 ACL 映射函数。
```

## 5. 思考题与架构演进训练

1. **为什么在列表快速切换筛选条件（如先点“全部订单”耗时 800ms、紧接着点“待付款”耗时 100ms）时，即使不用全局 Store，只用普通 `watch + axios` 也会出现“页面明明选中了待付款，列表却被晚回来的全部订单覆盖”的竞态 Bug？你有哪两种根治方案？**
2. **【架构演进题】你们团队正在把一个 10 万行代码的 Vue 2 + Vuex 老巨石系统渐进迁移到 Vue 3。为什么“停下所有业务需求，花两个月一次性全部重写”几乎必然失败？你会如何利用本讲的“防腐蚀边界”制定渐进式迁移计划？**

1. **异步请求竞态（Out-of-Order Response / Race Condition）的两种根治方案**：
   - **方案一（主动取消旧请求 `AbortController`）**：每次发起新查询前，调用上一次请求绑定的 `abortController.abort()`，直接中断旧请求；
   - **方案二（请求序号令牌 / `onCancel` 失效标记）**：递增一个 `requestId` 计数器（或使用 Vue `watch(source, async (val, oldVal, onCleanup) => ...)`），当响应返回时比对 `myReqId === latestReqId`，若发现自己已是过期的旧请求，直接丢弃响应结果不写状态（详见 [实验 08](../03-实验/实验08-手写LRU缓存与请求竞态锁.md)）。
2. **巨石系统渐进式演进策略（绞杀者模式 Strangler Fig Pattern）**：
   - 一次性停业务重写会面临业务需求双线同步、测试回归面失控与上线爆炸半径过大三大死穴；
   - 稳健做法是：① 先统一抽象数据请求与防腐蚀模型层（纯 TS 模块，不耦合 Vue 2/3 版本）；② 通过路由级微前端（见第 12 讲）或构建桥接，让新业务模块直接用 Vue 3 编写，老模块按业务迭代热度逐个页面替换（“修路不断交”），直至老代码自然归零。

</details>
