# 第 11 讲｜大型前端架构：状态分层、防腐蚀层与插件内核

> **本讲在主线的位置**：第三卷第 3 讲（大型项目软件设计核心）。回答前端架构师最核心的命题：**当业务需求天天变、后端接口经常改时，怎么设计前端代码结构，才能让“变化”被锁在最小的笼子里，不波及全站？**

## 1. 场景与核心问题

你接手了一个维护了三年的中后台项目，打开代码一看血压直接拉满：
1. **Pinia / Vuex 成了大垃圾桶**：所有的后端接口返回数据全往全局 Store 里塞，一共 200 个字段，没人知道哪个字段是谁改的，切个页面还经常看到上个页面的残留脏数据。
2. **后端改一个字段名，前端改 40 个 `.vue` 文件**：后端把订单接口里的 `ord_sts: 1` 改成了 `status: 'PAID'`，结果前端有 40 个组件里直接写着 `v-if="item.ord_sts === 1"`，全组人通宵全局搜索替换，还漏改了 3 处导致线上报错！
3. **核心组件写成了 3,000 行的 `if-else` 怪兽**：一个富文本编辑器或工作流画布，每加一个新功能就在核心文件里加 `if`，谁改谁崩。

这三大绝症，分别对应前端架构师的三大核心设计武器：**状态四层切分**、**防腐蚀层（ACL）** 与 **微内核插件化架构**。

## 2. 从零推导：大型前端系统的三大定海神针

### 2.1 第一针：状态分层 —— 严禁把“服务端缓存状态”和“客户端 UI 状态”混为一谈！
为什么你的全局 Store 会变成垃圾桶？因为你没有区分状态的**所有权**！
在现代前端架构中，任何状态必须严格对号入座归入以下四层：

| 状态层级 | 真实归属者 | 典型例子 | 架构师推荐管理工具 |
| :--- | :--- | :--- | :--- |
| **1. 服务端状态 (Server State)** | **后端数据库**（前端手里的只是一份随时可能过期的异步缓存快照！） | 用户订单列表、商品详情 | **TanStack Query (Vue Query)** 或带 [LRU 缓存](../02-概念/09-LRU缓存淘汰算法.md) 的请求层（管缓存、过期刷新、并发去重、竞态取消），**绝不手塞进 Pinia！** |
| **2. URL 路由状态 (URL State)** | **浏览器地址栏**（刷新不丢、复制链接能直接分享给别人复现当前视图） | 当前搜索关键词 `?q=vue`、页码 `page=2`、筛选 Tab | `vue-router` query / params 同步 composable |
| **3. 全局客户端状态 (Global UI State)** | **前端应用全局**（跨多个不相邻模块共享的纯客户端状态） | 当前亮暗主题、侧边栏折叠态、全局登录用户身份 | **Pinia / Zustand**（保持极度精简，通常全站不超过 5 个 Store！） |
| **4. 局部组件状态 (Local UI State)** | **单个组件内部**（别的组件根本不关心） | 弹窗开关 `isOpen`、表单输入框草稿值 | 组件内 `ref / reactive`（能放局部的，绝不提升到全局！） |

### 2.2 第二针：防腐蚀层（Anti-Corruption Layer, ACL）—— 不让后端脏字段污染你的视图层！
为什么后端改一个 `ord_sts` 字段名，你要改 40 个 `.vue` 组件？因为你让后端的原始接口格式（DTO）长驱直入冲进了所有的 UI 组件里！
正确的架构是在 `API 请求层` 和 `Vue 组件层` 之间立一道 **防腐蚀墙（ACL / Adapter 转换函数）**：

```text
后端接口原始返回 (脏、缩写、随后端表结构变动)
  { ord_id: "101", ord_sts: 1, amt_fen: 9900 }
        │
        ▼ 【防腐蚀层 ACL（全场唯一允许出现 ord_sts 的地方！）】
前端干净的领域模型 (Domain Model)
  { id: "101", isPaid: true, statusLabel: "已支付", displayPrice: "¥99.00" }
        │
        ▼
40 个 Vue 页面组件（只认 item.isPaid 和 item.displayPrice！以后后端再改字段名，只需改 ACL 那 1 行代码！）
```

### 2.3 第三针：微内核 + 插件化架构（Microkernel）—— 消灭 3,000 行 `if-else`
当你设计一个复杂模块（如报表引擎、画布编辑器、请求SDK、埋点SDK）时，把**永远不变的核心调度流程**抽成不到 100 行的**微内核（Core）**，把所有可能会新增的功能全部做成标准接口的**插件（Plugin）**：

```js
// 25 行实现一个工业级“微内核 + 插件化”架构（Axios 拦截器 / Vite 插件 / 编辑器内核通用范式）
class EditorCore {
  constructor() {
    this.plugins = []
    this.hooks = { beforeSave: [], afterSave: [] } // 生命周期钩子槽位
  }
  // 注册插件：每个插件只需提供一个 install(core) 方法，核心代码永远不用改！
  use(plugin) {
    this.plugins.push(plugin)
    plugin.install(this)
    return this // 支持链式调用 core.use(p1).use(p2)
  }
  async save(content) {
    let data = content
    for (const fn of this.hooks.beforeSave) data = await fn(data) // 依次过插件流水线
    console.log('💾 内核保存最终内容:', data)
    for (const fn of this.hooks.afterSave) await fn(data)
  }
}

// 插件 1：敏感词过滤插件 | 插件 2：自动打埋点插件（新增 100 个功能也不用改 EditorCore 一行代码！）
const wordFilterPlugin = { install: core => core.hooks.beforeSave.push(txt => txt.replace(/机密/g, '**')) }
const analyticsPlugin  = { install: core => core.hooks.afterSave.push(txt => console.log('📊 上报字数:', txt.length)) }

const editor = new EditorCore().use(wordFilterPlugin).use(analyticsPlugin)
editor.save('这是一份机密架构文档')
```

## 4. 思考题

1. **为什么把筛选条件（如搜索词、当前页码、选中的分类）放在 `ref()` 局部变量里往往是糟糕的设计，而应该同步到 URL Query（`?keyword=xxx&page=2`）里？**
2. **什么是“抽象过早（Premature Abstraction）”？为什么架构上有著名的“事不过三法则（Rule of Three）”？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **URL State 的核心价值**：如果筛选条件只存在内存 `ref()` 里，用户点进商品详情再点浏览器“后退”按钮，或者按 F5 刷新页面，刚翻到的第 5 页和筛选条件就全部清零丢失了；而且客服或同事想复现问题时，复制网址发过去别人看到的却是默认第 1 页。把筛选态放入 URL Query，天然具备了持久化、前进后退历史栈恢复与一键分享复现三大能力。
2. **Rule of Three（事不过三）**：当两段代码刚出现相似时，它们未来演进的方向可能完全不同；如果立刻强行抽成一个公共组件，后续两边各自提特殊需求，你就只能往公共组件里狂加 `isOrderPage`、`hideHeader`、`customMode` 等几十个布尔 props，把它变成谁也不敢动的怪兽。等到第 3 个真实场景出现、看清了什么是不变的共性、什么是变化的扩展点后，再用插槽（Slot）或插件模式抽象，才是最稳健的架构时机。

</details>
