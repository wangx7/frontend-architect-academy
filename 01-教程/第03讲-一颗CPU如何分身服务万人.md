# 第 03 讲｜一颗 CPU 如何分身服务万人？

> **本讲在主线的位置**：第一卷收官。搞懂了**进程（独立房子）与线程（同屋工人）**，你就同时看懂了为什么 Chrome 一个标签页崩了不会带崩整个浏览器、为什么 JS 主线程不准和 Worker 共享普通对象、以及后端高并发为什么会出现超卖竞态。

## 1. 场景与核心问题

你的电脑只有 8 颗 CPU 核心，却同时开着 50 个 Chrome 标签页、VS Code 和音乐播放器；你的后端服务器也只有 8 颗核心，却同时连着 3,000 个在线用户。
第 01 讲刚说过：**每颗 CPU 核心在同一纳秒只能执行一条指令**。那这“3,000 人同时在线”到底是真分身，还是魔术幻觉？

## 2. 从零推导：时间片轮转、进程房子与线程工人

### 2.1 拆穿“同时”的魔术：时间片切换（并发 vs 并行）
真相非常朴素：**单颗 CPU 核心永远一次只干一件事，“同时”是操作系统高速切换造出来的幻觉。**
操作系统把 1 秒钟切成几百个几毫秒的**时间片（Time Slice）**：
- 让程序 A 跑 2 毫秒 → 把 A 当前算到哪一行、寄存器里是什么数记在书签上（**保存上下文**）；
- 切换到程序 B 跑 2 毫秒 → 记下 B 的书签；
- 再切回程序 A 从书签处继续跑……

这就好比你同时读 5 本书：任何一秒你只能看一本，但你每看两页就夹上书签换下一本，手速快到别人以为你长了五双眼睛。
- **并发（Concurrency）**：通过快速“夹书签换书”（或者像 [队列](../02-概念/04-栈与队列.md) 交替调度），在一段时间内推进多件事——这是**组织结构的能力**（单核 CPU 也能高并发）；
- **并行（Parallelism）**：有 8 颗物理 CPU 核心，在同一纳秒真刀真枪同时跑 8 条指令流——这是**硬件钞能力**。

### 2.2 进程（Process）vs 线程（Thread）：独立大房子 vs 同屋亲兄弟
操作系统切换的对象分为两级：

```text
┌─ 进程 P1（OS 分给的独立大房子：独立内存门牌号 #100~#999）──────┐   ┌─ 进程 P2（另一套独立房子）─┐
│  【共享堆区 Heap】：全屋工人看的是同一批堆房间！                │   │  P2 和 P1 互相看不见内存！ │
│     #500 房间: { stock: 1 }   ◄── 工人1和工人2都能直接摸到它！ │   │  P2 崩溃着火，绝不波及 P1！│
│                                                                │   │  （Chrome 每站点一进程）   │
│  【独享栈区 Stack】：                                          │   └────────────────────────────┘
│     线程1 (工人1 的调用栈)      线程2 (工人2 的调用栈)         │
└────────────────────────────────────────────────────────────────┘
```

1. **进程（独立房子）**：每个进程拥有自己完全独立的内存门牌号空间。进程 A 绝对摸不到进程 B 的内存格子。
   - **好处**：安全隔离！Chrome 把每个网站标签页放在独立的渲染进程里，某网页写死循环崩了，关掉它就行，别的标签页毫发无损。
   - **代价**：切换进程等于“搬家换房”，开销很大。
2. **线程（同一房子里的多个工人）**：同一个进程内部可以雇多个线程工人。**它们共享同一个堆区（`#500` 房间大家都能直接读写），只各自独享自己的函数调用栈！**
   - **好处**：切换线程不用换房子，只换一下用哪个调用栈，比切进程便宜十倍！

### 2.3 共享堆的代价：竞态条件（Race Condition）是如何闯祸的？
既然同进程的多个线程能直接摸到同一个堆房间 `#500 { stock: 1 }`，如果两个线程同时来执行 `stock = stock - 1`（抢最后 1 件库存），灾难就发生了：
`stock = stock - 1` 在物理上其实是**三步动作**：① 读出 `stock` 的值（`1`） → ② 算出 `1 - 1 = 0` → ③ 把 `0` 写回格子。
如果线程 1 刚做完第 ① 步（读出 `1`），时间片到了被切走；线程 2 进来把 ①②③ 全做完（把库存改成了 `0`，抢购成功）；随后线程 1 恢复执行，**它手里拿的还是过期的旧值 `1`**，减 1 写回 `0`，也宣布抢购成功！**1 件库存卖出了 2 单（超卖）！**

### 2.4 示例代码：在异步 I/O 间隙亲眼复现一次“共享状态竞态超卖”
```js
// 哪怕在单线程异步环境里，“先读旧值 -> 异步等待 -> 把旧值减1写回”同样会引发竞态超卖！
let stock = 1 // 共享内存格子里只剩最后 1 件商品

async function buy(user) {
  const current = stock                        // ① 先读出库存（A 和 B 同时读到了 1！）
  await new Promise(r => setTimeout(r, 20))    // 模拟去查数据库或网络的等待间隙
  if (current > 0) {
    stock = current - 1                        // ② 两人拿手里的旧值 1 减 1 写回 0！
    console.log(`🎉 ${user} 抢购成功！剩余库存: ${stock}`)
  }
}

Promise.all([buy('用户张三'), buy('用户李四')])
// 输出：张三和李四双双抢购成功！这就是为什么并发修改共享状态必须加锁或用原子操作！
```

## 3. 前后端架构双视角映射

| 并发问题 | 前端架构的选择 | 后端与系统架构的选择 |
| :--- | :--- | :--- |
| **如何对付多线程竞态？** | **直接掀桌子不准共享！** 浏览器 JS 主线程与 `Web Worker` 线程之间默认**禁止共享堆内存**，通信只能靠 `postMessage` 把数据复印一份寄过去——宁可牺牲一点拷贝时间，也绝不让前端开发者每天写锁调死锁！ | Java / Go 多线程共享堆内存，必须使用互斥锁（`Mutex / synchronized`）、原子指令（`CAS`）或数据库行锁 / MVCC 保护共享状态 |
| **I/O 等待时 CPU 干嘛？** | 当发起 `fetch` 网络请求时，主线程绝不傻等，立刻通过 [队列](../02-概念/04-栈与队列.md) 切去跑别的事件和页面渲染（详见第 05 讲事件循环） | 传统线程模型将等待 I/O 的线程挂起让出 CPU；现代高并发网关（Nginx / Node）采用单线程/少量线程事件循环 + 非阻塞 I/O，用极少内存扛住数万并发连接 |

## 5. 思考题

1. **为什么切换线程比切换进程便宜得多？** 请用“房子（地址空间）”和“工作台（调用栈）”回答。
2. **JS 主线程选择“单线程不共享内存”躲开了锁和竞态，但它付出了什么代价？如果遇到一个要算 3 秒钟的加密或大表导出任务，页面会怎样？该怎么破？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **切换成本差异**：切换进程需要把整套虚拟内存地址空间（页表）全部换掉，还会导致 CPU 内部的高速缓存失效；而同一个进程里的多个线程住同一套房子、看同一片堆内存，切换线程只需保存几个寄存器并把栈指针切到另一个线程的调用栈即可。
2. **单线程的代价与破局**：代价是“算的时候不能响应交互”——因为 JS 执行、DOM 事件响应和页面重绘共用同一个渲染主线程，3 秒的纯计算会把主线程死死堵住，导致页面冻结 3 秒。破局方案有二：① 用 `Web Worker` 开辟真正的后台线程算完再把结果 `postMessage` 回来；② 用时间切片（Time Slicing）把 3 秒大任务切成几百个 8ms 的小分片，每片之间让出主线程给浏览器画画面（详见第 05 讲）。

</details>
