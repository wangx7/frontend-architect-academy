# 第 04 讲｜字节是怎么变成屏幕像素的？

> **本讲在主线的位置**：第二卷（浏览器与框架内核）第 1 讲。前端性能优化的 80%（白屏、闪屏、掉帧、布局抖动 CLS），全都是从浏览器这五步渲染流水线里长出来的。

## 1. 场景与核心问题

打开 Network 面板，`index.html` 只用 40ms 就下载完了。但为什么页面有时还会白屏好几百毫秒？为什么动画改 `transform` 丝滑如德芙，改 `width / left` 却卡成 PPT？为什么在循环里读一下 `offsetWidth` 会让页面慢十倍？

因为 HTML 响应只是**一串文本字节**，而显示器只认**像素点的颜色**。这中间必须跑完一条五步大流水线。

## 2. 从零推导：浏览器渲染五步流水线

```text
HTML 字节流 ──► 【1. 解析 Parse】 用栈配对标签，建出 DOM 树（骨架）
CSS 字节流  ──►                  解析样式规则，建出 CSSOM 树（尺码配色表）
                                     │
                                     ▼
                【2. 样式计算 Style】 算出每个 DOM 节点的最终 Computed Style
                                     │
                                     ▼
                【3. 布局 Layout】    算出每个可见盒子的精确坐标 (x, y) 与宽高 (w, h)
                                     │
                                     ▼
                【4. 绘制 Paint】     分层并列出一张“先画底色、再写字”的绘制指令单
                                     │ (以上 1~4 步全由【渲染主线程】干活！)
                                     ▼
                【5. 合成 Composite】 【合成器线程 + GPU】把图层切成瓷砖涂成像素，合成上屏！
```

### 2.1 第一步里的拦路虎：`<script>` 与 `<link>` 到底谁阻塞谁？
HTML 解析器用 👉 **[概念 04：栈与队列](../02-概念/04-栈与队列.md)** 边收字节边搭 DOM 树。但途中会遇到两位拦路虎：
1. **普通 `<script src="app.js">` 会当场叫停 HTML 解析**：因为 JS 里可能写着 `document.write` 或修改 DOM 的代码，解析器不敢继续往下搭树，只能停工等 JS 下载并执行完。
   - **解法**：业务脚本一律用 `<script defer>` 或 `<script type="module">`（后台并行下载，等整棵 DOM 树建完后再按顺序执行）；完全独立的统计脚本用 `<script async>`。
2. **CSS `<link>` 不阻塞 DOM 树构建，但阻塞“首次渲染”和“后续 `<script>` 执行”**：没有样式表就没法算坐标画屏幕（强行先画裸 HTML 会引发刺眼的无样式闪烁 FOUC）；而且如果 `<link>` 后面紧跟着 `<script>`，万一 JS 里要读元素的宽度，浏览器就必须等 CSS 下载解析完才敢放行 JS！

### 2.2 重排（Layout）vs 重绘（Paint）vs 直接合成（Composite）
为什么页面渲染好之后，你用 JS 或 CSS 修改样式，代价天差地别？

| 你修改了什么属性 | 触发的流水线阶段 | 性能代价与架构师对策 |
| :--- | :--- | :--- |
| **几何尺寸位置**（`width`, `height`, `top`, `left`, 增删 DOM） | `Style ──► Layout (重排) ──► Paint (重绘) ──► Composite` | **最贵！** 主线程必须重新计算受影响盒子的坐标。可用 👉 [概念 13：BFC 与 contain 边界](../02-概念/13-合成层与BFC布局边界.md) 隔离传染范围，大列表必上虚拟滚动 |
| **纯外观颜色**（`color`, `background-color`） | `Style ──────────────────► Paint (重绘) ──► Composite` | **中等**。盒子位置大小没变，跳过了几何计算 `Layout`，但主线程仍需重列绘制指令并重涂像素 |
| **独立合成层的 `transform` / `opacity`** | `仅触发合成器线程 + GPU：Composite` | **极速！** 彻底绕开主线程的 `Layout` 和 `Paint`，直接由 GPU 对显存里印好的透明胶片做位移（详见 👉 [概念 13：GPU 合成层](../02-概念/13-合成层与BFC布局边界.md)） |

### 2.3 示例代码：千万别在循环里“边写边读”制造强制同步布局！
现代浏览器本来会把你连续 100 次的样式修改攒到一起，等 JS 跑完只做 **1 次 Layout**。但如果你**刚写完样式，下一行立刻读取 `offsetWidth / getBoundingClientRect()`**，浏览器为了给你返回准确的最新宽度，会被迫暂停 JS，**当场同步跑一遍 Layout 重排**！

```js
// ❌ 灾难写法（读写交替 = 强行逼浏览器在循环里重排 100 次！）：
for (let i = 0; i < boxes.length; i++) {
  boxes[i].style.width = (boxes[i].offsetWidth + 10) + 'px'
}

// ✅ 架构师写法（读写分离：先集中读完，再集中写 = 合并为 1 次重排！）：
const widths = boxes.map(b => b.offsetWidth)
boxes.forEach((b, i) => { b.style.width = (widths[i] + 10) + 'px' })
```

## 4. 思考题

1. **为什么 `v-if` 和 `v-show` 在渲染流水线上的成本完全不同？分别在什么场景下选哪个？**
2. **既然提升为独立 GPU 合成层能让动画不掉帧，为什么不能给页面上所有 `* { will-change: transform }` 全開合成层？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **`v-if` vs `v-show` 的流水线账单**：`v-if` 切换时会真实创建/销毁 DOM 子树、挂载组件实例并跑完整条 `Style -> Layout -> Paint`；而 `v-show` 始终保留 DOM 节点，只切换 `display: none`（触发一次 Layout）。因此**频繁来回切换**的面板选 `v-show`；**初始条件大概率为假、且内部组件树极其庞大**的弹窗选 `v-if`（减少首屏 DOM 节点数与初始解析成本）。
2. **防止“层爆炸”撑爆显存**：每一张独立合成层都要在显卡显存（VRAM）里存一张实打实的位图纹理。如果全页几百个元素全开合成层，显存会被瞬间吃光，合成器管理成百上千张胶片的开销反而比直接重绘还慢，在手机上甚至会直接引发浏览器闪退白屏。

</details>
