# 第 16 讲｜数据落盘与分布式：B+ 树、事务、Redis 与 Raft

> **本讲在主线的位置**：第四卷第 3 讲（后端与系统架构底座的巅峰）。一口气串起数据库索引、事务与日志、Redis 缓存双写一致性、以及分布式集群的防脑裂共识。

## 1. 场景与核心问题

在第 02 讲我们知道，内存断电即清零。所以用户的余额和订单必须写进断电不丢的硬盘里。
但硬盘比内存慢上万倍！如果你直接拿 `fs.appendFile` 往硬盘文件里写订单，一旦数据到了 100 万条、并发到了每秒 5,000 次，你会接连撞上四堵墙：
1. **查不动**：查一条订单要从文件第一行扫到第 100 万行；
2. **写不对**：两个人同时抢最后 1 件库存超卖了，或者转账转一半断电钱丢了；
3. **扛不住**：双十一每秒 10 万次读取，硬盘冒烟了也读不过来；
4. **单机挂了全站完蛋**：一台数据库机器硬盘坏了，怎么让多台机器实时备份且绝不产生“双主脑裂”？

这四堵墙，逼出了后端架构的四大金刚：**B+ 树索引、ACID 事务与 WAL、Redis 旁路缓存、Raft 共识集群**。

## 2. 从零推导：从单机磁盘页到多机分布式共识

### 2.1 第一关：为什么内存里用红黑树，到了硬盘数据库里必用 B+ 树？
我们在【02-概念】里用了整整四篇连环画，把这件事从零推到了底（如果你还没读过，强烈建议现在点开看一眼那几张从 0 到 1 的生长慢放图）：
- 👉 **[概念 05：哈希表](../02-概念/05-哈希表与冲突拉链.md)** 虽然单点查只需 1 步，但取余数打乱了顺序，**做不了范围查询（`WHERE age BETWEEN 20 AND 30`）**；
- 👉 **[概念 06：二叉搜索树与旋转](../02-概念/06-二叉搜索树与跷跷板旋转.md)** 与 👉 **[概念 07：2-3 树与红黑树](../02-概念/07-2-3树与红黑树.md)** 在内存里能保持平衡，但因为每个节点只装 1 个数，100 万数据有 20 层高——放到每次必须整页批发 **16KB** 的硬盘上，查一次要读 20 次硬盘，慢哭了！
- 👉 **[概念 08：B 树与 B+ 树](../02-概念/08-B树与B+树.md)** 把上层目录页彻底“脱水”（只印数字 ID 和页码，不存用户档案），**一张 16KB 的目录页能塞 1,170 个路标，仅仅 3 层高就能管住 2,190 万行数据（最多读 3 次硬盘）**！而且所有真实数据沉在最底层的叶子页并用[双向链表](../02-概念/03-单向链表与双向链表.md)手拉手串起来，范围查询顺着底部链表一扫即完！

### 2.2 第二关：怎么保证“并发改不乱、断电绝不丢、写得还能飞快”？（ACID + MVCC + WAL）
详见 👉 **[概念 18：ACID 事务、MVCC 与 WAL 预写日志](../02-概念/18-ACID事务MVCC与WAL预写日志.md)**：
- **防并发读写互卡（MVCC）**：改数据时保留旧版本历史链，普通 `SELECT` 读历史快照，写操作改最新版本，读写互不阻塞；真正并发抢同一行库存时，用 `UPDATE goods SET stock = stock - 1 WHERE id = 1 AND stock > 0`（利用行锁 + 原子条件更新根除超卖！）。
- **防随机写盘太慢（WAL 预写日志）**：提交事务时，只改内存缓冲池里的页，并往硬盘末尾**顺序追加写一行 WAL 日志**就立刻返回成功！把昂贵的随机写盘换成了极速的顺序写盘，断电重启后重放日志（Redo）即可恢复如初。

### 2.3 第三关：Redis 缓存与数据库的“双写一致性”怎么选？
为了挡住 90% 的高频读请求，我们在数据库前面放了一个全内存的 **Redis**（底层正是 [哈希表](../02-概念/05-哈希表与冲突拉链.md) + [LRU 淘汰](../02-概念/09-LRU缓存淘汰算法.md)）。
最经典的 **Cache-Aside（旁路缓存）** 模式在更新数据时，为什么工程界普遍推荐 **“先写数据库，成功后再删除缓存”**，而不是“先删缓存再写库”？

```text
❌ 如果【先删缓存，再写数据库】（极易造成长期脏数据！）：
  线程A(写)：1. 先删掉了缓存 ────────────────────────────► 3. 终于把新值 99 写进数据库
  线程B(读)：      2. 趁A还没写完库，B来读发现缓存空了，
                      去数据库读出旧值 100 并回填进缓存！（完了！缓存里永远锁死了旧值 100！）

✅ 如果【先写数据库，再删除缓存】（推荐！不一致窗口极短）：
  线程A(写)：1. 先把新值 99 提交进数据库 ──► 2. 删掉 Redis 里的旧缓存
  线程B(读)：在此后进来发现缓存空了，去数据库读出最新的 99 回填进缓存！
```

### 2.4 示例代码：25 行实现防“缓存击穿”的互斥单飞锁（Singleflight）
当某一个超高频热点 key（如首页爆款商品）在 Redis 里过期的那一毫秒，如果同时有 10,000 个请求冲进来发现缓存没了，10,000 个请求会同时杀向数据库（**缓存击穿**）！用下面这招 **Singleflight（并发请求合并单飞）**，可以让 10,000 个并发只发 **1 次** 数据库查询，其余 9,999 个直接共享这 1 次的结果（前端请求层防重复发包也完全通用！）：

```js
// singleflight.js —— 无论是前端防重复请求，还是后端防缓存击穿，这 20 行代码都是神器！
const inFlightMap = new Map() // 存放当前正在飞行的 Promise

export async function getHotDataWithSingleflight(key, queryDbFn) {
  // 1. 先查缓存，命中直接返回
  if (cache.has(key)) return cache.get(key)

  // 2. 缓存未命中！看是否已经有另一个并发请求正在查数据库了？有就直接搭它的顺风车！
  if (inFlightMap.has(key)) {
    return inFlightMap.get(key)
  }

  // 3. 我是第一个发现缓存过期的请求：由我独自去查数据库，并把 Promise 挂进 inFlightMap
  const promise = queryDbFn(key).then(val => {
    cache.set(key, val) // 回填缓存
    return val
  }).finally(() => {
    inFlightMap.delete(key) // 查完卸磨杀驴，清理飞行记录
  })

  inFlightMap.set(key, promise)
  return promise
}
```

### 2.5 第四关：多台机器复制与 Raft 多数派防脑裂
当 1 台数据库装不下或怕坏掉时：
- **复制（Replication，一主多从）**：提升读吞吐与容灾备份，并靠 👉 **[概念 20：CAP 定理与 Raft 多数派共识](../02-概念/20-CAP定理与Raft多数派共识.md)**（任期压制 + `Math.floor(N / 2) + 1` 严格过半投票）确保主库宕机自动选新主时，绝对不会出现两个主库同时写数据的“脑裂”！
- **分片（Sharding，分库分表）**：把不同用户的数据按分片键拆到不同机器上分摊写入压力，但会带来跨分片查询与事务难题，因此架构铁律是**“能靠索引、缓存和读写分离解决的，绝不轻易分库分表”**。

## 4. 思考题

1. **为什么建数据库表时，强烈推荐用无业务含义的“自增整数（`AUTO_INCREMENT`）”或趋势递增 ID 作主键，而不推荐用完全随机的 `UUID` 作主键？** 请用 [概念 08：B+ 树底部叶子页分裂](../02-概念/08-B树与B+树.md) 的物理动作回答。
2. **为什么部署 Raft 或 ZooKeeper / etcd 共识集群时，永远推荐买 3 台或 5 台（奇数台）机器，而绝不推荐买 4 台机器？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **自增 ID 顺序追加 vs 随机 UUID 中间页分裂**：B+ 树最底层的叶子数据页是严格按主键大小顺序排列的。用自增主键时，新插入的记录永远比之前所有记录都大，只需在最右边的最后一页末尾**顺序追加**，写满一页再顺势开新页，零搬家；而随机 UUID 每次生成的落点毫无规律，会硬生生往中间已经装满的老叶子页里插队，迫使满页频繁**裂成两半并搬移数据（Page Split 页分裂）**，产生大量随机 I/O 和磁盘碎片！
2. **为什么买 4 台机器是冤大头**：严格过半（Quorum）的计算公式是 `Math.floor(N / 2) + 1`。3 台机器需要 2 票（最多允许挂掉 `3 - 2 = 1` 台）；而 4 台机器需要 `Math.floor(4 / 2) + 1 = 3` 票（最多也只允许挂掉 `4 - 3 = 1` 台，一旦挂 2 台就只剩 2 票，整个集群照样停摆）！也就是说，4 台机器多花了 1 台机器的钱、还增加了网络投票耗时，容灾能力却和 3 台一模一样。

</details>
