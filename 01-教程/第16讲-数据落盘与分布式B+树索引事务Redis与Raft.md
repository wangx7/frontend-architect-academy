# 第 16 讲｜数据落盘与分布式：B+ 树、事务、Redis 与 Raft

> **本讲在主线的位置**：第四卷第 3 讲（全栈与后端系统底座核心）。用我们统一的三层表达法（直观模型 ──► 真实机制 ──► 边界与反例），一口气打通数据库 B+ 树索引与最左前缀、ACID 事务与 MVCC/WAL、Redis 旁路缓存一致性边界，以及分布式复制与 Raft 防脑裂共识。

## 1. 场景与核心问题

在第 02 讲我们知道，内存断电即清零，因此用户的账户余额和订单必须持久化到磁盘数据库中。
但一旦数据规模达到千万行、并发达到每秒数万次，单纯靠写 SQL 调接口就会接连撞上四道工程高墙：
1. **为什么建了索引有时查询还是慢如蜗牛？** B+ 树的 3 层容量是怎么估算的？联合索引 `(city, age)` 在什么查询条件下会失效或退化为全索引扫描？
2. **高并发扣减库存时怎么防止“超卖”？** 数据库怎样利用 MVCC 快照读在许多场景下减少读写互相阻塞，又怎样利用 WAL 支持崩溃恢复？
3. **Redis 与 MySQL 双写时，为什么推荐“先更新数据库，再删除缓存”？** 它在什么极端时序下仍可能产生短暂不一致，该如何兜底？
4. **单机数据库一旦硬盘损坏怎么自动切换？** 主从异步复制会带来哪三种反直觉的读异常？Raft 共识算法除了“过半投票”外，靠什么机制防止日志落后的节点当选把数据冲掉？

## 2. 第一关：B+ 树索引机制、参数化容量估算与联合索引边界

### 2.1 从哈希表、红黑树到 B+ 树的演进闭环
我们在【02-概念】中用四篇连续图解完整推导了这条进化链：
- 👉 **[概念 05：哈希表](../02-概念/05-哈希表与冲突拉链.md)**：等值查询 `O(1)`，但哈希函数打乱了大小顺序，无法直接支持 `WHERE age BETWEEN 20 AND 30`、`ORDER BY created_at` 或 `LIKE 'abc%'` 前缀范围查询；
- 👉 **[概念 06：二叉搜索树与旋转](../02-概念/06-二叉搜索树与跷跷板旋转.md)** 与 👉 **[概念 07：2-3 树与红黑树](../02-概念/07-2-3树与红黑树.md)**：在内存中保证了有序性与平衡性（红黑树高度上界为 `2 log2(N+1)`，1,000 万节点高度约 24～40 层），但因为每个节点只存 1 个键，放到按 `16KB` 整页读写的磁盘上会导致树高过高、未命中缓存时磁盘 I/O 次数过多；
- 👉 **[概念 08：B 树与 B+ 树](../02-概念/08-B树与B+树.md)**：将节点扩建为 `16KB` 页。**B+ 树**进一步令上层非叶目录页**仅存放索引键与子页号指针**（不存完整行记录），从而将单页分支因子（Fan-out）拉满到数百至上千，仅需 **3～4 层** 即可管理千万级行记录，且底层叶子页通过[双向链表](../02-概念/03-单向链表与双向链表.md)串联，天然支持顺序范围扫描！

### 2.2 真实机制与边界：联合索引最左前缀、覆盖索引与 `SEARCH` vs `SCAN`
假设我们在用户表上创建了联合索引 `CREATE INDEX idx_city_age ON users(city, age)`。
B+ 树在排序时，就像电话簿一样：**先按第一列 `city` 排序；只有当 `city` 完全相同时，才按第二列 `age` 从小到大排序**！

```text
联合索引 idx_city_age 叶子页内部的真实排列顺序：
  [ ("北京", 18) ] ──► [ ("北京", 25) ] ──► [ ("北京", 35) ] ──► [ ("上海", 18) ] ──► [ ("上海", 22) ]
        └── 在 "北京" 内部，age 是严格递增的！──┘                   └── 但全局看 age (18->25->35->18) 并不是有序的！──┘
```

这就直接决定了 SQL 查询条件能否利用 B+ 树做 `O(log N)` 二分定位（`SEARCH`）：

| 查询条件 | 能否利用 `idx_city_age` 树二分定位？ | 底层执行机制与架构师排障结论 |
| :--- | :--- | :--- |
| `WHERE city = '北京' AND age = 25` | ✅ **完全使用（双列精确定位）** | 先按 `'北京'` 二分定位，再在 `'北京'` 区间内按 `25` 二分定位。 |
| `WHERE city = '北京' ORDER BY age` | ✅ **最左前缀命中 + 免文件排序** | 命中 `'北京'` 后，由于其内部 `age` 天然有序，直接顺着叶子链表读取即可，无需额外的 `Using filesort`！ |
| `WHERE age = 25`（缺少最左列 `city`） | ❌ **无法二分定位（退化为全表/全索引扫描 `SCAN`）** | 因为全局来看 `age` 是乱序散落在各个城市里的！<br>⚠️ **边界警惕**：如果只查 `SELECT city, age WHERE age = 25`，`EXPLAIN` 可能显示 `Using index`（覆盖索引），但它实际做的是**从头到尾扫一遍整棵索引树（Index Scan）**，而非二分查找（Index Seek）！ |
| `WHERE city > '北京' AND age = 25` | ⚠️ **仅 `city` 列用于范围定位，`age` 无法继续二分** | 范围查询（`>`, `<`, `BETWEEN`）之后的列在不同城市间不再有序，只能顺着链表逐行过滤（MySQL 5.6+ 引入 **ICP 索引条件下推**，在存储引擎层提前过滤 `age=25` 以减少回表次数）。 |

## 3. 第二关：ACID 事务、MVCC 与 WAL 崩溃恢复

详见 👉 **[概念 18：ACID 事务、MVCC 与 WAL 预写日志](../02-概念/18-ACID事务MVCC与WAL预写日志.md)**：
1. **MVCC 怎样在许多场景下减少普通快照读与写之间的阻塞？**：
   每行记录通过隐藏的 `trx_id` 和 `roll_pointer` 指针串联起一条 **Undo Log 历史版本链**。当写事务正在修改某行尚未提交时，并发的普通 `SELECT`（快照读）会根据自身的 `ReadView` 顺着版本链读取符合隔离级别要求的历史版本，从而在许多场景下与写操作并发。锁定读、写写冲突、隔离级别以及具体索引条件仍可能引入等待。
2. **高并发扣库存怎么根除“超卖”？（当前读与原子条件更新）**：
   - ❌ **错误写法（先 `SELECT` 读出 `stock=1`，在 JS/Java 代码里减 1，再发 `UPDATE`）**：两个并发请求在第一步读到的都是 `1`，随后各自写回 `0`，导致 1 件商品卖出了 2 单！
   - ✅ **正确写法（数据库原子条件扣减）**：直接执行 `UPDATE goods SET stock = stock - 1 WHERE id = 101 AND stock > 0`。InnoDB 在执行该语句时会对 `id = 101` 的行加上**排他行锁（X 锁）**，并读取最新已提交值（当前读）校验 `stock > 0`，从存储引擎层防止该类超卖。
3. **提交事务时怎么做到既快又断电不丢？（WAL 预写日志 + Buffer Pool）**：
   事务提交时无需同步把分散在磁盘各处的 `16KB` B+ 树脏页随机刷盘，而是**先修改内存 Buffer Pool，并将修改动作顺序追加写入 Redo Log（WAL）落盘**即返回成功；后台线程再异步将脏页刷回磁盘。

## 4. 第三关：Redis 旁路缓存（Cache-Aside）双写一致性与三大灾防

为了分担数据库读压力，架构上常在 MySQL 前置一层内存 **Redis**。
在最经典的 **Cache-Aside（旁路缓存）** 模式下，当业务数据更新时，应该怎么操作缓存？

### 4.1 为什么是“删除缓存”而不是“更新缓存”？为什么是“先写数据库，再删缓存”？

```text
【反例 A：先删缓存，再写数据库 ──► 高概率引发长期脏数据！】
  请求 A (写)：1. 先删掉 Redis 缓存 ───────────────────────────► 4. 终于把新值 99 写进 MySQL
  请求 B (读)：      2. 趁 A 还没写完库，B 进来发现缓存空了
                     3. B 去 MySQL 读出旧值 100，并回填进 Redis！（完了！Redis 被永久污染成了旧值 100！）

══════════════════════════════════════════════════════════════════════════════════

【推荐方案 B：先写数据库，成功后再删除缓存（Cache-Aside 标准实践）】
  请求 A (写)：1. 先把新值 99 提交进 MySQL ──► 2. 删除 Redis 缓存
  请求 B (读)：此后进来发现缓存未命中，去 MySQL 读出最新的 99 回填进缓存！
```

### 4.2 第三层（边界与反例）：Cache-Aside 在什么极端条件下仍会不一致？如何兜底？
哪怕采用了“先写数据库，再删缓存”，作为架构师你也必须知道它的**两个边界漏洞与工程兜底方案**：
1. **漏洞一（第二步“删缓存”网络抖动失败了怎么办？）**：
   如果 MySQL 更新成功了，但紧接着调 `redis.del(key)` 时网络闪断失败，缓存里就会一直留着旧值！
   - **兜底方案**：① 给所有缓存 Key 设置合理的 **TTL 过期时间**作为最终一致底线；② 引入**消息队列重试**或通过 **Canal / Debezium 监听 MySQL Binlog 变更日志**异步可靠删除缓存。
2. **漏洞二（缓存恰好过期瞬间的并发读写交叉）**：
   读请求 B 进门时缓存恰好自然过期，B 去查库拿到了旧值 `100`（还没来得及回填缓存）；就在这几毫秒内，写请求 A 完成了“更新库为 `99` + 删缓存”；紧接着慢吞吞的 B 把旧值 `100` 写回了缓存。（注：由于读操作通常远快于写事务，该时序发生概率极低；对一致性要求极严苛的场景可配合短期延迟双删或分布式读写锁，但**切忌用缓存承载需要绝对线性一致的金融余额账本**！）。

### 4.3 可独立运行代码：用 `Singleflight（请求合并单飞锁）` 彻底防御“缓存击穿”

当某个超高频热点 Key（如首页秒杀爆款）在 Redis 中过期的那一毫秒，若有 5,000 个并发请求同时发现缓存未命中，全部直接杀向 MySQL 就会瞬间打挂数据库（这叫 **缓存击穿 Hotkey Breakdown**）。
下面这段 **Singleflight（并发请求合并单飞）** 代码既可用于 Node.js BFF/后端防缓存击穿，也可用于前端请求层防止同一接口被多个组件重复并发调用：

```js
// singleflight-cache.mjs —— 直接用 node 运行，验证 100 个并发请求在缓存失效瞬间仅触发 1 次底层查库
const memoryCache = new Map()
const inFlightPromises = new Map() // 记录当前正在飞行中的查询 Promise

export async function getWithSingleflight(key, queryDatabaseFn, ttlMs = 5000) {
  const now = Date.now()
  const cached = memoryCache.get(key)
  if (cached && cached.expireAt > now) {
    return { source: 'cache', data: cached.val }
  }

  // 核心机关：如果已经有另一个并发请求正在查这个 key，直接复用它的 Promise 搭顺风车！
  if (inFlightPromises.has(key)) {
    const sharedData = await inFlightPromises.get(key)
    return { source: 'singleflight-shared', data: sharedData }
  }

  // 我是第一个发现缓存过期的探路者：发起唯一一次查库，并登记到 inFlightPromises
  const dbPromise = (async () => {
    try {
      const freshVal = await queryDatabaseFn(key)
      memoryCache.set(key, { val: freshVal, expireAt: Date.now() + ttlMs })
      return freshVal
    } finally {
      inFlightPromises.delete(key) // 无论成功失败，落地后立即清理飞行锁
    }
  })()

  inFlightPromises.set(key, dbPromise)
  const data = await dbPromise
  return { source: 'db-origin', data }
}

// 压测验证：模拟热点 key 过期瞬间，50 个请求在同一毫秒并发涌入
let dbQueryCount = 0
const mockSlowDbQuery = async key => {
  dbQueryCount++
  await new Promise(r => setTimeout(r, 30))
  return { id: key, title: '爆款耳机', price: 299 }
}

Promise.all(
  Array.from({ length: 50 }, () => getWithSingleflight('hot_item_1', mockSlowDbQuery))
).then(results => {
  const originHits = results.filter(r => r.source === 'db-origin').length
  const sharedHits = results.filter(r => r.source === 'singleflight-shared').length
  console.log(`50 个并发请求结果 -> 实际打到数据库的次数: ${dbQueryCount} (仅 ${originHits} 次探路，${sharedHits} 次搭顺风车共享！)`)
})
```

## 5. 第四关：多机主从复制异常、CAP/PACELC 与 Raft 防脑裂共识

当单台数据库容量或可用性触顶时，架构进入分布式深水区（详见 👉 **[概念 20：CAP 定理与 Raft 多数派共识](../02-概念/20-CAP定理与Raft多数派共识.md)**）：
1. **一主多从异步复制的三大反直觉读异常**：
   如果主库写完立即返回，异步同步给从库（读写分离：写走主库、读走从库），由于主从复制存在几毫秒到几秒的延迟（Replication Lag），前端用户会遇到：
   - **违背“读己之写（Read-Your-Own-Writes）”**：用户刚提交完评论，页面刷新请求落到了还没同步过来的从库，发现自己的评论“消失了”！（**解法**：提交后短时间内对该用户的读请求强制路由到主库，或前端本地乐观合并）；
   - **违背“单调读（Monotonic Reads）”**：用户连续刷新两次页面，第一次落到较新的从库 A 看到了新状态，第二次负载均衡落到滞后的从库 B，画面竟然“时光倒流”回到了旧状态！（**解法**：按用户 ID 哈希固定路由到同一台从库，或读取时携带客户端已知的最大版本号/LSN）。
2. **Raft 共识安全边界**：
   为了在主库宕机时自动选出新主且不发生双主脑裂，Raft 不仅要求 **`Math.floor(N/2) + 1` 严格多数派投票**，还强制执行 **候选人日志新旧度检查（Log Up-to-Date Check）**——任何日志比投票者旧的候选人都会被拒投，确保当选的新 Leader 必定持有全部已提交数据。

## 7. 思考题与架构决策训练

1. **区分“缓存击穿（Breakdown）”、“缓存穿透（Penetration）”与“缓存雪崩（Avalanche）”三者的成因，并给出各自的防线设计。**
2. **为什么部署 Raft（如 etcd、TiKV）或 ZAB（如 ZooKeeper）集群时，生产环境永远推荐买 3 台或 5 台（奇数台）机器，而绝不推荐买 4 台机器？**

<details>
<summary>💡 点击展开本讲思考题参考解析</summary>

1. **三大缓存灾防矩阵**：
   - **缓存击穿（单个热点 Key 过期）**：用上面手写的 **Singleflight 互斥锁合并请求**，或将极热点数据设为逻辑永不过期（后台异步刷新）；
   - **缓存穿透（恶意请求根本不存在的 `id = -999`，缓存和数据库都查不到，每次都穿透打到 DB）**：① 接口层做参数合法性校验；② 对数据库查不到的数据也在 Redis 中缓存一个短期的**空值占位符（`NULL` 缓存 30 秒）**；③ 在网关前放置 **布隆过滤器（Bloom Filter）** 拦截不存在的 ID；
   - **缓存雪崩（同一时间大批量 Key 集中过期，或 Redis 节点宕机）**：① 给批量缓存的过期时间加上**随机抖动值（Jitter，如 `3600s + random(0~300s)`）**打散过期峰值；② 部署 Redis Sentinel / Cluster 高可用集群并配置网关降级熔断。
2. **为什么 4 台机器反而不划算**：严格多数派门槛公式为 `Math.floor(N / 2) + 1`。3 台机器需要 `2` 票（允许挂 `1` 台）；4 台机器需要 `3` 票（同样只允许挂 `1` 台，挂 2 台就只剩 2 票无法达成多数派）。因此 4 台机器并未提升容错台数，反而增加了复制开销与网络投票成本。

</details>
