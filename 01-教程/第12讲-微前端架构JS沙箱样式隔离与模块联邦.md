# 第 12 讲｜微前端架构：JS 沙箱、样式隔离与模块联邦

> **本讲在主线的位置**：第三卷第 4 讲。微前端不是用来炫技的，它是解决**跨团队独立开发、独立发版、巨石遗留系统渐进式重构**的终极手术刀。本讲带你亲手拆开微前端框架（如 qiankun / Garfish / Wujie）最核心的 **JS 沙箱** 与 **CSS 隔离** 黑盒。

## 1. 场景与核心问题

公司有一套跑了 5 年的 Vue 2 老ERP系统（50 万行代码，没人敢重写），现在新业务要用 Vue 3 开发，并且要求用户点击左侧菜单时，老页面和新页面在同一个浏览器标签页里丝滑切换，就像同一个单页应用（SPA）一样。
如果你直接把两个项目的 JS 和 CSS 往同一个 HTML 里一塞，当场就会发生两起车祸：
1. **全局 `window` 污染车祸**：子应用 A 往 `window.user = '张三'` 写了个属性，切到子应用 B 时，B 把 `window.user` 改成了 `'李四'` 或删掉了，切回 A 直接崩溃！
2. **CSS 样式打架车祸**：子应用 A 和子应用 B 都写了一个 `.btn { color: red }` 和 `.modal { z-index: 999 }`，后加载的样式直接把前一个应用的页面冲得面目全非！

怎么把每个子应用关进一个**“既能跑在同一个页面里，又互不污染 `window` 和样式”**的透明隔离舱里？

## 2. 从零推导：手撕微前端三大核心引擎

### 2.1 第一大引擎：JavaScript 隔离沙箱（Proxy Sandbox）
怎么让子应用 A 觉得自己独占了整个 `window`，随便 `window.xxx = 123` 怎么改都不污染真正的全局 `window`，而且多个子应用还能同屏运行？
答案就是利用我们在第 07 讲学过的 **`Proxy` 代理 + 独立虚拟盒子（`fakeWindow`）**！

```text
子应用 A 执行：window.token = "abc"
     │
     ▼ (被 Proxy 沙箱拦截 set！)
写进子应用 A 自己的私有盒子 fakeWindowA { token: "abc" }  ──► 真正的全局 window 干干净净，毫发无损！

子应用 A 执行：window.location.href 或 window.console.log
     │
     ▼ (被 Proxy 沙箱拦截 get！)
先查私有盒子 fakeWindowA 有没有？ ──没有──► 再去真正的全局 window 上读取！
```

### 2.2 示例代码：25 行手写一个支持多应用并行的微前端 `ProxySandbox`
```js
// 25 行复刻 qiankun MultipleProxySandbox（多实例代理沙箱）核心原理！
class ProxySandbox {
  constructor(appName) {
    this.appName = appName
    this.running = false
    const fakeWindow = Object.create(null) // 子应用私有的“假 window 储物格”

    this.proxyWindow = new Proxy(fakeWindow, {
      set: (target, key, val) => {
        if (this.running) target[key] = val // 激活期间，所有修改全写进私有盒子，绝不碰真 window！
        return true
      },
      get: (target, key) => {
        // 优先从私有盒子读；私有盒子没有的原生属性（如 console/document），再去真 globalThis 拿！
        return key in target ? target[key] : globalThis[key]
      }
    })
  }
  active()   { this.running = true }
  inactive() { this.running = false }
}

const appA = new ProxySandbox('订单子应用'); appA.active()
const appB = new ProxySandbox('财务子应用'); appB.active()
appA.proxyWindow.currentUser = '张三'
appB.proxyWindow.currentUser = '李四'
console.log('子应用A:', appA.proxyWindow.currentUser, '| 子应用B:', appB.proxyWindow.currentUser, '| 真全局:', globalThis.currentUser)
// 输出：子应用A: 张三 | 子应用B: 李四 | 真全局: undefined（完美隔离！）
```

### 2.3 第二大引擎：CSS 样式隔离的三种流派与天坑
怎么防止两个子应用的 `.btn` 互相覆盖？工业界有三种方案，各有优劣：

| 隔离方案 | 实现原理 | 核心优点 | 架构师必须知道的“天坑” |
| :--- | :--- | :--- | :--- |
| **1. 动态样式表卸载** | 子应用激活时插入它的 `<link>`，切走时从 DOM 移除 | 零改造成本 | **不支持两个子应用同屏同时显示** |
| **2. 运行时 Scoped CSS 改写** | 微前端框架把子应用的所有 CSS 选择器自动加上前缀，如 `.btn` 改成 `div[data-qiankun="appA"] .btn` | 支持多应用同屏 | **弹窗（Modal/Tooltip）挂载到 `document.body` 时跳出了 `div[data-qiankun="appA"]` 容器，导致弹窗样式全部丢失！** |
| **3. Shadow DOM（Web Components 硬件级隔离）** | 将子应用挂载在原生 `attachShadow({ mode: 'open' })` 影子根节点内（如无界 Wujie） | 浏览器引擎级绝对样式隔离，内外完全不串味 | 越界挂载到外层 `body` 的弹窗事件与顶层坐标计算需框架劫持修正 |

### 2.4 第三大引擎：模块联邦（Module Federation）—— 跨项目运行时直接借用组件
如果 5 个独立仓库的子应用都想共用同一套最新的头部导航组件或公共工具库，传统发 npm 包每次修改都要让 5 个项目重新安装、重新打包发版。
Webpack 5 / Vite 的 **Module Federation（模块联邦）** 允许应用 A 在构建时生成一个远程清单 `remoteEntry.js`；应用 B 在浏览器运行时直接通过网络动态 import 应用 A 的组件，且自动共用内存中已加载的同一份 Vue/React 实例！

### 2.5 架构师铁律：什么时候绝对不要上微前端？
**微前端是“组织架构问题”的解药，不是技术升级的玩具。** 如果你们团队只有 5 个人、维护 1 个同技术栈项目，用 Monorepo（`pnpm workspace`）就够了；强行上微前端只会平白增加沙箱性能损耗、弹窗越界 bug 与跨应用通信复杂度。

## 4. 思考题

1. **在上面的 `ProxySandbox` 中，如果子应用在运行期间调用了 `window.addEventListener('resize', fn)` 或 `setInterval`，当子应用切换卸载（`inactive`）时，仅仅把 `running` 设为 `false` 够不够？还会漏掉什么？**
2. **为什么很多微前端项目打开弹窗（如 Element Plus 的 `ElDialog` 加了 `append-to-body`）时，弹窗的样式会突然消失？该怎么解决？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **副作用清理（Side-effect Cleanup）**：仅仅关闭 `running` 开关只拦住了后续对 `window` 属性的赋值，但子应用在运行期间向全局注册的 `window.addEventListener` 监听器、以及未清除的 `setInterval / setTimeout` 依然在后台继续存活运行（既造成内存泄漏，又会在其他子应用里乱报错）！因此完整的微前端沙箱还必须劫持 `addEventListener` 和 `setInterval`，记录下该子应用登记的所有事件和定时器 ID，在 `inactive()` 卸载时自动帮它全部执行 `removeEventListener` 和 `clearInterval`。
2. **弹窗跳出容器导致 Scoped 前缀失效**：运行时样式隔离把子应用的样式改写成了 `[data-app="subA"] .el-dialog { ... }`。一旦弹窗开启了 `append-to-body`（或 Vue 3 `<Teleport to="body">`），弹窗 DOM 被直接挂到了最外层的 `<body>` 底下，不再是 `[data-app="subA"]` 的子孙节点，选择器匹配失败！解法：将弹窗挂载点统一指向子应用自己的根容器，或由微前端框架劫持 `document.body.appendChild` 自动补齐属性标记。

</details>
