# 第 02 讲｜变量和数据住在哪个格子里？

> **本讲在主线的位置**：理解了程序在 CPU 上跑之后，必须搞清楚数据是怎么在内存里安家的。搞懂了**栈（Stack）与堆（Heap）**，你就同时看懂了 JS 引用传递、爆栈报错、闭包内存与垃圾回收。

## 1. 场景与核心问题

看下面这段你每天都在写的代码：

```js
function handleOrder(orderId) {
  const taxRate = 0.1
  const order = { id: orderId, total: 100 }
  return order
}
```

如果我问你：`taxRate` 和 `order` 在内存里的物理住址有什么区别？为什么 `handleOrder` 执行完后，`taxRate` 当场消失了，而 `order` 还能活着交出去？
要回答这个问题，必须看懂内存里的两大社区：**栈区（Stack）** 与 **堆区（Heap）**。

## 2. 从零推导：栈帧盘子 vs 堆区大房间

### 2.1 栈区（Stack）：专门服务“函数调用”的叠盘子区
观察函数调用的顺序：`main()` 调 `A()`，`A()` 调 `B()`——必须 `B()` 先算完退场，才轮到 `A()` 继续，最后回到 `main()`。
这种**“后进先出”**的顺序，天生就该用 👉 **[概念 04：栈与队列（叠盘子）](../02-概念/04-栈与队列.md)** 来管理！

- 每调用一个函数，就在栈顶压入一个**栈帧（Stack Frame）**，里面装着函数的参数和简单局部变量（如 `taxRate = 0.1`）；
- 函数一 `return`，栈帧直接弹出销毁，里面的局部变量瞬间清零回收，快如闪电！
- **栈的软肋**：空间很小（通常只有几 MB）。如果你写了个没有终止条件的无限递归函数，栈帧盘子一直往上叠，几毫秒就会撞上天花板，报出你最眼熟的错误：`RangeError: Maximum call stack size exceeded`（爆栈）。

### 2.2 堆区（Heap）：专门安置“大块头、活得久”的对象
像 `order = { id: 101, total: 100 }` 这样的对象，体积可能随时变大，而且函数结束后外面还要继续用它，绝对不能随着函数栈帧一起被销毁！
于是引擎采用了 👉 **[概念 01：内存门牌号与指针引用](../02-概念/01-内存门牌号与指针引用.md)** 的分家方案：

```text
         【栈区 Stack（紧凑、随函数自动弹栈销毁）】
    ┌──────────────────────────────────────────────────┐
    │ handleOrder 的栈帧：                             │
    │   #101 (taxRate) ： [ 0.1 ]        (直接存数字)  │
    │   #102 (order)   ： [ 纸条 #500 ]  (只存门牌号!) │
    └───────────────────────────┬──────────────────────┘
                                │ 顺着门牌号 #500 找过去
                                ▼
         【堆区 Heap（宽敞、由垃圾回收器 GC 负责巡逻回收）】
    ┌──────────────────────────────────────────────────┐
    │ 门牌号 #500 房间 ： { id: 101, total: 100 }      │
    └──────────────────────────────────────────────────┘
```

### 2.3 示例代码：一眼看穿值拷贝与门牌号拷贝
```js
let a = 100
let b = a
b = 200
console.log(a) // 100 —— 栈格子直接存数字，改 b 不影响 a

let obj1 = { count: 1 } // 对象住在堆 #500，obj1 格子里存着纸条 "#500"
let obj2 = obj1         // 把纸条 "#500" 复印一份给 obj2（两人指向同一个 #500 房间！）
obj2.count = 99         // 顺着 #500 纸条进房间改家具
console.log(obj1.count) // 99 —— 因为看的是同一个 #500 房间！
```

### 2.4 堆里的房间用完了谁来收？（垃圾回收 GC）
栈帧随函数结束自动弹出，那堆里的 `#500` 房间什么时候回收？
JavaScript 和 Java/Go 都采用 **标记清除（Mark-and-Sweep）垃圾回收器**（详见 👉 **[概念 11：闭包背包 Context 与垃圾回收 GC](../02-概念/11-闭包背包Context与垃圾回收GC.md)**）：
> **GC 的核心不是“找垃圾”，而是“找还活着的”**——定期从全局根（`window` / `global`）和当前调用栈里的门牌号纸条出发顺藤摸瓜；凡是还能顺着纸条摸到的堆房间就保留，摸不到的孤岛房间全部清空回收！

因此，前端所谓的**内存泄漏**，99% 都是因为你以为某个大对象没用了，但全局变量、未解绑的事件监听或定时器里还留着一张指向它的门牌号纸条，导致 GC 不敢收它！

## 3. 前后端架构双视角映射

| 内存机制 | 前端架构中的投影 | 后端与系统架构中的投影 |
| :--- | :--- | :--- |
| **栈与堆分治** | 递归组件未写终止条件引发 `Maximum call stack size exceeded`；大对象浅拷贝只复制顶层门牌号，深拷贝需 `structuredClone` | JVM 堆栈调优（`-Xms / -Xmx` 调堆大小，`-Xss` 调线程栈大小）；Rust 在编译期用所有权规则自动回收堆内存 |
| **GC 泄漏治理** | Chrome DevTools `Memory` 面板拍堆快照（Heap Snapshot），顺着 `Retainers`（持有者引用链）定位是谁拽住了死组件的门牌号 | Node.js / Java 生产环境监控老年代堆内存锯齿曲线，若只升不降则导出 Heapdump 排查全局 Map 缓存未淘汰问题 |

## 5. 思考题

1. **为什么栈溢出（无限递归）被设计成“主动报错停机”，而不是放任栈无限往下生长？**
2. **如果执行 `let o1 = { x: 1 }; let o2 = o1; o2 = { x: 2 };`，此时 `o1.x` 是 `1` 还是 `2`？为什么？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **防止踩坏其他内存区与栈溢出攻击**：在进程的一维内存长线上，栈和堆是分区居住的，而且每个栈帧里都存着极其关键的“函数返回地址”。如果不设护栏放任无限递归压栈，栈帧就会越界踩坏堆区数据，甚至被黑客利用来覆盖返回地址、劫持程序跳转到恶意代码（经典的缓冲区/栈溢出攻击）。
2. **`o1.x` 依然是 `1`**：因为 `o2 = { x: 2 }` 不是顺着旧纸条 `#500` 去改房间内容，而是去堆里新开了一个 `#600` 房间放 `{ x: 2 }`，再把 `o2` 自己的栈格子里存的纸条换成了 `#600`。`o1` 手里攥着的依然是 `#500` 纸条，`#500` 房间从未被修改过。

</details>
