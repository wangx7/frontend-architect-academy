# 第 14 讲｜一次请求出门：DNS、TCP、TLS 与 HTTP 演进

> **本讲在主线的位置**：第四卷（网络、数据库与分布式底座）第 1 讲。打开 Chrome DevTools 的 Network 瀑布图，把每一个彩色进度条（`DNS Lookup → Initial Connection → SSL → Waiting TTFB`）背后的物理来回彻底算清楚。

## 1. 场景与核心问题

你在前端写了一行 `await fetch('https://api.example.com/orders')`。
这行代码从离开你的浏览器，到穿过海底光缆到达几千公里外的服务器，中间到底套了几层“信封”？为什么冷启动发第一个 HTTPS 请求要多花好几百毫秒？为什么状态码 `304` 响应体是空的却能让页面秒开？为什么 HTTP 从 1.1 升级到 2 之后，到了 HTTP/3 连底层的 TCP 都换成了 UDP（QUIC）？

## 2. 从零推导：四层信封与三次协议大换代

### 2.1 为什么要分层？—— 四层信封各司其职
两台相隔千里的电脑只靠光纤里的光脉冲对话。为了不把所有难题揉成一团乱麻，网络协议像寄快递套信封一样分成了四层：

```text
┌─ 1. 链路层信封（MAC 地址）：只管“当前这一段网线/WiFi 下一站交给哪块网卡”（每过一个路由器换一次信封）
│  ┌─ 2. 网络层信封（IP 地址）：管“全球最终收货地址”（路由器看目的 IP 查表指路，尽力送达但不包丢包）
│  │  ┌─ 3. 传输层信封（TCP / QUIC 端口）：管“把货物交给这台机器上的哪个进程”，并保证不丢不乱序！
│  │  │  ┌─ 4. 应用层正文（HTTP + TLS）：加密后的业务对话（GET /orders HTTP/2）
```

### 2.2 算出架构师必懂的账：一个冷启动 HTTPS 请求要花几个来回（RTT）？
在真正发出 `GET /orders` 之前，浏览器如果在本地没有命中强缓存，必须先打通三条隧道：
1. **第 1 个来回（DNS 查门牌号）**：人记域名 `api.example.com`，机器只认 IP `93.184.216.34`。浏览器先问 DNS 服务器拿到 IP（若本机有缓存则 0 RTT）；
2. **第 2 个来回（TCP 三次握手）**：建立可靠字节流管道，确认双方收发正常并对齐初始序号（详见 👉 **[概念 16：TCP 三次握手与队头阻塞](../02-概念/16-TCP三次握手与队头阻塞.md)**）；
3. **第 3 个来回（TLS 1.3 加密握手）**：通过 ECDHE 调色盘算法隔空算出相同的对称密钥，并用 CA 数字证书验明服务器正身（详见 👉 **[概念 17：TLS 1.3 握手与数字证书信任链](../02-概念/17-TLS握手与数字证书信任链.md)**）；
4. **第 4 个来回（HTTP 请求与响应）**：发出加密后的 HTTP 请求，拿到第一批响应字节（TTFB）。

**结论**：一次冷启动请求，光是路上来回打招呼就要花掉 **3～4 个 RTT**！如果用户在弱网环境（1 个 RTT = 100ms），光是握手就要耗掉 **300～400ms**！
这就解释了为什么性能优化的头号杠杆永远是：**① 用强缓存彻底省掉网络请求；② 用长连接与多路复用省掉重复握手！**

### 2.3 HTTP 两级缓存：强缓存（零请求）vs 协商缓存（304 空响应）
```text
浏览器要请求 app.a1b2.js 或 index.html
   │
   ▼
【第 1 级：强缓存检查 (Cache-Control: max-age=31536000, immutable)】
   ├─ 还没过期！ ──► 直接从本地磁盘/内存拿副本！（0 网络请求，0 RTT，最快！）
   │
   ▼ 过期了，或者配了 Cache-Control: no-cache（注意：no-cache 意思是“每次用前必须问一下服务器”！）
【第 2 级：协商缓存验证 (带上上次服务器给的指纹 If-None-Match: "v1-hash")】
   ├─ 服务器比对指纹发现文件没变 ──► 返回 【304 Not Modified】（响应体为空！省掉 99% 下载带宽！）
   └─ 服务器发现文件变了         ──► 返回 【200 OK】 + 最新文件内容 + 新 ETag 指纹
```

### 2.4 示例代码：15 行 Node 代码亲手造一个支持 `ETag + 304` 的 HTTP 服务器
```js
import http from 'node:http'

const content = '<h1>前端架构师学院</h1>'
const etag = '"v1-fingerprint-888"' // 资源内容的唯一指纹

http.createServer((req, res) => {
  // 如果浏览器带来的 If-None-Match 指纹和当前内容指纹一致：直接回 304 空包！
  if (req.headers['if-none-match'] === etag) {
    res.writeHead(304)
    return res.end() // 绝不重复发送正文！
  }
  res.writeHead(200, {
    'Content-Type': 'text/html; charset=utf-8',
    'Cache-Control': 'no-cache', // 允许缓存，但每次复用前请拿 ETag 来核对
    'ETag': etag
  })
  res.end(content)
}).listen(3000)
```

### 2.5 HTTP/1.1 → HTTP/2 → HTTP/3（QUIC）演进一张表看透

| 版本 | 解决了上一代的什么痛点？ | 留下了什么新窟窿？ |
| :--- | :--- | :--- |
| **HTTP/1.1** | 默认开启长连接（`keep-alive`），不用每发一个请求都重新握手 | 同一个连接上必须“前一个响应回来，后一个请求才准发”（HTTP 队头阻塞），浏览器被迫对同域名开 6 个并发连接 |
| **HTTP/2** | **二进制分帧 + 多路复用**：同域名只需 **1 条 TCP 连接**，几十个请求切成小帧交错并发传输，外加头部压缩（HPACK） | 治好了 HTTP 层的排队，但底层的 **TCP 只认一条连续字节流**——只要丢了 1 个包，所有并发流全部被内核扣留卡住（👉 [概念 16：TCP 队头阻塞](../02-概念/16-TCP三次握手与队头阻塞.md)） |
| **HTTP/3** | 抛弃 TCP，改在 UDP 上实现 **QUIC**：把重传和排序缩小到每个独立流（Stream）内部，**彻底消灭跨流队头阻塞**，且切换 WiFi/5G 时连接不断（连接迁移） | 需要服务端与边缘 CDN 开启 UDP 443 端口支持 |

## 4. 思考题

1. **为什么 `Cache-Control: no-cache` 的真实意思不是“不缓存”，而是“走协商缓存”？真正禁止存任何副本的指令叫什么？**
2. **为什么前端接口超时报错（比如 Axios 5 秒超时断开）时，绝对不能简单认为“后端那笔订单肯定没创建成功”并直接无脑自动重发 `POST`？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **`no-cache` vs `no-store`**：`no-cache` 的规范含义是“切勿在未向源服务器验证新鲜度的情况下直接使用本地缓存”——即浏览器仍然会把响应存下来，只是下次用之前必须发 `If-None-Match` 走 304 协商验证（最适合 `index.html`）；而 `no-store` 才是“严禁任何浏览器和代理保存该响应的任何字节”（适合银行账单等机密响应）。
2. **超时 = 状态未知**：前端超时可能发生在请求已经到达服务器、数据库事务已经提交成功，只是响应在回程路上慢了或丢了。如果此时对非幂等的 `POST /createOrder` 无脑自动重试，就会给用户下两笔重复订单、扣两次钱！重试前必须确保接口携带了客户端生成的唯一幂等键（`Idempotency-Key`）。

</details>
