# 第 08 讲｜React Fiber 架构与双框架设计权衡

> **本讲在主线的位置**：第二卷收官之作。一个真正的前端架构师绝不会陷入“Vue 和 React 谁更好”的口水战，而是能从底层数据结构一眼看穿：**这两大框架分别押注了哪条技术路线，各自牺牲了什么、换来了什么。**

## 1. 场景与核心问题

在第 07 讲里我们看到，Vue 3 靠 **“Proxy 细粒度追踪（精确知道哪个组件变了）+ 模板编译优化（精确知道哪个标签变了）”**，让每次更新的工作量变得极小。
那问题来了：**为什么 React 不直接用 Proxy，反而每次调用 `setState` 默认都会把当前组件及其所有子孙组件重新执行一遍？为了解决整树重跑太慢的问题，React 为什么还要大费周章把虚拟 DOM 树改造成“Fiber 链表”？**

## 2. 从零推导：两条截然不同的哲学路线

### 2.1 根源分歧：模板（Template）vs 纯 JavaScript（JSX）
- **Vue 选择了“受约束的模板（Template）”**：因为 `<template>` 的语法是固定的，编译器很容易在打包时静态分析出谁是静态节点、谁是动态节点（画出 `Block Tree`）；运行时再配合 `Proxy` 可变状态直接定位到具体组件。
- **React 选择了“完全自由的纯 JS 函数（JSX）”**：在 React 眼里，`UI = f(state)`。JSX 里你可以随便写 `if/else`、`map`、把变量赋来赋去。**极致的灵活性带来了一个必然代价：编译器很难单靠静态分析猜出你下次渲染哪块会变；而且 React 坚持不可变数据（Immutable Snapshot），不用 Proxy 监听对象属性**。
  结果就是：一旦调了 `setState`，React 不知道具体哪个小角落变了，只能从当前组件开始，把底下整棵子树的函数重新跑一遍做比对（Reconciliation）！

### 2.2 React 15 的噩梦：同步递归大树把主线程卡死！
如果这棵组件树有 2,000 个节点，像普通树一样用**递归**（依赖我们在 [第 02 讲](./第02讲-变量和数据住在哪个格子里.md) 学过的函数调用栈）一口气比对完，可能要花 **100 毫秒**。
还记得 [第 05 讲](./第05讲-JS单线程与事件循环调度.md) 的铁律吗？**只要调用栈里的递归没退出来，主线程就被死死卡住 100 毫秒，用户此时在输入框打字、点按钮全部卡顿掉帧！**
而且函数调用栈有一个致命死穴：**一旦开始递归，中途绝对没法暂停让出主线程、等下一帧再接着跑**（因为你一 `return`，栈帧就销毁了，进度全丢了）！

### 2.3 React Fiber 的破局：把“递归树”改造成“带三张纸条的链表”！
怎么才能做到**“比对 5 毫秒 → 暂停！把主线程让给浏览器画画面和响应打字 → 下一帧从刚才停下的那个节点继续往下比对”**？
React 团队用我们在 👉 **[概念 03：单向链表与双向链表](../02-概念/03-单向链表与双向链表.md)** 学过的门牌号纸条，把原本靠函数递归遍历的树，改造成了 **Fiber 链表节点**：
每个 Fiber 节点身上揣着**三张门牌号纸条**：
1. **`child` 纸条**：指向我的大儿子；
2. **`sibling` 纸条**：指向我的亲弟弟（下一个兄弟节点）；
3. **`return` 纸条**：指向我的老父亲！

```text
          App (Fiber #100)
         │   ▲
  (child)│   │(return 纸条指回父亲)
         ▼   │
        Header (#201) ──(sibling 纸条指向弟弟)──► List (#202) ──(return 指回 App #100)
```

有了 `child / sibling / return` 这三张纸条，遍历整棵树**再也不需要函数递归调用栈了**，只需要一个最简单的 `while` 循环和一个指向当前节点的全局变量 `workInProgress`！

### 2.4 示例代码：20 行复刻 React Fiber 可随时暂停与恢复的并发循环
```js
// 20 行看穿 React Fiber 时间切片（Concurrent Mode）的全部核心机密！
let workInProgress = rootFiber // 全局指针：记住当前干活干到哪个门牌号了！

function workLoop(deadline) {
  // 只要还有节点没比对完，且当前帧还没超时（比如还有剩余时间），就接着干活
  while (workInProgress !== null && deadline.timeRemaining() > 1) {
    workInProgress = performUnitOfWork(workInProgress)
  }
  // 如果因为时间片用完了跳出循环，但活还没干完：把接力棒挂到下一帧继续跑！
  if (workInProgress !== null) {
    requestIdleCallback(workLoop) // (React 源码内部用 MessageChannel 模拟实现了更高精度的调度)
  }
}

function performUnitOfWork(fiber) {
  console.log('正在比对节点:', fiber.name)
  // 按深度优先顺序，顺着三张纸条找下一个要处理的节点：有大儿子走大儿子 -> 没儿子走亲弟弟 -> 没弟弟顺着 return 回叔叔！
  if (fiber.child) return fiber.child
  let next = fiber
  while (next) {
    if (next.sibling) return next.sibling
    next = next.return
  }
  return null
}
```
*(补充：为了防止比对到一半暂停时，用户看到画了一半的残缺 DOM，React 在内存里维护了**两棵 Fiber 树（双缓冲 Double Buffering）**：在后台默默拼好新树 `workInProgress`，全部算完后再一口气在 Commit 阶段同步更新真实 DOM！)*

## 3. 架构师终极视野：Vue 3 vs React 核心架构权衡表

| 对比维度 | Vue 3 路线（精确制导导弹） | React 路线（时间切片并发引擎） |
| :--- | :--- | :--- |
| **核心哲学** | **“从源头减少不必要的工作”**：既然知道谁变了，就别去烦别人 | **“既然重跑不可避免，就让重跑可中断、可插队”** |
| **状态感知** | `Proxy` + [`WeakMap->Map->Set`](../02-概念/12-WeakMap与响应式依赖图.md) 运行时自动细粒度依赖追踪 | 显式调用 `setState`，依靠不可变数据引用比对（`Object.is`）与 `useMemo` |
| **编译与运行时分工** | 重度依赖模板编译期分析（`PatchFlags` + `Block Tree` 靶向更新），运行时负担极轻 | JSX 极其灵活，主要靠运行时 Fiber 链表双缓冲 + Lane 优先级时间切片（近年推出 React Compiler 补齐自动记忆化） |
| **心智负担对比** | 心智直觉自然（直接改 `.value`），但需注意解构丢失响应性等代理边界 | 纯函数快照心智统一，但需开发者关注闭包陈旧值与 `useMemo/useCallback` 优化 |

## 5. 思考题

1. **为什么 React Hooks（如 `useState`）严禁写在 `if (condition)` 条件判断或 `for` 循环里，必须写在组件顶层？** 请用我们在[概念 03](../02-概念/03-单向链表与双向链表.md) 学过的“单向链表按顺序领号”推出来。
2. **为什么 Vue 3 不需要像 React 那样搞一套复杂的 Fiber 链表和时间切片？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **React Hooks 的底层就是一个单向链表**：函数组件每次重渲染都会从头重新执行。React 在当前组件的 Fiber 节点上挂了一条**单向链表（`memoizedState`）**来按顺序存放第 1 个 Hook、第 2 个 Hook、第 3 个 Hook 的状态，而没有名字 key。如果你把第 2 个 `useState` 写进了 `if (show)` 里，当 `show` 变为 `false` 时，原本排在第 3 位的 `useState` 就会错位去领第 2 号链表节点的数据，导致整条链表的状态全部串位崩溃！
2. **为什么 Vue 3 不需要 Fiber**：因为 React 默认不知道哪个子组件变了，一次更新可能牵连整棵大树重跑（耗时长，所以必须切片防卡顿）；而 Vue 3 通过 `Proxy` 组件级精准订阅 + 编译期 `Block Tree` 动态节点直达，已经把单次更新的范围压缩到了极小的局部，同步毫秒级就能跑完，引入 Fiber 反而会增加额外的链表维护与内存开销。

</details>
