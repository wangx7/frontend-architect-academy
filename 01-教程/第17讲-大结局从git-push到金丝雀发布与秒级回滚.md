# 第 17 讲｜大结局：从 git push 到金丝雀发布与秒级回滚

> **本讲在主线的位置**：全套 17 讲大结局。把构建产物、CI/CD 门禁、CDN 缓存配合、金丝雀灰度与前后端兼容回滚串成最后一道架构闭环，并为你绘制一张贯穿前后端的终极架构全景图。

## 1. 场景与核心问题

周五下午 5 点，你修完了一个紧急需求，满怀信心地敲下 `git push origin main`。
流水线显示绿灯部署成功！但 3 分钟后，客服群炸了：一大批正在使用系统的老用户反馈点击菜单页面直接白屏，控制台一片血红：`ChunkLoadError: Loading chunk OrderPage.a81f2c.js failed (404 Not Found)`！
你明明只是发了个新版本，新用户打开也完全正常，**为什么偏偏把在线的老用户搞白屏了？如果此时发现新版本有个严重 Bug 需要回滚，为什么回滚代码只需 3 秒，而回滚数据库却可能引发灾难？**

## 2. 从零推导：发布不是“复制覆盖”，而是一场“多版本共存协议”

### 2.1 破案发版白屏：为什么绝对不能“一发新版本就清空旧 `assets/` 目录”？
看看发版那一秒，线上同时存在着两拨处于不同时空的用户：
- **旧版本构建产物**：`index.html` 引用着 `OrderPage.a81f2c.js`；
- **新版本构建产物**：因为你改了订单页代码，文件名内容指纹变成了 `OrderPage.f93b11.js`。

如果你的部署脚本干了一件蠢事——**先把旧目录清空（`rm -rf dist/*`），再把新文件传上去**：
1. 那些上午就已经打开了网页、一直停留在首页没刷新的老用户，手里内存里跑的还是**旧版路由表**；
2. 当他在下午 5 点 01 分点击“我的订单”菜单时，浏览器按旧路由表去请求 `OrderPage.a81f2c.js`；
3. 服务器说：“旧文件刚被发布脚本删光了，404！”——老用户当场白屏！

**架构师的安全静态发布五步铁律**：
```text
第 1 步：把新版本的带 hash 静态资源（JS/CSS/图）【增量上传】到对象存储 / CDN（保留旧版本文件不删！）
   │
   ▼
第 2 步：验证新静态资源在 CDN 上已可正常访问（200 OK）
   │
   ▼
第 3 步：最后一步才切换入口 `index.html`（HTML 配置 Cache-Control: no-cache，让新访问立刻拿到新清单）
   │
   ▼
第 4 步：金丝雀灰度放量（先切 5% 流量观察错误率与 P99 延迟，正常再扩到 100%）
   │
   ▼
第 5 步：旧版本的 hash 静态资源至少保留 7~30 天兼容窗口，过完窗口期再自动归档清理！
```

### 2.2 为什么回滚必须基于“不可变制品（Immutable Artifact）”，而不是重新跑一次 `pnpm build`？
如果线上出了故障要紧急回滚到上一版 v1.0.0：
- **错误做法**：切回 v1.0.0 的 Git 分支，重新跑一遍 `pnpm install && pnpm build`（既要等好几分钟，而且万一环境或某个未锁死的小依赖变了，打出来的包跟上次根本不一样！）。
- **正确做法（制品归档与指针秒切）**：每次 CI 构建产出的 `dist` 压缩包或 Docker 镜像都按版本号永久归档；回滚时**一秒钟都不需要重新编译，直接把网关/Nginx 软链接或 K8s Deployment 镜像标签切回 `v1.0.0`**，3 秒内完成止损！

### 2.3 前后端与数据库兼容窗口：扩展—迁移—收缩（Expand-Migrate-Contract）
如果新版本要把后端接口字段 `amount` 改名为 `totalPrice`，或者修改数据库列：
**严禁“删旧字段”和“上新代码”在同一秒发生！** 必须分三步走：
1. **扩展（Expand）**：后端先同时返回 `{ amount: 100, totalPrice: 100 }` 新旧两个字段（此时新旧前端都能跑，随时可无损回滚！）；
2. **迁移（Migrate）**：前端发布新版本，改读 `totalPrice`；
3. **收缩（Contract）**：等过完一周兼容期，确认线上再也没有任何旧版前端请求 `amount` 且不再需要回滚后，后端再安全删除 `amount` 字段。

### 2.4 示例代码：一份可直接用于生产的“不可变构建 + 多版本保留”GitHub Actions 流水线
```yaml
name: Production Release Pipeline
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: 'pnpm' }

      # 1. 严格按 pnpm-lock.yaml 安装，若锁文件不匹配直接红灯拦截！
      - run: pnpm install --frozen-lockfile
      # 2. 质量门禁：类型检查与生产构建
      - run: pnpm run build
      # 3. 归档本次不可变构建制品（以 Git Commit SHA 唯一命名，随时可秒级回滚！）
      - uses: actions/upload-artifact@v4
        with:
          name: dist-${{ github.sha }}
          path: .vitepress/dist
```

1. **防止无限刷新死循环与丢失用户输入**：如果因为服务端配置错误导致新版本的 chunk 也是 404，无脑 `location.reload()` 会让页面陷入“刷新 → 404 → 再刷新 → 再 404”的死循环！正确做法是：① 服务端发布时保留旧版本 hash 资源从根源消灭 404；② 前端在路由 `onError` 捕获到 `ChunkLoadError` 时，先在 `sessionStorage` 里检查当前目标路径是否已经自动刷新重试过一次，只允许携带时间戳自动刷新重试 1 次，若仍失败则展示友好的“发现新版本，请保存草稿后点击刷新”提示条。
