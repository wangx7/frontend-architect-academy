# 第 07 讲｜Vue 响应式、编译优化与快速 Diff

> **本讲在主线的位置**：第二卷第 4 讲（前端框架内核重头戏）。把你在前六讲学到的所有积木（**Proxy 拦截、`WeakMap -> Map -> Set` 哈希集合、微任务队列、AST 编译、最长递增子序列 LIS**）组装成一台精密运转的 Vue 3 引擎。

## 1. 场景与核心问题

当你写下 `count.value++` 时，页面上的数字自动变了。
但作为一个前端架构师，你必须能回答这四个连环追问：
1. **谁在听？** Vue 怎么知道页面上 500 个组件里，偏偏只有这 1 个组件用到了 `count`？
2. **怎么不重算？** 如果我在一个函数里连续改了 10 次 `count.value++`，为什么组件只重新渲染 1 次而不是 10 次？
3. **怎么跳过静态标签？** 组件里有 99 个写死的静态 `<div>` 和 1 个动态 `{{ count }}`，Vue 3 怎么做到不遍历那 99 个静态节点？
4. **列表乱序怎么少搬家？** `v-for` 列表顺序变了，Vue 3 是怎么算出最少 DOM 移动次数的？

## 2. 从零推导：一条完整的 Vue 3 更新流水线

```text
state.count++ (触发 Proxy setter)
   │
   ▼
【第 1 关：精准寻人 (Trigger)】 查 WeakMap -> Map -> Set 三层通讯录，找出订阅了 count 的组件 effect
   │
   ▼
【第 2 关：异步批处理 (Scheduler)】 用 Set 去重排队，借第 05 讲的 Promise 微任务在当前同步代码跑完后只刷 1 次！
   │
   ▼
【第 3 关：靶向比对 (Block Tree)】 编译器提前给动态节点贴好 PatchFlags 并收进 dynamicChildren 数组，直接跳过静态树！
   │
   ▼
【第 4 关：快速 Diff (LIS)】 若遇 v-for 列表重排，先掐头去尾，中间乱序区间用【最长递增子序列 LIS】算出最少 DOM 移动！
```

### 2.1 第一关：Proxy 拦截与三层通讯录（加上“分支依赖清理”）
Vue 3 用 `new Proxy` 拦截对象的读取（`get`）和修改（`set`），并把依赖关系存进 👉 **[概念 12：WeakMap 与响应式依赖图](../02-概念/12-WeakMap与响应式依赖图.md)**（内含 👉 **[概念 05：哈希表 Map](../02-概念/05-哈希表与冲突拉链.md)**）。
这里有一个生产级必考细节——**分支切换时的旧依赖清理**：
```js
watchEffect(() => {
  // 当 showName 从 true 变成 false 后，下次重跑不再读取 user.name！
  // 每次重跑前必须先把当前 effect 从上一轮订阅的所有 Set 集合里删掉，重新收集本轮真正读到的属性！
  console.log(state.showName ? state.name : '已隐藏')
})
```

### 2.2 第二关：为什么需要 `Scheduler` 调度器与 `nextTick`？
如果每次 `state.count++` 都当场同步去改真实 DOM，连续改 10 次就要跑 10 次重排！
Vue 3 的解法是：**数据在内存格子里当场改，但组件的重新渲染任务（Job）先塞进一个 `Set` 队列去重，然后用 `Promise.resolve().then(flushJobs)` 挂到微任务阶段统一执行 1 次！**
这就是为什么你同步改完 `count.value++` 立刻读 `dom.textContent` 读到的是旧值，必须 `await nextTick()`（等那轮微任务刷新完）才能读到新 DOM！

### 2.3 第三关：编译期优化（Static Hoisting + PatchFlags + Block Tree）
传统虚拟 DOM 最大的毛病是“不管三七二十一，每次更新都把整棵组件 VNode 树从头到尾比对一遍”。
Vue 3 的模板编译器利用 👉 **[概念 14：AST 抽象语法树](../02-概念/14-AST抽象语法树与模块依赖图.md)** 在打包阶段看穿了模板里哪些是死节点、哪些是活节点：

```html
<!-- 模板里有大量静态节点，只有 span 的文字是动态的 -->
<div>
  <header class="nav">固定标题</header>
  <span>{{ count }}</span>
</div>
```
编译器生成的渲染代码干了三件绝活：
1. **静态提升**：把 `<header>` 提拔到 `render` 函数外只创建一次，以后渲染直接复用门牌号；
2. **靶向标记（`PatchFlags`）**：给 `<span>` 贴上数字标签 `1 /* TEXT */`，告诉 Diff：“只准比对文字，别管属性！”；
3. **拍平动态数组（`Block Tree`）**：外层 `<div>` 作为 Block，把所有子孙里的动态节点直接装进 `div.dynamicChildren = [span]` 数组——更新时**彻底绕开整棵树的遍历，直接遍历 `dynamicChildren` 数组里的这 1 个节点**！

### 2.4 第四关：快速 Diff 与最长递增子序列（LIS）
当遇到 `v-for` 动态列表更新（比如旧列表 `[A, B, C, D, E, F, G]` 变成新列表 `[A, B, E, C, D, H, F, G]`）时，Vue 3 分三步走：
1. **掐头**：从左往右跳过相同的 `A, B`；
2. **去尾**：从右往左跳过相同的 `F, G`；
3. **乱序区间求最长递增子序列（LIS）**：中间旧的剩 `[C, D, E]`，新的剩 `[E, C, D, H]`。通过 👉 **[概念 10：最长递增子序列 LIS](../02-概念/10-最长递增子序列LIS.md)** 算出 `C` 和 `D` 原来的先后顺序根本没乱，于是**让 `C, D` 原地不动**，只把 `E` 移到 `C` 前面、再把新节点 `H` 挂上去，仅用 **1 次移动** 完成重排！


### 2.5 慢放拆解：Vue 3 `patchKeyedChildren` 快速 Diff 算法的五大阶段与边界

当新旧子节点列表带有 `key` 时，Vue 3 并不会一上来就做全量复杂比对，而是按 **5 步漏斗** 层层剥离：

```text
旧子节点序列 c1 ： [ A, B,   C, D, E,   F, G ]
新子节点序列 c2 ： [ A, B,   D, C, E, H,   F, G ]
                     └──┬──┘  └────┬────┘  └──┬──┘
                   ①头同步跳过  ⑤乱序核心区  ②尾同步跳过
```

1. **阶段 1（头部同步 `i++`）**：从左向右比对相同 `key` 节点（`A`、`B` 原地 patch 复用），遇到 `C !== D` 停下；
2. **阶段 2（尾部同步 `e1--, e2--`）**：从右向左比对相同 `key` 节点（`G`、`F` 原地 patch 复用），缩小中间待处理区间；
3. **阶段 3（纯新增挂载）**：若旧节点已遍历完而新节点还有剩余（`i > e1 && i <= e2`），直接批量挂载新节点；
4. **阶段 4（纯多余卸载）**：若新节点已遍历完而旧节点还有剩余（`i > e2 && i <= e1`），直接批量卸载旧节点；
5. **阶段 5（乱序核心区 + LIS 最长递增子序列）**：建立新节点 `key -> index` 哈希表，收集新旧位置映射数组，调用 👉 **[概念 10：最长递增子序列 LIS](../02-概念/10-最长递增子序列LIS.md)** 找出相对顺序未变的节点集合（如 `[C, E]`）保持原地不动，仅对极少数乱序节点（如 `D`）调用 `insertBefore` 移动，对标记为 `0` 的全新节点（如 `H`）执行挂载！

## 4. 思考题

1. **为什么 Vue 3 要用 `Proxy` 全面替换 Vue 2 的 `Object.defineProperty`？**
2. **为什么在带输入框或子组件状态的 `v-for` 列表里，在头部插入元素时用 `index` 作 `key` 会导致输入框内容错位？**

<details>
<summary>💡 点击展开本讲思考题完整参考答案</summary>

1. **`Proxy` vs `defineProperty`**：`defineProperty` 只能在初始化时递归遍历对象已有的属性逐个改装 getter/setter，不仅初始化慢，而且拦不住“新增属性（`obj.newProp = 1`）”、“删除属性（`delete obj.prop`）”和“数组下标/长度修改”。而 `Proxy` 是贴在整个对象大门上的保镖，任何读写、新增、`in`、`delete` 操作都逃不过它的拦截，且嵌套对象只有在真正被访问（`get`）时才按需代理（惰性代理，首屏更快）。
2. **`index` 作 `key` 导致身份错配**：旧列表 `[张三(key=0), 李四(key=1)]`，往排头插入王五后变成 `[王五(key=0), 张三(key=1), 李四(key=2)]`。Diff 按 `key` 认人时，看见新排头的 `王五` 拿着 `key=0`，误以为它就是旧排头的 `张三(key=0)`，于是直接把原本属于张三的那个真实 `<input>` DOM 节点拿给王五复用，导致张三刚才在输入框里敲的字留在了王五头上！用唯一 `item.id` 作 `key` 则能精准识别出“张三和李四没变，只是排头新增了一个王五”。

</details>
